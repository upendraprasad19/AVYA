## What lives here

`lib/features/profile/` owns the 👤 Profile tab and the suite of settings
screens hanging off it. Screens:

- `profile_screen.dart` — top-of-tab rank pill + bio stats + goal card + targets + ladder + edit / photos (one row, opens the hub) / reports / settings / AVYA / share & grow (referrals, submissions, rate) / subscription / logout.
- `edit_profile_screen.dart` — full editor for the user_profile fields (name, DOB, sex, goal (Unit 3B: Build / Cut / Maintain only, `FitnessGoals.selectableTokens`; an unhealed `strength` / `recompose` opens on its healed goal and focus via `goalFormSeed`, with the RAW originals so the change is seen), weight, height, body fat, activity level, lifestyle activity, food type (`diet_preference`, shared `FoodTypeChips`, no Keto chip), diet strategy (`diet_strategy`, shared `DietStrategyChips`, only with `DietStrategyFlags` on; seeded from the EFFECTIVE strategy, saved only when a different chip was tapped, a confirm dialog at Save previews all four targets over the edited form's recompute, Cancel saves nothing; Unit 3a), injuries, equipment access, days/week, fitness experience, pace preference, target weight).
  - Profile key `diet_supplements` (diet plan Unit 4a; a bool, absent = off): written ONLY by `UserProfileNotifier.setDietSupplements` from the Diet Plan screen's Supplements switch, never by Edit Profile (its Save does not touch the key; a restore merge or a stored `false` stay as they are). Edit Profile's date of birth feeds the age gate: a date that makes the user under 18, or that cannot be read, hides the Supplements section and removes the shake and the card (the stored choice is kept). Nothing reads the key raw except `dietSupplementsInputsProvider` (it reads Hive, and is rebuilt on the restore tick because a restore never touches `userProfileProvider`'s state); everything else goes through `dietSupplementsActive` (`lib/core/utils/diet_supplements_rule.dart`), and the section shows the STORED choice (a lapsed user can still turn it off).
  - Profile key `diet_serving_view` (OI-517; 'portions' | 'grams', absent = portions; LOCAL ONLY, never pushed): written ONLY by `setDietServingView` (`lib/features/nutrition/services/diet_serving_view_actions.dart`, through `updateProfile`) from the switch on the Diet chart's calorie card, and by `completeOnboarding` (a new user = grams). Edit Profile's Save does not touch it. Read only through `dietServingViewProvider` (it reads Hive and rebuilds on the restore tick).
- `settings_screen.dart` — notifications toggle, health-sync toggle, theme (locked dark), DPDP delete account, sign out, build info.
- `reports_screen.dart` — "Coach's Weekly Dispatch" (PRO; 1 free lifetime report) — sparklines + protein/calorie/workout trend. Issue #78 (`d7b2e5`): NO video row (`video-status` is a 410 stub; the video stack stays dormant) and NO manual regenerate (a back button instead). The open-time refresh is PRO-only (`gateAndVerify`, `onFree` is a no-op, so a free user's one report is spent only by the explicit Generate tap) and at most once per IST day (`shouldSilentRefreshWeeklyReport`, `services/weekly_report_refresh_policy.dart`) because every refresh is one thinking-on Gemini call and the server has no PRO per-day cap. One `weekly-report` call at a time ACROSS screen instances via `WeeklyReportCallGate` (an observable, so a screen opened mid-call wakes and re-reads the cache; 120s call timeout; a spent free report is recognised by the 403 body code `NOT_PRO`, `isLifetimeFreeReportSpent`). Copy lives in `WardroomCopy.reportCard*`.
- `progress_photos_screen.dart` — the progress photo log (OI-348 Landing 3c, founder calls 2026-11-26). Everyone sees the gallery or the empty state, deletes by long-press and gets the Add button; the screen's verified verdict (`gateAndVerify(featureProgressPhotos)` in the single writer `_reload` and again on Add) picks `pro` (uploads uncapped) or `free` (a lapsed PRO included: ONE photo per IST week, caption `ProgressPhotoCopy.freeCaption`). ## Common pitfalls

| Pitfall | How to avoid | Source |
|---|---|---|
| "This week's free photo is in" (PhotoQuotaException) | A free or lapsed user already HOLDS a photo created this IST week (Mon 00:00 IST onward) in their Storage folder: `ensureFreeSlotOpen` counted it before the pick. An object with no row counts too until the sweep removes it (60 minutes; 2 for this device's own failed cleanup). Deleting this week's photo opens the slot again (a retake). PRO is never counted. The paywall feature string is `ProgressPhotoCopy.paywallFeature` ('Unlimited Progress Photos'), the DISPLAY string. | OI-348 Landing 3c; `test/contracts/progress_photo_free_slot_test.dart`, `progress_photos_free_flow_test.dart` |
| Progress-photo upload fails with a Storage "row-level security" error, `progress_photo_pro_required`, or `P0001 progress_photo_pro_required` | The SERVER free cap refused the INSERT: no active, unexpired `public.subscriptions` row AND an object (storage door) or row (row door) already in that IST week. The client classifies it with `isProgressPhotoProRefusal` (pure; conservative; the literal in a `StorageException` counts too) and `capture` throws `ProgressPhotoProRequiredException`; `ProgressPhotosScreen._onProRefused` answers: payment in flight → "still activating"; otherwise a forced server verify: NOT PRO → the weekly-used snackbar and a reload (never an automatic paywall), PRO or unreachable → "couldn't confirm". To diagnose, read the user's `subscriptions` row and their bucket objects / rows since Monday 00:00 IST (`public.progress_photo_week_start(now())`). A just-paid user is capped until the row exists (seconds to about 20 minutes). A bare 403 with another message (an expired token) is NOT a refusal and shows "Upload failed". Never loosen the triggers to fix one user. If the cap stops working for everyone, check that `trg_progress_photo_object_cap` still exists: the rule FAILS OPEN if it is dropped (OI-316). | the free weekly cap migration; `test/contracts/progress_photos_free_weekly_cap_rule_test.dart`; live verify `test/sql/progress_photos_free_weekly_cap_live_verify.sql` |
| Weekly Report sparkline dips to 0 between weigh-ins | By design only for calories/protein/workouts (zero-fill = genuinely no activity). Weight series is **forward-filled** from last known — if you see it dropping to zero on un-weighed days, `weeklyReportDataProvider` has regressed. | (relocated 2026-05-18 — see docs/diagnoses/INDEX.md, a local build: CLAUDE.md §4.1.5) |
| Edit Profile saves but home doesn't refresh | `ProfileWriteService` must invalidate the same provider set as the onboarding completion path: `userProfileProvider`, `homeProvider`, `dietPlanProvider` (when goal/weight changes), `nutritionTargetsProvider`. Missing any one = stale UI. | `user_full_name` SoT |
| Profile screen `usageWeeks` counter reads dead Hive key | Fixed 2026-05-20 (commit `00c36cc`). `usageWeeks` now reads `users.created_at` from Supabase, NOT the dead `configBox['signup_at']` key. Don't reintroduce a Hive-side counter — Supabase signup date is canonical. | `feedback_writer_reader_field_drift_recurring.md` |
| `usageWeeksProvider`'s only invalidation was a user retry-tap/background-restore, never the week boundary itself | Bug ff3131 (2026-09-28) — fixed via `DayRolloverObserver._doRolloverWithRef`. Same `presence_only: true` shape as bug 4018b3 (referralEligibilityProvider) — derives from `SupabaseService.instance.currentUser.createdAt`, no Hive-mutable proxy to test staleness with. | `docs/diagnoses/2026-09-28-usage-weeks-provider-invalidation-ff3131.md` |
| Edit Profile silently recomputes calories from a fabricated body-fat | `recalculateTargets` reads `body_fat_percent` and feeds it into `BmrCalculator.calculateTargets` via **Katch-McArdle** on EVERY edit. It is the CONSUMING reader of onboarding's body-fat. Pre-Unit-4, onboarding SAVED a fabricated `18.0` for skip-users (their own calc ignored it) → the first profile edit recomputed from a made-up 18% lean mass. Fixed (c3f2d8, 2026-06-14): onboarding saves `null` on skip; `BodyFatDefaultHealer` (boot) clears legacy 18.0. Never reintroduce a body-fat default — null → Mifflin is correct. | SoT `onboarding_bodyfat_calc_input`; diagnose c3f2d8 |
| Delete account leaves orphan rows | `delete_account_screen` → `delete-account` Edge Function executes the DPDP §17 hard-delete + pseudonymization. Migration 049 set ON DELETE SET NULL on `user_custom_exercises`, `user_custom_foods`, `community_reviews.reviewer_id`, `food_corrections`, `promo_code_uses`. **Read consumers MUST tolerate `user_id = NULL`** ("deleted user" preserved for community signal). | `supabase/migrations/CLAUDE.md` |
