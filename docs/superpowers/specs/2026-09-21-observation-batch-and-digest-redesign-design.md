## Part B — founder-digest redesign

### B1. Reuse existing metrics functions instead of reinventing queries

`founder_digest_content.ts`'s `gatherDigestInput` currently hand-writes queries against `usage_counters`/`alerts`/`subscriptions`/`users`. Three SECURITY DEFINER functions already compute overlapping data and are unused by the digest:

- `founder_metrics_for_admin_api()` → `total_users, signups_today_ist, signups_7d, signups_30d, pro_active, pro_expired, free_users, active_subscriptions, active_last_7d`.
- `founder_metrics_ops()` → `client_errors_today, client_errors_7d, open_alerts_count, cron_failures_24h` (already excludes `error_code='info'` noise per migrations 135-137).
- `founder_metrics_engagement()` → workouts/food-logs/AI-messages today, streak-maintained count, hold-cohort starts.

**Fix:** add three new `readSection`-wrapped calls in `gatherDigestInput` invoking these RPCs (`supabase.rpc('founder_metrics_for_admin_api')` etc.), each independently three-state (data / none / unreadable) per this file's own established convention.

**Two NEW issues from review round 2, both needing an explicit resolution before implementation (neither is a redesign, both are "decide and state it"):**
1. **Field-to-section mapping was never specified.** `founder_metrics_for_admin_api()` bundles `signups_today_ist/7d/30d` together with `pro_active, pro_expired, free_users, active_subscriptions, active_last_7d, total_users` in ONE row — none of the subscription-state fields are "new signups" data. Resolution: render `signups_*` under "New signups," and `pro_active/free_users/total_users/active_subscriptions` under a separate "Account totals" section (a genuinely new section, small addition) — never render `pro_expired` from this RPC anywhere in the digest text, since B3 now computes its own windowed "Lapsed" figure independently (see B3) and rendering the RPC's raw `pro_expired` anywhere would duplicate/contradict it with no cross-reference.
2. **`signups_today_ist` is NOT "yesterday."** Its SQL is `created_at >= date_trunc('day', now() at time zone 'Asia/Kolkata')` — a "since 00:00 IST today" gauge. The digest cron runs at 08:00 IST, so naively surfacing this under the digest's "yesterday" framing would show a partial ~8-hour count mislabeled as a full day. Resolution: do NOT use `signups_today_ist` for the "New signups (yesterday)" line at all — add a genuinely windowed count instead (`SELECT count(*) FROM users WHERE created_at >= <yesterday IST start> AND created_at < <yesterday IST end>`, reusing `istYesterdayWindow` like every other section already does). `signups_7d`/`signups_30d` from the RPC ARE safe to surface as-is (rolling windows ending "now," correctly labeled as such, not "yesterday").

- **BLOCKING finding from review round 1, addressed here: this ignores an existing, load-bearing privacy control that governs exactly this data.** `coach_memory.private_mode` (`supabase/migrations/027_create_coach_memory.sql:36`, boolean, default false) is a real user-facing opt-out ALREADY checked by 7+ functions before surfacing a user's name anywhere — `re-engagement`, `morning-alert`, `plateau-alert`, `pr-detection`, `protein-gap-alert`, `workout-window-closing`, `daily-snapshot`, `ai-proxy`. The established precedent, confirmed live: `re-engagement/index.ts:299-317` resolves a first name only `if (!isPrivate)`. "Mirror re-engagement's pattern" cannot mean adding DB calls inside `buildDigestText` without breaking that purity contract. **Correct wiring:** in the IMPURE `gatherDigestInput`, batch-fetch `private_mode`+`full_name` for every distinct `user_id` already present in `windowed.rows` (one query, `.in('id', distinctUserIds)` against `users` joined to `coach_memory`) and thread the resulting `Map<userId, {firstName: String?}>` through a new field on `DigestInput`. `buildDigestText` stays pure — it only ever reads from that pre-built map, never queries anything itself.

### B3. Revenue (new MRR) + churn tracking

- **Writer investigation result (resolves open question 4 below):** grepped both `supabase/functions/` and `lib/` for any code path that writes `subscriptions.status = 'cancelled'` — **there is none.** Every `'cancelled'` reference in the repo is a READ-side filter (e.g. `founder_metrics_admin_function.sql` excluding cancelled rows from a count). The `cancelled` rows currently live in the table were set by a manual dashboard/SQL edit, not by any app code. This means "patch the writer to also set `cancelled_at`" has no single call site to patch.
- **Revised fix, stronger than the original plan:** a `BEFORE UPDATE` trigger on `subscriptions` — `IF NEW.status = 'cancelled' AND OLD.status IS DISTINCT FROM 'cancelled' THEN NEW.cancelled_at := now(); END IF`. This is self-maintaining regardless of HOW the status changes (manual dashboard edit today, a future automated cancellation flow, an admin script) — no future writer can forget to set it, because nothing needs to. Add `subscriptions.cancelled_at timestamptz null` in the same migration (nullable, no backfill for historical cancellations — the founder explicitly accepted "not tracked retroactively, only from the migration date on").
- **New MRR (yesterday):** sum plan price (₹349 monthly / ₹2,999 yearly, per CLAUDE.md §1 — derive from `plan` text value, no price column exists) over `subscriptions` rows with `created_at` in yesterday's IST window and `status='active'`. **Caveat surfaced by review round 1:** `razorpay-webhook/index.ts:130-143` shows promo codes discount the actual captured amount, and the discount is never persisted on the row — a promo-redeemed signup overstates "New MRR" by the discount amount. Digest copy must carry a one-line caveat ("gross, before promo discounts") rather than presenting this as an exact figure.
- **BLOCKING finding from review round 1, addressed here: "churn" as originally designed would read ~0 forever except on a manual dashboard edit, silently hiding the dominant real churn mode.** This project's own canonical subscription-state doc, `supabase/functions/_shared/subscription.ts:8-20`, states plainly: *"`status` is NEVER reconciled to 'expired' by any job, cron or trigger... At the time of writing, live production held 5 `status='active'` rows and zero of them were unexpired [i.e., some were actually past end_date while still marked active]."* The dominant real-world churn event — a subscription simply not renewing at `end_date` — never touches `status` at all and would never fire B3's `cancelled_at` trigger. As specced, "Churn: 0" on every normal day reads to the founder as "nobody churned," which is exactly the bad-news-vs-no-news collapse this project's own culture is built to catch (`feedback_bad_news_vs_no_news.md`, cited repeatedly in project history).
- **Corrected churn definition, revised AGAIN per review round 2 — do not reuse `pro_expired` as originally planned:** round 2 verified `private.founder_metrics()`'s live SQL body has **no lower bound** on `subscription_expires_at` (`subscription_expires_at <= now()`, full stop) — it's a point-in-time CUMULATIVE total of every user ever lapsed, not a "lapsed yesterday" figure. Using it as "yesterday's churn" doesn't fix the original bad-news-vs-no-news problem, it relocates it: instead of "Churn: 0" forever (silently hides real churn), the founder would see a large, near-static number every day that LOOKS like daily tracking but isn't — arguably worse, since a constant 0 invites suspicion while a slowly-drifting nonzero number reads as legitimate. Report TWO distinct, GENUINELY windowed figures instead: (1) **"Cancelled (manual)"** — count of rows with `cancelled_at` in yesterday's IST window (manual-dashboard-action only, will read 0 most days — correct and expected). (2) **"Lapsed"** — a NEW windowed query, NOT the `pro_expired` RPC field: `SELECT count(*) FROM users WHERE subscription_status = 'pro' AND subscription_expires_at >= <yesterday IST start> AND subscription_expires_at < <yesterday IST end>` (verified live during review: syntactically sound, runs cleanly, returns a small plausible number on a representative day — `subscription_status` staying `'pro'` indefinitely past expiry, per `subscription.ts`'s own documented non-reconciliation behavior, is exactly what makes this the correct proxy for "PRO access that lapsed yesterday specifically," not a workaround). Use `istYesterdayWindow`'s existing bounds (already computed in `gatherDigestInput` for every other section) — do not recompute the window separately. Never merge these two figures into one "Churn" line.
- Both figures, once `cancelled_at` exists, read 0-for-cancellations for all history before the migration lands (expected, stated explicitly as "manual-cancellation tracking started 2026-09-21" in the digest copy — not silently shown as a bare 0).

### B4. Real-time Health-threshold alert — REDESIGNED per review round 1: this infrastructure already exists, live, today

- **BLOCKING finding from review round 1, addressed here: this was scoped as greenfield ("TBD... new Edge Function?") against infrastructure that is already deployed.** Live `cron.job` query (re-verified) shows **five existing pg_cron jobs already doing exactly this pattern** — plain SQL, no Edge Function, no new secret: `INSERT INTO public.alerts (...) SELECT ... WHERE <threshold> AND NOT EXISTS (<dedup>)`, all already wired to `trg_dispatch_critical_alert_notify` (migration 133) for real-time Telegram paging:
  - `alert_client_errors_spike` (every 15 min) — counts `client_errors` in the last 1h, critical≥500/warn≥250, dedup via `NOT EXISTS (...acknowledged=false AND detected_at > now()-1h)`.
  - `alert_cron_silence` (hourly), `alert_cron_function_dead` (daily) — watch for cron jobs going silent.
  - `alert_edge_function_health` (every 15 min), `alert_payment_flow_health` (hourly).
  - This is the exact "check prior art before proposing new monitoring infra" step that should have run before this section was drafted — corrected now, not glossed over.
- **Corrected design, two parts:**
  1. **Client-errors burst — do NOT add a second, differently-tuned duplicate.** `alert_client_errors_spike` already exists with its own filter (100/hr) and its own dedup convention (`acknowledged`-based, 1h window) — different from both this spec's originally-proposed 15/hr AND from `gemini_failure_alert.ts`'s `resolved_at`+severity-downgrade convention. Shipping a THIRD alert mechanism with a THIRD dedup convention on overlapping data is confusing, not additive. **Decision: tune the existing `alert_client_errors_spike` job's thresholds if 100/hr is too insensitive at current scale, rather than add a parallel mechanism.** This is a one-line migration editing existing SQL, not new infrastructure.
  2. **Cron-failures alert — genuinely novel, keep it, same lightweight idiom.** None of the 5 existing jobs check `cron_call_log` for `status='failed'`/stuck-`status='started'` the way `founder_metrics_ops()`'s `cron_failures_24h` does. Add this as a 6th SQL-only `cron.schedule(...)` job, same pattern as the 5 existing ones (a plain `INSERT ... SELECT ... WHERE ... AND NOT EXISTS(...)`), NOT a new Edge Function. **Noted per review round 2 (not blocking, state it rather than leave it implicit):** this job's subject matter overlaps two existing jobs on a different time horizon — `alert_cron_silence` (fleet-wide, no success in 2h) and `alert_cron_function_dead` (one function, no success in 8 days). A persistently-failing function could eventually trigger all three for one root incident, at three different speeds. Acceptable — different time horizons genuinely serve different purposes — but the diagnose-doc/migration comment should say so explicitly.
- **Dedup convention:** use the SAME `acknowledged`-based convention the 5 existing jobs already share, not `gemini_failure_alert.ts`'s `resolved_at`+severity-downgrade convention — picking the majority existing pattern rather than adding a third one. (This table currently has two incompatible dedup conventions coexisting; don't make it three.)
- **Threshold values — CORRECTED, review round 2 caught my own citation error.** I originally reported `alert_client_errors_spike` as "100/hr critical, 250/hr..." — this is backwards. Verified live via `pg_get_functiondef`: the real mapping is **100/hr = floor to insert anything at all (severity `info`, does NOT page), 250/hr = `warn` (does NOT page), 500/hr = `critical` (the ONLY tier `trg_dispatch_critical_alert_notify` pages on, confirmed via `pg_get_triggerdef`: `WHEN (new.severity = 'critical')`)**. If tuning this job's sensitivity, the number that actually controls paging is the 500 threshold, not 100. Cron-failures alert fires on **any value ≥ 1** in a `cron_call_log` check (genuinely new, still a Phase-1 placeholder per `alerts/_thresholds.yaml` convention).
- **NEW cross-cutting note from review round 2, not previously discussed anywhere in this spec:** `trg_dispatch_critical_alert_notify` is the SAME downstream paging trigger for BOTH `gemini_failure_alert.ts`'s inserts (A5/OI-226) and every SQL cron job's inserts (including `alert_client_errors_spike` and this new 6th job). Before this batch, `client_errors` had zero rows from Gemini-failure symptoms (verified live under A5) — so a Gemini outage could never reach `alert_client_errors_spike`'s threshold at all. A5's own client-side fix (adding `ErrorTelemetry` calls to previously-silent AI/network catch blocks) will, for the first time, let a sufficiently broad/sustained Gemini outage populate `client_errors` AND independently cross `gemini_failure_alert.ts`'s 30-min dedup — meaning a single incident could now page the founder TWICE, under two unrelated-looking `source` labels, with no cross-reference between them. Unlikely to double-fire at current ~32-user scale (reaching 500 client_errors/hr from Gemini failures alone is a lot), but stating this explicitly in the diagnose-doc is the honest thing to do rather than leaving it as a silent side effect to be discovered mid-incident. Not a blocker — redundant signals for a real incident are arguably fine — but must be a stated, conscious decision, not an accident.
- **Cadence:** matches whichever existing job pattern is followed — the existing jobs already resolve the boundary-miss concern (rolling window, re-checked every 15 min catches a burst within 15 min of crossing) — state this explicitly rather than leaving cadence open.
