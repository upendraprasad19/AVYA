# Exercise animations in the app (Batch M2, OI-440 and OI-354): design

Status: DRAFT r2 for founder review, 2026-10-28. Nothing is built. Parent programme: `docs/superpowers/specs/2026-10-21-exercise-library-comprehensive-design.md`. Builds on Batch M1 (`docs/plans/2026-10-27-library-batch-m1-media-data.md`, `docs/operations/EXERCISE_MEDIA.md`). r2 folds in: the founder's old-exercise picks, OI-354 (the Active Workout hero tile and full-screen viewer), the builder check of r1 and the founder's answers of 2026-10-28.

## 1. Intent and why

M1 put 616 Wardroom animations (animated WebP, 720 x 720) in a private Storage bucket, `exercise-media`, and wrote three keys on 617 library rows (`media_slug`, `media_version`, `media_source`). Nothing in the app reads them. A user still sees a small gold drawing (a "plate") or, with no drawing, the exercise's initials.

M2 makes the app show the animation wherever it shows a plate today, and builds the Active Workout hero tile and full-screen viewer that the founder designed on 2026-10-18 (OI-354, blocked only on this delivery path). The founder's words (2026-10-28): "when I see the different exercises... there where the plates were visible instead of the plates, the WEBP files should be there to show me the exercise animations. And from the weekly calendar wherever the plates are visible right now."

Success for the founder: after onboarding, a user opens their workout and sees the exercise pictures move where drawings used to be, on the phone and on the web, without waiting and without surprise data use. This holds for every exercise that has an animation. On an M2-only build that is the 617 new rows, a small share of a generated plan; most of a plan animates once the old-row mapping (OI-443, call C23) is in.

## 3. Decisions the founder made (2026-10-28)

1. **Where:** the animation replaces the plate everywhere a plate shows today (the sites above).
2. **Mobile data:** the bulk download of a plan's animations happens on Wi-Fi only. Opening an exercise whose animation is not saved on the phone fetches that ONE file on any connection (mobile data included).
3. **No Profile switch** for mobile-data downloads.
4. **Access design A:** any logged-in account reads directly with its own login (the existing policy stays). No counted-links Edge Function in M2. The app keeps a download budget of its own. Every download goes through ONE place in the app so counted links can replace it later by changing that one place. The launch gates stay on the board: CAPTCHA at sign-up (OI-445), the Pro plan, Spend Cap off and a usage alert (OI-444).
5. **Tiles:** a still picture on the 44 px tiles; the moving animation on tap.
6. **OI-354 is part of M2:** the hero tile and the full-screen viewer are designed here ("Add 354 style and viewer to the M2 design").
7. **The old-row picks** (OI-443) are mapped by an agent after the equipment check; the founder said the equipment check of the 160 picks should be done.
8. **The picture check of the 529 never-compared new animations is LATER** (founder: "we will do it later"). It is appended to OI-443 and does not block M2. It stays a hard gate before the store launch (my default, section 6).

## 4. Calls I made (the founder has not seen these; each is reversible in the plan review)

- **C1. Small tiles stay still.** The 44 px tile in the plan list, the calendar day sheet and the collapsed active-workout header shows the bundled 192 px still (founder decision 5). The animation plays in what a tile opens (the bottom sheet on the plan list and the calendar, the full-screen viewer on the active workout, C17) and in the OI-354 hero tile (C16).
- **C2. The stills ship inside the app** (3.1 MB for the 616, about 3.9 MB with the old-row picks), so a tile is correct on the first frame, offline, with no download. A build step copies them from the founder's folder into the repository and a test checks each against `thumb_sha256`.
- **C3. Fallback chain, per row:** saved animation -> the bundled still -> the plate drawing -> the initials. After the old-row mapping a row can have both a still and a plate (116 rows); the animation side wins.
- **C4. A refused or failed read is "retry later", never "no animation".** On the authenticated route a forbidden read and an absent object both answer HTTP 400 (observed 2026-10-27), so status alone cannot say "this row has no file". A mapped row always has a file; the app keeps showing the still and tries again on the next open (back off after repeated failures).
- **C5. Cache by object name** on the device. The name carries the version (`_v<n>`), so a name never changes content, and the signed-link response has no `Cache-Control` (observed), so the client cannot rely on HTTP caching. A size cap with least-recently-shown eviction that never evicts a file used by the current plan window. First value: 150 MB (about 365 average files). Sizing: a 7-day window holds about 30 to 50 distinct exercises, so at full coverage it needs at most about 20 MB and today about 8 to 15 MB. The cap is generous on purpose; the builder may lower it.
- **C6. Wi-Fi prefetch scope = the plan window**, not the library: the exercises of the next 7 days of scheduled workouts, one or two downloads at a time, paused when Wi-Fi drops, resumed when it returns. A per-day byte ceiling on prefetch (first value 60 MB per device per day) guards against a loop. This is the "Wi-Fi budget" of OI-440.
- **C7. Free to every tier**, like the plates. The founder's rule is "installed and logged in"; I did not add a PRO gate. (Reversible when reading.)
- **C8. The cache is not user-scoped.** The files hold no personal data; they stay after sign-out. The delete-account flow has nothing to purge for this bucket.
- **C9. Kill switch** `configBox['disable_exercise_animations']`, default ON feature (cosmetic, additive), same pattern as `plate_flags.dart`. Set, the app behaves exactly as it does today (plates, no hero tile, no viewer). A test proves the OFF behaviour is the current behaviour.
- **C10. Motion:** loop forever; honour the system "reduce motion" setting by showing the first frame with a play button (as OI-354 specifies).
- **C11. Rendering memory:** decode the animation at display size (a resized image provider), not at 720 x 720 (one decoded 720 px frame is about 2 MB; the largest file has 24 frames). Only the visible hero tile or the open sheet or viewer plays; nothing else animates.
- **C12. Not user-visible but binding:** the app reads the bucket with plain HTTP GET on `/storage/v1/object/authenticated/exercise-media/<name>` using the user's session token, in ONE class, NOT through `storage.from` (the trap in section 8).
- **C13. Budgets.** The 60 MB per day ceiling (C6) limits the background prefetch only. An on-demand fetch (one file per open, founder decision 2) is never blocked by it; it is counted. Every download, prefetch or on-demand, adds to a local counter reported through the existing telemetry, so the Supabase usage alert (OI-444) has a client-side companion. The budget does not stop someone who calls the API directly; under access design A that is accepted and is what OI-445 (CAPTCHA) and OI-444 are for.
- **C14. If the Task 1 spike fails, the fallback ladder is pre-approved** and none of it touches an Edge Function: (a) if the browser blocks the authenticated route (CORS with an Authorization header), the web path asks `POST /storage/v1/object/sign/exercise-media/<name>` over plain HTTP with the user's token and GETs the returned link (M1 observed `Access-Control-Allow-Origin: *` on a signed response); (b) if an animated WebP does not decode or animate on a platform, that platform ships the bundled stills only (the sheet and viewer show the large still), which is still a visible improvement over initials. Neither uses `storage.from`, so the delete-account contract and `user_owned_buckets.ts` stay untouched.
- **C15. Mixed lists.** The still tile uses the same 44 px rounded frame, border and background as the plate tile so a list of drawings, stills and initials reads as one set; the builder checks it on a device (the plate comment in `exercise_plate_thumb.dart` already warns about card height).
- **C16. The OI-354 hero tile lives in the FOCUSED active-workout card only**, so at most one animation plays on that screen. `isExpanded` is not enough (a superset partner is expanded too), so `screen.dart` passes the card one more flag, `isFocused` (true only for `_effectiveFocusedIndex`). A superset partner that is expanded but not focused keeps the compact header and the 44 px thumb; in move mode no card is expanded and none shows a hero; when every exercise is done the last card stays focused and shows its hero as a still. It is the square tile of OI-354: about half the card width, centred ENLARGE overlay, a fold back to the 44 px thumb while the keyboard is open (C21), first frame plus a play button under reduce-motion. While the hero shows, that card's 44 px header thumb is hidden (so the same exercise is not drawn twice); it returns when the hero folds or the card is not focused. A card for a row with no animation keeps the compact header and the 44 px thumb (a permanent fallback). While the file is not yet on the phone the tile shows the bundled still and the animation fades in when it arrives.
- **C17. Viewer versus sheet.** One entry-point rule. **On the active workout screen** every picture door (the hero tile's ENLARGE, the 44 px header thumb, the "VIEW PLATE" link) opens the OI-354 full-screen viewer (animation edge to edge, form and cues below, a sticky BACK TO WORKOUT, no bottom sheet) **when the row has an animation**; for a row with only a plate drawing or only initials, those doors open today's bottom sheet unchanged, so the viewer never has to draw a plate. **On the plan list and the calendar** every tile opens the bottom sheet, which for a row with an animation shows the moving animation in place of the START and END drawings (a lighter surface for a glance) and for any other row is today's sheet. When the file is not yet on the phone, the viewer and the sheet open with the still and the animation fades in on arrival. Whether the sheet and the viewer share one widget is the builder's call.
- **C18. A mockup first.** Because the two mockups OI-354 names are not in the repository, the plan's first UI task produces a mockup of the hero tile in its states (still, loading, playing, reduce-motion, typing fold, viewer) through the `/ui-mockup` skill for the founder to approve before any widget is written.
- **C19. The old-row mapping is data work, not app work.** After the founder settles the 11 held pairs (section 6; the 148 other pairs do not wait for them), an agent builds the `--old-rows` file, uploads about 160 files and bumps the library seed (OI-443). The app code does not change for it: a row simply starts carrying media keys. Until then the old rows keep their plates.

- **C20. Wi-Fi on native, never on web.** Bulk prefetch runs only when the connectivity list holds `wifi` or `ethernet` (the OS reports a phone hotspot as Wi-Fi and the app cannot tell; accepted). An unknown or absent connection type counts as NOT Wi-Fi (fail closed, decision 2). A browser cannot report Wi-Fi versus mobile data, so **on web the bulk prefetch never runs**; web still fetches the one animation a user opens, on any connection, and keeps what it fetched in the browser store (C5). The fake-connectivity test asserts: native with `wifi` or `ethernet` runs; `mobile` only, `none` or empty does not; web never.
- **C21. The fold keys off the keyboard, not a "typing mode".** The hero folds to the 44 px thumb while the focused card sees `MediaQuery.viewInsets.bottom > 0` and unfolds when it closes. This works whether or not the card is in log mode (set-field focus nodes exist only in log mode, so they cannot be the trigger). The fold changes the layout above the field the user just tapped, so the builder checks on a device that the tapped field stays visible and under the finger; if it does not, the fold shrinks the tile instead of removing it.
- **C22. The two kill switches.** `disable_exercise_plates` (existing) silences every picture surface: tiles show initials, the sheet does not open, and no animation surface (still tile, hero, viewer) shows. `disable_exercise_animations` (new, C9) silences only the animation surfaces and leaves the plates working. So animations are active only when both are unset. The OFF tests cover the three combinations: plates off (today's plates-off behaviour), plates on with animations off (today's behaviour), both on (the new behaviour).
- **C23. Order against OI-443, and how it is verified.** M2 may merge before the old-row mapping lands. Until then only the 617 new rows animate, which is a small share of a generated plan. The data step of OI-443 (the 147 checked pairs, about 66 MB of uploads, a seed bump) needs no app code, so it can run before or beside M2 and is the way the device check gets a realistic plan; the founder's go is needed for its live upload. The tests do not depend on the generator: they seed library rows that carry the media keys. The device check uses a plan or a swap that holds rows with media.

## 5. What the user sees

- **Calendar day sheet, collapsed active-workout header (and the unused plan-list card, section 2):** the 44 px tile shows the still of the animation for a row with media; a row with only a plate keeps its drawing; a row with neither keeps its initials.
- **Tap a tile in the calendar day sheet:** the sheet opens at once with the still in the large frame; when the file is on the phone it starts moving immediately; when it is not, it downloads (any connection) and the still turns into the animation when it arrives; offline or on failure the still stays. The form cues and breathing cue under the picture are unchanged.
- **Active workout, the focused exercise (when it has an animation):** a square tile plays the animation next to the sets. ENLARGE (or the thumb or VIEW PLATE) opens the full-screen viewer; BACK TO WORKOUT returns. While the keyboard is open the tile folds to the 44 px thumb. A superset partner that is not the focused card keeps the compact header and thumb. A row without an animation behaves exactly as today.
- **Wi-Fi:** the first time the plan is on screen, the animations for the next 7 days download quietly.
- **Switch off:** the plates return exactly as today.

## 7. Goals, non-goals, anti-goals

Goals: animations on every plate site for rows that have one; the OI-354 tile and viewer on the active workout; works offline once saved; phone and web; bounded data use; one download place; a kill switch.

Non-goals: new animations or the intake tool (OI-441); the 40 core rows and other rows with no animation (OI-442); the picture check (OI-443); counted links or a per-account cap (option B, not chosen); any change to the plan generator or the library data in the app; PRO gating; fixing equipment tags (the founder's call, section 6).

Anti-goals (a failure even if it technically works): a spinner or a blank frame where a tile was; a workout screen that waits for the network; bulk download on mobile data; a user with a missing file seeing an error box; more than one animation playing at once on the workout screen; the animation reachable by a signed-out request; the delete-account purge test weakened to get green.

## 8. Constraints and traps

- Hive-first and offline-first (root rules 1 and 4): the UI never waits for the network; widgets do not call Storage or Hive directly. The fetching class is a repository-style class behind a Riverpod provider.
- `test/contracts/delete_account_purges_all_user_buckets_test.dart` (message at line 181) fails any `lib/` file that names a bucket through `storage.from` until `supabase/functions/_shared/user_owned_buckets.ts` carries the documented "holds no user-owned objects" treatment. M2 reads over plain HTTP (C12). It does not weaken that test.
- Tile widgets rebuild about once a second on the active workout screen: resolve in `initState` / `didUpdateWidget`, not in `build()` (`exercise_plate_thumb.dart` header).
- The seed is already v16 (`seed_service.dart`); the three media keys are on installed rows after one launch. The old-row mapping bumps the seed again (OI-443). Community rows can hold any JSON type: guard with `is String` / `is int`.
- Platform tier: `pubspec.yaml` is pinned `platform` in `docs/blast_radius.yaml` and bundling the stills needs a pubspec asset entry, so the batch needs the full two plan-review rounds, a plan-review record and a B-pass, and carries the C9 kill switch. The hero tile and viewer are UI on the active workout screen, a large existing file (`exercise_card.dart`, `screen.dart`), which makes the plan a candidate to split (section 11).
- All copy and UI (ENLARGE, BACK TO WORKOUT, the play button, any empty state) goes through the Wardroom brand soul (`lib/shared/widgets/wardroom/CLAUDE.md`) before it is written; "VIEW PLATE" may need a new label once the picture moves.
- Web: a Flutter web build has no file system. The builder must give the web path a persistent store that survives a reload and obeys the same cap (Hive on web is IndexedDB), and must check that the authenticated route works from the browser (CORS with an Authorization header).
