# APK Test #12.4 — observation-driven hotfix batch (2026-05-06 evening)

**Branch:** `feat/apk-test-12-4-batch`
**Trigger:** Founder install of APK Test #12.2 (versionCode 9) — three regressions surfaced.

## Findings (root causes)

### #1 — Jump Rope renders "540 reps" on receipt cards
- Cloud row: `logging_type=timed`, `set_number=2`, `reps=1080`, `duration_seconds=NULL`
- Bundled exercise library says Jump Rope = `timed` (correct)
- **My Test #12.2 `LoggingTypeRepairMigrator` introduced a regression:** when library says `timed` but data has `reps>0` and no duration, the library-consistency check returned false, and the migration's data-driven fallback flipped Jump Rope to `bodyweight_reps`. Receipt then renders bodyweight chips with reps from the corrupt data (per-set `reps=540` × 2 sets).
- **The right policy:** library wins for known exercises. Migration should fix the DATA to match library, not flip the type to match corrupt data.

### #2 — Train calendar expanded row shows "0 sets · 26 reps · 85.0 kg"
- Sibling renderer at `train_screen.dart:808 _buildExpandedExercises` was missed in Test #12.2 — it still uses single-source `log['sets_completed']` (returns 0) and raw `log['logging_type']`.
- I patched the bottom sheet at `train_screen.dart:1110` but missed this one despite it reading from the SAME `WorkoutRepository.getExerciseLogsForDate`.
- **Source-of-truth audit failure on my part** — should have grepped all renderers in the same batch.

### #3 — Breakfast meal saved but UI doesn't reflect it
- Cloud confirms: nutrition_logs row + nutrition_log_items entry both landed.
- `food_search_sheet.dart:498` save callback calls `NutritionWriteService.logMeal` successfully and shows the toast — but **does NOT invalidate the today's-meals provider**. Same class as the PRO cold-start bug — write succeeds, UI doesn't know.

## Per-task plan

### Task #1a — Migration v2 (library-strict)

**File:** `lib/core/services/logging_type_repair_migrator.dart`
**Bump flag:** `_flagKey` from `'logging_type_repair_v1_done'` → `'logging_type_repair_v2_done'` so devices that already ran v1 (corrupted by my regression) re-run v2 and get the fix.

**New logic:**
```
if (libByName.containsKey(name)) {
  final libType = libByName[name];
  if (libType == 'timed') {
    // Trust library. Migrate data to match.
    if (hasReps && !hasDur) {
      // Move top-level reps_completed to duration_seconds.
      m['duration_seconds'] = reps_completed_value;
      m['reps_completed'] = 0;
      // Same for per-set entries: move sets[i].reps to duration_sec.
      // Clear weight_kg if zero (timed exercises don't have weight).
    }
    m['logging_type'] = 'timed';
    return correction;
  }
  if (libType == 'bodyweight_reps') {
    if (hasDur && !hasReps) {
      // Move duration → reps (rare, but symmetric).
    }
    m['logging_type'] = 'bodyweight_reps';
    m['weight_kg'] = 0.0; // bodyweight has no weight
    return correction;
  }
  if (libType == 'weight_reps' || libType == 'weighted_bodyweight') {
    m['logging_type'] = libType;
    return correction;
  }
}
// Custom exercises (not in library) — fall back to data-driven.
```

**Key change:** library type is final for library-known exercises. Data is migrated to match, not the other way around.
