## Decisions (each has a safe default; a reversal is another full pipeline run, because the registry is platform tier)

**D1 — Width and boundary: the engine class under ONE written rule of three prongs.** The five files OI-282 names were a sample from where the problem was found, not a boundary; leaving the rest at account would leave its own stated problem ("sync-engine changes skip the platform review tier") half-open. The tier definition is "Multi-user data integrity, sync, or cross-account" (registry, the `platform` tier line). Round 2 showed the first draft's line was drawn by no single rule (it promoted two restore-merge helpers while declining the file hosting the freeze merge, and called a migrator "one-shot" against its own header); the B-pass showed the rewrite still applied its cap, its cross-account hook and its scope unevenly. The rule, written once in the registry block's header and applied to EVERY `lib/` file an engine file imports, exports or declares as a part: **platform when the file is (1) engine machinery (it itself pushes, queues, retries, serialises, probes, pages or runs a restore merge), listed whatever its churn; or (2) cross-account isolation the engine registers with; or (3) shared with other code, but its own words say a function in it MERGES the cloud copy with the local one, supplies the identity a push keys on, gates a push, or is a rule the restore merge itself delegates to, AND promoting it alone adds at most one newly-platform commit per 60 days (measured against the base registry; the cap attaches to prong 3 only). A file the engine only consults (a type, an accessor, a utility, telemetry, transport, ingest, a domain read, a payload builder, a computation applied to the winners, a writer) stays below platform and is declined by name, with the engine-called function.** Applied (evidence and per-file costs in the diagnose doc): promoted under prong 3 `streak_progress_service`, `template_identity_migrator`, `template_identity`, `day_swap/day_swap_rules`, and, outside the services layer, `lib/shared/repositories/user_repository.dart` (`mergeCloudProgress`) and `lib/features/profile/services/notification_prefs_repository.dart` (`adoptFromCloud`) (costs 0, 0, 0, 1, 0, 0); machinery kept whatever it costs, `sync_queue` (+2) and `plan_integrity_reconciler` (+3); declined with the engine-called function `workout_schedule_read_service` (7 alone, over the cap), `workout_write_service` (5) and `nutrition_write_service` (4) (both meet the verbs and are held by the cap; recorded because their explicit account rules would otherwise hide the decision), `template_service`, `day_swap/day_swap_result`, `health_sync_service`, `migrated_key`, `restore_telemetry_policy`, `result`, `supabase_service`, `error_telemetry`, `subscription_service`, `profile_target_recompute` and seven more consulted files outside the layer. Judgment calls, flagged for the founder rather than asked, each reversible by one rule: the two schedule restore-merge helpers (OI-285 already calls the schedule merge platform tier), `singleton_lifecycle_registry` (a cross-account reset hook, same class as `hive_user_session.dart` / `guarded_box.dart`), the six prong-3 promotions, the cap of one commit per 60 days (a tunable), and the declines of `supabase_service`, `profile_target_recompute` (the one file that passes the cap but not the verb list: disclosed borderline) and the two write services. **Callers are a stated scope limit** (B-pass round 2): the boundary applies to what the engine files REACH, so a file that merely CALLS the engine is outside what the derivation can see and is judged on its own words. Two are known and both stay below platform: `auth_session_bootstrapper.dart` (its `hydrateFromCloud` runs a second restore merge, the twin of the engine's `_restoreUserProgress` by its own comment, so prong 1's "runs a restore merge" is met literally; 6 commits touch it, 3 would be newly platform) and `lib/shared/providers/sync_state_provider.dart` (decides WHEN the engine retries; 3 touch it, 1 newly platform). The reason is scope, NOT cost (the first fold had offered the cap for the bootstrapper, which the registry confines to prong 3): a promoted caller must become a derivation root, pulling its own imports into the declined map, and the bootstrapper is mostly auth routing under a `feature_flag` it would newly owe. Both are decided by name in a `_callers` map pinned by a test (each entry stays below platform, is not reached by an engine file, and still makes the named call, comments stripped) and disclosed to the founder as one-rule flips. `supabase_service.dart` stays declined with its real shape named (`callFunction` cold-start retry and `ensureFreshToken` coalescing are called by the orchestrator, but the same transport serves AI, payments and telemetry; promoting it adds no commit alone but would pull every transport change into the sync review). There is no "narrow later" escape hatch: the set that is reviewed is the set that ships.

**D2 — Exact paths + a derived completeness test over every engine file's imports, exports and `part`s across all of `lib/`, not a `sync_*.dart` glob and not one file's imports.** The registry's own SoT entry says exact paths are deliberate because a glob auto-promotes future files with nobody deciding, and a name glob would have missed `serial_slot.dart`, `backend_probe.dart` and `paginate_all.dart`. The repo's cure for this class (a3d7b1) is DERIVE the set from a source of truth, name the exclusions with reasons, and fail "until its tier is decided". The first draft rooted the derivation at `sync_service.dart` alone and read only single-quoted imports; both round-2 reviewers found that a promoted file's own imports then escape (`day_swap/day_swap_rules.dart` was imported by a platform file and decided by nobody). The B-pass found two more holes of the same class: `part` directives were not read at all (`sync_service.dart` declares nine part files, so a part placed outside `sync/` and not named `sync_*.dart` would be invisible), and the scan stopped at the services layer (`UserRepository.mergeCloudProgress` is a restore merge living in `lib/shared/repositories/`). Now the roots are the listed exact paths, everything under `sync_domains/` and `sync/`, and any `sync_*.dart` on disk (40 roots); the reader takes every quoted URI of an `import` / `export` / `part` / `part of` directive (single or double quoted, conditional-import alternatives, no space after the keyword, several directives on one line), resolves relative URIs against the importing file's own directory, keeps any `lib/` path, and is itself tested on a synthetic source. The derived set (the family on disk plus everything the roots reference) is 64 files. "Decided" means platform OR declined by name, never "some rule claims it": a declined entry must exist, carry a reason, still be derived and stay below platform, so a stale entry fails and an explicit account rule written for another reason no longer hides an undecided file. An exactness test pins the policy: each engine path is claimed by its own exact rule, a brand-new `sync_*.dart` is NOT claimed, and no platform wildcard exists under `lib/core/services/` besides `sync/**` and `sync_domains/**`. `sync_domains/**` is a directory glob on purpose (a whole directory of wrappers, like `sync/**`). Known limit, written in the test header: it follows what the engine files reach, one hop, and cannot see a CALLER of the engine; the two known callers (`auth_session_bootstrapper.dart`, a second restore writer, and `sync_state_provider.dart`, the retry scheduler) are decided by name in the test's `_callers` map and any other caller is not found.
