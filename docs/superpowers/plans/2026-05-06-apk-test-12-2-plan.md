## Per-task plan

### Task #3 — log-client-error validator widen

**File:** `supabase/functions/log-client-error/index.ts`
**Change:** Replace `VALID_ERROR_CODES` Set check with: accept any non-empty string ≤ 64 chars. Truncate longer strings. Keep `VALID_PLATFORMS` check as-is.
**Why not normalize on client:** that's correct in the long run, but right now we need to UNBLOCK telemetry first. Server-widening costs nothing; we can normalize client-side later when we have data.
**Deploy:** via `node .claude/deploy_via_api.js` (per CLAUDE.md). `verify_jwt: true` stays.
**Acceptance:** any subsequent dead-letter logs land in `client_errors`. Verify via `SELECT count(*) FROM client_errors WHERE created_at > now() - interval '5 minutes'` after a manual client trigger.

### Task #1 — Train view + Receipt 3rd fallback

**Writers identified:**
- `WorkoutWriteService.logExercise` — writes `set_number=mergedSets.length` and `sets=[…]`
- `EditWorkoutLogSheet._save` — writes `sets_completed`, `sets_detail` (legacy)
- Pre-Test-#6 writers — wrote `sets_detail` only (now in user's Hive as legacy data)

**Readers (need fix):**
- `train_screen.dart:1195` — already has Test #12.1 MAX of (set_number, sets_completed). Needs 3rd fallback.
- `workout_receipt_card.dart:280` — same.

**Fix:** extend the MAX to cover array length:
```dart
final fromSetNumber = (log['set_number'] as num?)?.toInt() ?? 0;
final fromSetsCompleted = (log['sets_completed'] as num?)?.toInt() ?? 0;
final setsArray = log['sets'];
final fromSetsArrayLen = setsArray is List ? setsArray.length : 0;
final setsDetail = log['sets_detail'];
final fromSetsDetailLen = setsDetail is List ? setsDetail.length : 0;
final sets = [fromSetNumber, fromSetsCompleted, fromSetsArrayLen, fromSetsDetailLen]
    .reduce((a, b) => a > b ? a : b);
```

**Acceptance:** founder's existing edited workouts render correct sets count. Pinned by extending `test/contracts/edit_log_field_normalization_test.dart` with an assertion that a row with only `sets_detail` array reads back at length N.

### Task #2a — Reader-side logging_type defensive correction

**File:** `train_screen.dart` + `workout_receipt_card.dart` (per-exercise rendering branches).
**Logic:** if `logging_type == 'timed'` AND no `duration_seconds` AND `reps > 0` → render as bodyweight_reps. Same logic for the inverse: if `logging_type == 'weight_reps'` AND `weight_kg == 0` AND `duration_seconds > 0` → render as timed.

**Acceptance:** founder's Push Up / Hanging Leg Raise existing rows render as "X reps" not "0s". Handstand Hold renders as "Ns" not "0kg × 3 reps".

### Task #2b — One-shot self-repair migration

**New file:** `lib/core/services/logging_type_repair_migrator.dart`. Runs on splash if `migrationBox['logging_type_repair_v1_done'] != true`. Walks `exlog_*` rows. For each:
1. Read sets[] data (or sets_detail).
2. Re-infer logging_type using same `_inferLoggingType` logic + library lookup by exercise_name.
3. If inferred ≠ stored, update the row's logging_type AND clear the offending field (e.g. `duration_sec` if it should have been `bodyweight_reps`).
4. Sync corrected rows to cloud via `SyncService.syncWorkoutData()`.

**Order in splash:** after `UserConfigMigrator` (which v2 ran in Test #11.1). Set flag once done.

**Acceptance:** after one launch on the new APK, founder's Push Up / Hanging Leg Raise / Chin Up rows have `logging_type=bodyweight_reps` in both local and cloud. Pinned by a new test `test/contracts/logging_type_repair_test.dart`.

### Task #7 — workout_log_sets 0-rows projection

**Investigation step first.** Read `sync_service.dart:1118-1140` (the per-set branch). ### Task #6 — Double-payment guards

**Client (primary):** `paywall_sheet.dart` (or wherever Upgrade button triggers checkout) — before invoking Razorpay, call `verify-subscription`. If `is_pro=true`, show "You're already PRO — expires DDD. Renew before then?" dialog; only proceed to Razorpay if user explicitly confirms (treats as renewal).

**Server (last resort):** `create-razorpay-order/index.ts` — query `subscriptions` for active row. If exists AND `end_date > now() + 7 days`, return 409 with `{error: 'already_pro', current_expires_at, renewal_eligible_at}`. Client surfaces this if the client-side check missed (race condition).

**Acceptance:** founder taps Upgrade as PRO user → sees "already PRO" instead of Razorpay checkout opening.

### Task #5 — PRO unlock root cause
