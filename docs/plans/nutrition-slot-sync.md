- S8 P and W edit the same meal offline → the later edit wins on both; one entry.

- S11 Account switch mid-pull, mid-push, mid-restore or mid-re-baseline → nothing written into the other account's box or rows.
- S12 An OLD client (AAB +50) writes a slot directly → new clients converge without a double count (§4.5 legacy rows).
- S13 A fresh install restores each meal as its own entry under its original key.

## 3. Server (one migration; number from `sh scripts/mint_migration.sh <slug>`, never `ls`)

1. `nutrition_logs`: `+ rev bigint not null default 1`, `+ updated_at timestamptz not null default clock_timestamp()`, `+ entries jsonb` (null = legacy row: no per-meal split), `+ legacy_rev bigint not null default 0` (the `rev` of the last write that did NOT go through the RPCs; 0 for every row that exists when the migration runs). Index `(user_id, updated_at, id)`. The tombstone table carries `legacy_rev` too (copied from the row on delete, copied back on the next insert), so a delete and re-create never forgets a legacy write.
2. `nutrition_log_items`: `+ entry_key text` (null on legacy rows).
3. `nutrition_slot_tombstones(user_id uuid not null references users(id) on delete cascade, date date not null, meal_type text not null, rev bigint not null, deleted_at timestamptz not null default clock_timestamp(), legacy_rev bigint not null default 0, primary key (user_id, date, meal_type))`, index `(user_id, deleted_at, date, meal_type)`. RLS select/insert/update/delete own (the INVOKER RPCs write through it). A client can forge its OWN tombstone through PostgREST: self-harm only, the accepted stance of `user_progress`. A hard delete plus this table (not a `deleted_at` column): every server reader keeps working with no filter.
4. **Revision rule (every writer):** a slot's `rev` only grows over its whole life, across delete and re-create: current = the row's `rev`, else the tombstone's `rev`, else 0; every successful write sets `current + 1`.
5. `nutrition_slot_put(p_date date, p_meal_type text, p_base_rev bigint, p_totals jsonb, p_entries jsonb, p_items jsonb) returns jsonb`, plpgsql, SECURITY INVOKER, `set search_path = public`:
   - `v_uid := auth.uid()`, raise if null; `p_base_rev` null or negative raises. Bounds: meal_type ∈ {breakfast, lunch, dinner, snacks}; every string field of an entry (`id`, `k`, `s`, `la`, `ca`, `src`) and every item `food_name` at most 200 characters; each entry's `n` <= 500; `entries[].id` unique within the call; `jsonb_array_length(p_entries) <= 100`; `p_items <= 500`; `sum(entries[].n) = jsonb_array_length(p_items)`; every item `entry_key` ∈ `entries[].id`; numerics within the FC6 ceilings (`nutrition_write_service.dart:190-194`) applied PER ENTRY (its totals) and PER ITEM, never to the slot sum `p_totals` (a full slot may legitimately exceed one meal's ceiling; `p_totals` must equal the sum of entry totals after both are rounded to 3 decimals: the client rounds the sum with the signature's text rule, the server compares `round(sum, 3)`; R16 P2-1: an exact double sum such as 0.1 + 0.2 would otherwise raise for ever); the client checks every bound before the call (counts, string lengths incl. `food_name`, ceilings) and treats a breach as `nslot_slot_too_large` (permanent, no RPC), so the server raise is a last line only; anything else raises.
   - `set_config('app.nutrition_rpc', 'on', true)`; `pg_advisory_xact_lock(hashtext(v_uid::text || '|' || p_date::text || '|' || p_meal_type))`; `select id, rev from nutrition_logs where (user_id, date, meal_type) = (v_uid, p_date, p_meal_type) FOR UPDATE` (the row lock also serializes an old client's direct UPDATE); else the tombstone `FOR UPDATE`.
   - `current <> p_base_rev` → `{status: 'conflict', rev, updated_at, row}`, `row` = the row's `id`, `rev`, `legacy_rev`, `created_at`, `updated_at` (timestamps as the server's text), totals, `entries` (null = a legacy row) and items with `entry_key`; or `{tombstone: true, rev, legacy_rev, deleted_at}`; or null. The same fields the pull reads, so a conflict reply is merged exactly like a pulled row.
   - else INSERT or UPDATE the parent (`rev = current + 1`, `created_at` = min(`entries[].ca`) on insert); an INSERT's `unique_violation` (an old client inserted after the lock) is caught and returned as a conflict with the fresh row. Replace ALL items (delete + insert, `item_index` by ordinality, `entry_key`). Delete the tombstone. Return `{status: 'ok', rev, updated_at}`.
6. `nutrition_slot_delete(p_date, p_meal_type, p_base_rev)`: same lock, CAS and conflict payload; ok → delete the parent (items cascade) and upsert the tombstone with `rev = current + 1`, `legacy_rev` = the deleted row's `legacy_rev`, AND `deleted_at = clock_timestamp()` on both the insert and the conflict branch (a stale `deleted_at` would hide it from the tombstone cursor); nothing there and `p_base_rev = current` → ok no-op.
7. `nutrition_server_now() returns timestamptz` (`clock_timestamp()`, INVOKER): the capability probe and the re-baseline's cursor start.
8. Triggers for writes without `app.nutrition_rpc = on` (old clients, manual SQL):
   - `trg_zz_nutrition_rev` BEFORE INSERT OR UPDATE on `nutrition_logs` (sorts after `trg_suppress_redundant_updates`, so a true no-op stays suppressed): always `updated_at := clock_timestamp()`; non-RPC: `entries := null`; non-RPC INSERT: `rev := coalesce(tombstone.rev, 0) + 1` and delete that tombstone; non-RPC UPDATE: `rev := OLD.rev + 1` only when `NEW.rev = OLD.rev`; non-RPC (INSERT or UPDATE, after `rev` is set): `legacy_rev := NEW.rev`. The RPCs never change `legacy_rev` (an RPC UPDATE keeps it; an RPC INSERT after a tombstone takes the tombstone's). So a legacy write stays visible to every device through every later new-format write.
   - `trg_zz_nutrition_items_rev` AFTER INSERT OR UPDATE OR DELETE on `nutrition_log_items`, non-RPC only: `update nutrition_logs set rev = rev + 1, entries = null where id = <log_id>` (the explicit `rev` change defeats suppression when `entries` is already null; the parent trigger then sees `NEW.rev <> OLD.rev` and does not bump again).

## 4. Client

### 4.1 Identity
- Every `nlog_` row written on this build carries `entry_id` (UUID v4). `logMeal` stamps it in the payload (`nutrition_write_service.dart:114-134`), so `relogSavedMeal`, the coach and every caller get one. `editLog`, `appendItemsToMeal` and `moveMealLog` copy the row and keep it; `editLog` strips `entry_id`, `id`, `log_key`, `date` and `meal_type` from `updates` (an `updates` map can never re-identify or re-slot a row; a move is `moveMealLog`); a test greps every `editLog(` caller in `lib/` for those keys. `restoreLastDeleted` / `restoreFoodLog` keep the saved copy's id.
- **Undo of a meal that is back** (R9 F5): `restoreLastDeleted` / `restoreFoodLog` refuse a stash whose `entry_id` is already held by a local row (a pull brought the meal back meanwhile); the user sees the existing meal, and no slot holds one id twice.
- A row with no `entry_id` is a **legacy row** (written before this build). Only the re-baseline (§4.11) consumes legacy rows (and, after a legacy-mode pass, every local meal row: §4.6, §4.11 "full"). After `rebaselined` is set: `restoreLastDeleted` / `restoreFoodLog` refuse an id-less payload (an undo of a pre-build row would re-add a meal the rebuild already restored), and so does any write while a re-baseline is in flight (§4.11 step 2 clears the undo stash in the same synchronous run as its writes). Any other id-less row found later (a dev seed, a migrator straggler) is stamped with a fresh UUID by `stampLocked` (§4.7) and is from then on an ordinary new entry: no content matching anywhere. **`stampLocked` runs only in new mode AND only when `nslot_meta.rebaselined` is true**: before that an id-less row is exactly what marks pre-build history, and stamping it would make the re-baseline keep it beside the cloud's copy (a double count).
- **Synthetic entry**: the one entry that stands for a LEGACY cloud row (`entries == null`). `entry_id` = UUID v5(fixed namespace, `"<cloud row id>|<row rev>"`): a uuid string and an integer, identical on every platform (no timestamp is parsed: Flutter web keeps milliseconds where the phone keeps microseconds, so a parsed `created_at` would give web and phone different ids for one row). Every device that reads the same version of the row builds the same id; a new version (an old client changed it, so `rev` grew) gives a new id (§4.5).
- Cloud: `entries[i].id` = `entry_id`; `nutrition_log_items.entry_key` = `entry_id`.

### 4.2 Projection and signature
- One function projects local rows, the RPC payload and rows read back: each item → `[lowercased trimmed name, quantity_g, calories, protein, carbs, fat, fiber]`, numbers rounded to 3 decimals (null → 0; a value equal to zero is written as `0.000`, never `-0.000`: web's `toFixed` drops the sign of zero, the VM keeps it); the entry's five totals the same. The name is lowercased for the signature by mapping ASCII `A`-`Z` only (platform `toLowerCase` differs for some non-ASCII letters). **Signature** = SHA-256 of a canonical TEXT built by hand: fields in a fixed order, separated by `|`, every number written with `toStringAsFixed(3)` (never `jsonEncode` of a double: web prints `100` where the phone prints `100.0`). So one content has one signature on every platform, and the tie-breaks that compare signatures (§4.5) decide the same on every device. The NAME is sent trimmed with its case kept (`food_name`); only the signature lowercases it (a case-only rename is invisible to sync, accepted). The NUMBERS sent are the projected numbers, so cloud and local hold the same numbers and a round trip cannot change a signature (S10). An edit below 0.0005 is invisible (accepted). The RPC stores the signature in `entries[i].s` for diagnostics only; every comparison recomputes it.
- Shared bounds (100 entries / 500 items) are one Dart const; a test greps the SQL for the same numbers.

### 4.3 Cloud slot content
`entries` = ordered `[{id, k: local key, s, la: logged_at, ca: created_at, src: source, t: totals, n: item count}]` `stampLocked` normalises and PERSISTS `created_at := created_at ?? logged_at ?? now` and `logged_at := logged_at ?? created_at` on every row it touches, and the push sends those (`ca`, `la`) (a legacy-restored row has `created_at` and no `logged_at`; a migrated row may have neither), so the RPC always receives two valid timestamps; the RPC still casts each with a fallback to `now()` instead of raising (R12 P2-1: a raise there would be a permanent per-slot failure); items ordered by entry, and inside an entry in the entry's own item order, with `entry_key = id` and `item_index` by ordinality. Every reader (pull, re-baseline, restore, a conflict reply) SORTS the embedded items by `item_index` before grouping them by `entry_key` (the embed `nutrition_log_items(*)` has no guaranteed order; today's restore sorts the same way, `sync_nutrition.dart:689-695`), and keeps the `entries` array order; parent totals = sum of entry totals.

### 4.4 Ledger, cursors, meta (all in `nutritionBox`, same lifetime as the entries)
- **Ledger** (the 3-way base), sharded per date: `nutritionBox['nslot_ledger_<date>']` = `{<meal>: {rev, ua, e: {entry_id: signature}}}` (a tombstoned slot: its `rev`, `e: {}`). A pass accumulates shard changes in memory and writes each touched shard once (every 25 slots during a re-baseline).
- **Cursors**: `nutritionBox['nslot_cursor']` = `{rows: {ts, row}, tombs: {ts, d, m}}` (keyset). Every server timestamp the client keeps (`ts`, the ledger's `ua`) is the server's TEXT, stored and compared as text (equality), never round-tripped through `DateTime` (web drops microseconds). Only the 5-minute overlap is computed from a parsed value (millisecond loss is irrelevant inside it).
- **Meta**: `nutritionBox['nslot_meta']` = `{rebaselined: bool, full?: 'legacy_pass' | 'legacy_seen', inflight_since?: ts, inflight_sigs?: {entry_id: signature}}`.
- All go through one helper `_nslotStore(userId, gen)` that no-ops when the owner OR the section generation changed (§4.7); the `nslot` `SyncSkipIndex` gets the same generation-inclusive predicate as its `ownerChangedNow` (`sync_skip_index.dart:234, 274`). `lib/features/dev/simulation_service.dart:178` (dev reset) also clears the `nslot_` prefix and its "(now 17)" comment at `:183` is updated; `user_repository.dart:1210` `.clear()` already covers them.
- Every whole-box `nutritionBox` reader is checked against these keys (§5).

### 4.5 Merge (Phase B: 3-way by `entry_id` over a known base)
`mergeSlot(base, local, cloud)`, pure, `lib/core/services/sync/nutrition_slot_merge.dart` (no Hive). Per `entry_id` in L ∪ C ∪ B (signatures; absent = null):
1. L == C → keep.
2. L == B → take C (C null → remove locally).
3. C == B → keep L (L null → stays removed).
4. both changed, both present → the newer `logged_at` wins, compared as TEXT normalised to `YYYY-MM-DDTHH:MM:SS.mmm` (the first 19 characters, then the fractional digits cut or zero-padded to 3; every meal writer emits UTC, `nutrition_write_service.dart:132, 300, 363, 443`, and a synthetic entry's server `created_at` is UTC; an absent or shorter-than-19 value sorts as the empty string, oldest); the phone writes microseconds, web keeps milliseconds; tie → the larger signature (platform-neutral, §4.2). Same order on every device. The day pass uses the same comparison.
5. both changed, one null → keep the present (edited) one (S9).
- A slot with NO ledger entry (first seen, after the re-baseline) has base `{}`: every id is new on one side, so the result is the union by `entry_id` (S6, S7). No content matching anywhere.
- **Placement**: a kept entry keeps its key; an incoming entry goes to its own `k` when free, else `firstFreeLogKey(baseLogKey(k))`; an entry whose `entry_id` already exists locally IN THE SAME SLOT is written at THAT key; one that exists only in ANOTHER slot of the date is placed at its own key and the day pass then keeps the newer copy (R11 P2-1: a same-key overwrite across slots would make the result depend on which slot is applied first). Apply rewrites the row's `id` and `log_key` to the placed key.
- **Day pass** (after every slot of one date is merged; S4, S4b): an `entry_id` present in two slots of the date → keep the copy with the newer `logged_at` (tie: larger signature, then larger key), remove the other. Applied as a local change.
- **Duplicate id inside a move** (`moveMealLog` puts the new key, then awaits the delete of the old one): the push's GROUPING applies the same day-pass rule read-only — an `entry_id` held by two local rows of one date counts only in the copy with the newer `logged_at` (`:443` makes that the destination). The push writes nothing locally; `moveMealLog`'s own delete finishes the move. The pull's day pass (a local write) re-checks the value before deleting (§4.10).
- **Legacy write seen in steady state** — an ADMITTED (§4.11 slot admission) ROW winner (pull winner, conflict reply, steady-restore row; never a tombstone, which rules 1-5 merge safely) with `rev` greater than this device's ledger `rev` for that slot (the stale-skip gate runs FIRST, so an untouched legacy row re-read in the overlap never re-triggers; R15 P2-2) AND (`entries == null` OR `legacy_rev` greater than that ledger `rev`) (0 when the ledger has no entry: a slot absent from the ledger was created after this device's last re-baseline, so any legacy write in it is one this device never merged). Only an old client or a device in legacy mode makes either. The rule is deliberately conservative (R16 P3-2): a slot an RPC re-created after a legacy delete inherits that `legacy_rev`, so a device that missed the delete runs a FULL re-baseline even where a 3-way merge would have been safe; §9 (d) states the cost. R14 P1: a device that missed the legacy row itself and pulls only the new-format row a re-baselined device wrote over it still sees `legacy_rev`. The pass that sees it (a pull winner, a conflict reply, a steady restore row) merges NOTHING for it: it sets `nslot_meta.full := 'legacy_seen'` and `rebaselined := false` (same ticket, synchronously), stops the pass, logs LOW `nslot_legacy_seen_rebaseline`, and after release schedules ONE pull (`unawaited(pullNutritionSlots(userId))`, owner and generation re-checked; R14 P2-1: without it the gate would wait for the next launch or a throttled resume), whose pass runs the FULL re-baseline (§4.11), which turns the legacy row into its synthetic entry with every other device's view of the cloud. So no device ever holds a synthetic entry next to per-meal entries of the same slot that it merged itself, and every synthetic id comes from the same cloud row version on every device. Cost: this device's unsynced meal changes at that moment (§9 d). A synthetic entry made by a re-baseline is afterwards an ordinary entry (edit, move, delete by rules 1-5); when another device replaces its slot, rules 1-5 decide by `entry_id` like any entry (no special rule).

### 4.6 Modes, capability, kill switch, gate
- Per pass, a capability probe: `nutrition_server_now()` (memoized only on success). `PGRST202` / 404 / `42883` / a network failure → NO nutrition sync this pass (no push, no pull, no restore write, no flag changed) + LOW `nslot_rpc_missing` once per launch for the first three; probed again next pass. A missing function NEVER selects legacy mode: PostgREST also answers `PGRST202` while it reloads its schema cache, and a legacy push from a device that has not pulled would overwrite another device's newer meals (R10 P1). The rollout (§7) applies the migration before any build ships, so a lasting "missing" means the migration was rolled back: the kill switch is then the lever.
- `configBox['disable_nutrition_slot_sync'] == true` → **legacy mode**. This is the ONLY way into legacy mode.
- **Legacy mode** = today's code verbatim: legacy push body (its `nlog` skip index, `disable_nutrition_slot_merge`, `nlogHashSkipDisabledFor`), legacy restore, no pull, no re-baseline, NO gate. Precedence: legacy mode wins over everything below.
- **Every legacy-mode pass** (the switch; re-baselined or not): the legacy push and the legacy restore may move this device's meals into a legacy cloud row (push) or rewrite them as id-less rows (restore, `sync_nutrition.dart:767, 773`), so after one the device's entries no longer match its ledger. A wrapper AROUND the verbatim legacy body (the body itself is unchanged) takes the nutrition ticket like a body (the push wrapper finding it busy sets owed and returns; the restore wrapper waits, bounded, abandon-on-turn, §4.12), so no legacy pass ever runs beside a new-mode body (R11 P2-3). Holding it, synchronously before the body starts, it sets `nslot_meta.rebaselined := false` and `nslot_meta.full := 'legacy_pass'` (a kill-switch FULL outranks a pending legacy-seen one). So the next new-mode pass runs a FULL re-baseline (§4.11): the cloud's content replaces EVERY local meal row (not only id-less ones), the whole ledger and both cursors are rebuilt, and nothing is written to the cloud. No per-row bookkeeping: whatever the legacy body sent or rewrote, the device ends exactly on the cloud's content (R11 P1: the per-id list of v10 could block the commit for ever). The cost is §9 (c2).
- **New mode**: the new push / pull / restore. **Gate**: until `nslot_meta.rebaselined` is true the push sends nothing (returns `true`, no failure) and logs LOW `nslot_push_gated_not_rebaselined` once per launch (a stuck gate is visible); the pull body runs the re-baseline.
- In new mode the launch pull's old nutrition leg never runs, whatever `restore_nutrition_launch_pull` says (1a-i's switch acts in legacy mode only), so no copier writes id-less rows beside a re-baselined box.
- A legacy row written by ANOTHER device (an old client, or a device in legacy mode) and seen by a re-baselined device in new mode → a FULL re-baseline on the seeing device (§4.5).

### 4.7 The nutrition section (one ticket) and the call graph
- One `SerialSlot` for the nutrition domain, replaced in `_onUserChanged` (with the coalescers). `SerialSlot` gains `bool get isBusy`. A **section generation** `_nslotGen` (an int) is bumped in `_onUserChanged`; each body captures it with its user id, and every owner check in a body and its locked helpers is `ownerChangedSince(userId) || _nslotGen != captured` (R10 P2-1: an A → B → A switch makes the uid check pass again while a fresh slot lets a second body for A run; the generation stops the old one).
- **Exactly three bodies take the ticket**, each released in `finally`: `pushBody(userId)` (new-mode `_syncNutritionLogs`), `pullBody(userId)` (`pullNutritionSlots`), `restoreBody(userId, preFetched?)` (new-mode `_restoreNutritionLogs`, all callers). **Locked helpers assume the ticket and never take it:** `rebaselineLocked`, `applyLocked`, `stampLocked`. No body calls another body or `syncNutritionData()` while holding the ticket; a body that wants another schedules it with `unawaited(...)` after release.
- `pushBody` finding the section busy → sets `_nslotPushOwed[userId]` and returns `true` at once (never waits; no failure, so neither the 45 s ceiling nor the retry sweep is hit by queueing). `pullBody` finding it busy → sets `_nslotPullOwed[userId]` and returns (R11 P2-2: a launch pull that met a push in flight is not lost). `restoreBody` waits for the ticket (bounded, §4.12).
- The holder's `finally`: release, read and clear `_nslotPushOwed[its userId]` and `_nslotPullOwed[its userId]`, and fire `unawaited(syncNutritionData())` / `unawaited(pullNutritionSlots(userId))` for each one owed, only when that user is still the live owner and the generation is unchanged — one synchronous run (a test pins the order). A pull fired this way that finds the section busy again sets owed again; it never waits, so no loop forms without a holder's progress.
- **Owed is set only** when the section was busy, or a push stopped on its budget after confirming at least one RPC. A pass that only failed sets nothing (failures wait for the existing retry sweep and the next launch/resume; test: 20 failing passes → one body run each, no re-trigger). Permanent failures (`nslot_slot_too_large`, a validation raise) never set it.
- `ownerChangedSince(userId)` after every `await` and before every ledger or Hive write.

### 4.8 Push (new mode; replaces the `_syncNutritionLogs` body behind §4.6)
- Order: the §4.6 gate first (not re-baselined → return, nothing stamped, nothing sent); then `stampLocked` (also called at the start of the pull's and the steady restore's merge, under the same ticket, so no body merges an id-less row) (id-less rows only, §4.1; one synchronous read, one `putAll` of the stamped copies, a key whose value changed before the write is skipped). `stampLocked` also removes the OLDER of two same-date rows holding one `entry_id` (the day-pass order, value re-checked before the delete): a kill between `moveMealLog`'s put and delete (`nutrition_write_service.dart:472-473`) leaves both, and the screens would count the meal twice until a pull.
- A legacy-seen stop (§4.5) inside a push closure returns `false` (so `pushIfChanged` records no fingerprint) WITHOUT `_reportSyncFailure`; the push body then ends normally with no failure recorded (nothing was sent; the scheduled pull re-baselines), and a steady restore with failure `restore_nutrition_slots`, reason `legacy_seen_rebaseline` (R14 P2-2: no caller may treat nutrition as restored).
- `PGRST202` / 404 / `42883` on a put or delete after a successful probe (a schema reload mid-pass): the closure returns `false` with no `_reportSyncFailure`, the memoized probe is dropped, and the next trigger probes again.
- A failed capability probe (§4.6): `PGRST202` / 404 / `42883` → push and pull return normally with nothing sent and nothing recorded as a failure (a schema reload is transient, and a re-arm would loop); a NETWORK or timeout failure of the probe in the push → recorded as an outage-shaped `sync_nslot_put` failure through `_reportSyncFailure`, so `SyncRetryController` re-arms exactly as today's offline push does (`sync_retry_controller.dart:226-234`) and a meal logged on a bad connection is pushed when the network returns (R13 P2-1); a restore records failure `restore_nutrition_slots` with reason `capability_unavailable`, so no caller treats nutrition as restored.
- Group local rows per slot (with §4.5's duplicate-id rule). Slots = local slots ∪ ledger slots, ordered every put before any delete (a move adds the destination before the source goes). Each through `nslotIndex.pushIfChanged(slot, fp, push)` on a NEW `SyncSkipDomain.nslot` with its own index key (the legacy `nlog` index is never written by the new path); `fp` = `"<ledger rev>|<ledger ua>|" + sorted id:signature pairs`. `liveKeys` = every slot visited.
- Closure: local signatures == ledger `e` → `return true`. Local empty, ledger `e` non-empty → `nutrition_slot_delete(base_rev)`. Else `nutrition_slot_put(base_rev, ...)`. Over the bounds → no RPC, `return false`, LOW `nslot_slot_too_large` once per launch per slot. `ownerChangedSince(userId)` immediately before every RPC. A test pins both RPC calls inside the closure (`.rpc(` is a terminal read to Gate G1, `sync_hash_skip_atomicity_lib.dart:106`, so G1 does not enforce it), and that every catch inside a closure ends in `rethrow;` or `return false;`.
- `ok` → ledger slot := `{rev, ua, e: the signatures that were SENT}` (never a re-read: a user edit made during the RPC stays dirty). `conflict` → `mergeSlot(ledger, local, returned)` + day pass → `applyLocked` → ledger := returned → retry with the new base, max 3 rounds; then `return false` + LOW `nslot_conflict_rounds_exhausted`.
- Budget: stop issuing RPCs after 15 s or 50 slots; RPC timeout 10 s; so a body ends by ~25 s.
- Cost: each pass groups every local row and every ledger slot, as today's legacy push already groups every local row each pass (`mergeNutritionLogsBySlot`); the `nslot` skip index keeps unchanged slots RPC-free. No new per-pass cost class.
- Failures go through `_reportSyncFailure` (it redacts row values). Op types: `sync_nslot_put`, `sync_nslot_delete` (the `sync_` prefix re-arms the sweep via `isPushFailureOpType`, `sync_retry_controller.dart:117-123`); `pull_nutrition_slots`, `rebaseline_nutrition`, `restore_nutrition_slots` are reads: `isPushFailureOpType` is already false for them (no `sync_` / `upsert_` / `restore_sync_` prefix); they are listed in `kNotSweptOpTypes` only so the forcing-function test enumerates every op name. A failed read is retried by the next trigger (launch, resume, restore), never by the sweep. None in `highPriorityOpTypes`.

### 4.9 Pull (new mode)
- `pullBody`: if not `rebaselined` → `rebaselineLocked` and nothing else this pass. Else `stampLocked`, then rows keyset-paged until a short page: the first page `updated_at >= cursor.rows − 5 min`, each next page `(updated_at, id) > (last row's updated_at, last row's id)` (no empty-string uuid is ever sent) (`*, nutrition_log_items(*)`), and tombstones keyset-paged on `(deleted_at, date, meal_type)` from `cursor.tombs − 5 min`. The overlap absorbs commit-order skew; applying is idempotent.
- **One winner per slot**: everything read this pass for a slot (row versions from several pages, its tombstone) → the item with the largest `rev` wins. A winner whose `rev` <= the ledger's is skipped (stale or already applied).
- Per slot: `mergeSlot(ledger, local, winner)` + day pass → `applyLocked` → ledger := winner. A result that differs from the winner is dirty; after release the pull schedules `unawaited(syncNutritionData())` when it wrote anything.
- Page size: every read here uses the page size of today's `_fetchAllRows` (1000, equal to the project's `db-max-rows`, `sync_service.dart` doc comment above `_fetchAllRows`), one shared constant, so a capped page is never mistaken for a short one; the same hazard note applies if the cap is ever lowered.
- Budget 25 s per pass, page timeout 20 s; the budget is checked only after the first page that reaches past the overlap, so a busy 5-minute window cannot stop the cursor advancing. Order: read pages (rows, then tombstones) until a short page or the budget; pick one winner per slot over EVERYTHING read this pass; apply; then advance each cursor ONCE, to the last fully read position. A slot whose newer version lies beyond that position is applied in a later pass: safe, because `rev` only grows, a stale winner is never applied, and any push from the intermediate state is a CAS that conflicts and merges. Any failure leaves both cursors.
- Runs: in `checkAndSync` (where the old nutrition leg ran) and on `AppLifecycleState.resumed` (registered by SyncService itself, at most once per 2 minutes, never signed out).

### 4.10 Apply (`applyLocked`, the ONE local writer for pulled, conflicted, restored and re-baselined content)
- Re-read the slot's rows, compute, then start `box.putAll(changed)` and `box.deleteAll(removed)` in one synchronous run with no `await` between the read and both calls, then await both. **`removed` never contains a key that is also in `changed`** (a put overwrites it). A key is deleted only if its value still has the identity and signature that was read (a user write landing first is never removed).
- `ownerChangedSince(userId)` before the read and before the writes; every written entry clamped (`clampRestoredNutritionRow`); incoming entries keep their own `source`, `created_at`, `logged_at`. A clamp that changes a value leaves that entry dirty, so the next push sends the clamped values (one put, intended).
- After a pass that wrote anything: `NutritionWriteService.invalidateAfterSync()` (shipped in 1a-i).

### 4.11 Re-baseline (`rebaselineLocked`; once per device and user; never writes to the cloud)
Why: pre-build rows have no per-meal identity, and rounds 2-6 showed every content-matching migration of them can double count or lose data. Pre-launch every account is a testing account and every post-launch install starts on this build, so pre-build history is replaced by the cloud's copy, once, with no cloud write.
**Replaceable rows** `R` (one definition, used by steps 1, 3 and 4):
- NORMAL re-baseline (`full` absent): every `nlog_` row with no `entry_id`, plus every UUID-keyed meal-shaped row that is not a saved meal (has `date` and `meal_type`, `is_saved_meal != true`, no `is_template`: the pre-Test-12.8 restore shape with `source: 'cloud_restore'`, which 1a-i's cleanup keeps on purpose and every whole-box reader counts). Recomputed at step 3 (a new id-less row appearing stops the run).
- FULL re-baseline, kill-switch kind (`nslot_meta.full == 'legacy_pass'`, set by the legacy wrapper, §4.6): every `nlog_` row and every such UUID row PRESENT AT STEP 1.
- FULL re-baseline, legacy-seen kind (`nslot_meta.full == 'legacy_seen'`, §4.5): the same, EXCEPT an id-bearing row whose `entry_id` is in neither the ledger nor the cloud read (a meal this device logged and never pushed: it cannot be inside any cloud row, legacy or not, so keeping it cannot double count; R15 P2-5). It is a build row, pushed after the commit. A meal whose put reached the server but whose reply was lost IS in the cloud read, so it is replaced (by the cloud's copy of itself), never duplicated (R16 P3-3). A row created after step 1 (a meal logged during the read) is a build row: never in `R`, kept, pushed later (R12 P2-4: a log during a long read no longer restarts the run).
- In both: PLUS a row holding an `entry_id` that `inflight_sigs` lists with an EQUAL signature (an interrupted run wrote it and nobody touched it: rewritten from the cloud version read now, so a newer cloud edit is not lost); EXCEPT a row whose `entry_id` `inflight_sigs` lists with a DIFFERENT signature (the user edited an interrupted run's output: kept, see placement).
1. **Snapshot** (synchronous, before any await): `S0` = `R` as `{key: value}`. Set `nslot_meta.inflight_since` (a re-run of an interrupted re-baseline logs LOW `nslot_rebaseline_resumed`).
2. **Read**: `t0 = nutrition_server_now()`, then the full cloud history (`*, nutrition_log_items(*)`, keyset-paged on `(updated_at, id)`, page timeout 20 s, no whole-body deadline), then all tombstones. Pages already read are KEPT in memory per user (with `t0`) across a failed attempt, so a retry continues from the last page; tombstones are always read in the attempt that finishes. Per slot, one winner by largest `rev` (§4.9). Any failure or owner change → stop, nothing local changed, retried at the next pass (launch, resume, restore).
3. **Rebuild**, in ONE synchronous run from the read of the box to the start of both writes:
   - Stop (nothing written; retried next pass) when any `S0` key now holds a different value or is gone, or (NORMAL only) an id-less `nlog_` row exists that is not in `S0`. So nothing is removed that the decision did not consider.
   - **Slot admission** (one shared predicate, applied BEFORE anything else to every cloud row the client reads: re-baseline, pull winner, conflict reply, steady restore): a row whose `meal_type` is not one of the four (or null) is skipped with LOW `nslot_bad_meal_type` (no slot, no ledger shard, never the legacy-seen test): the RPC would refuse every later write of it, and testing it for legacy-seen would loop FULL re-baselines while it sits in the cursor overlap (R16 P2-2). Live 2026-11-23: 92 rows, all four values, no null (R15 P2-4).
   - Per slot (a UUID row counts in the slot of its `date` and `meal_type`):
     - cloud winner is a ROW → its entries (a new-format row → its entries by `entry_id`; a legacy row → one synthetic entry, `logged_at` = the row's `created_at`, `source: 'cloud_restore'`); the slot's `R` rows are removed.
     - cloud winner is a TOMBSTONE → the slot's `R` rows are removed.
     - NO cloud row and NO tombstone → the slot's `R` rows are KEPT (a meal whose push never reached the cloud is not lost and nothing in the cloud can double it; the push sends them). The **kept set** `K` = their final keys: an id-less `nlog_` row is stamped with a fresh `entry_id` in place (same key, in `K`); an id-bearing row (FULL mode) stays as it is (same key, in `K`); a UUID-keyed row is rewritten under `firstFreeLogKey(computeLogKey(...))` with a fresh id (the new key in `K`, the old UUID key in `deleteKeys`).
   - **Day pass over the result** (R12 P2-3; R13 P3-1 adds the kept rows): an `entry_id` held in two slots of one date by the cloud entries and the kept rows `K` together is written (or kept) once, in the slot of the copy with the newer `logged_at` (§4.5 order); the other copy is not written (its slot's ledger still lists it, so the next pull or push settles the cloud).
   - Placement (§4.5) of each cloud entry, by where its `entry_id` is held among the rows that are NOT in `R`:
     - nowhere → a synthetic entry (no `k`) at `firstFreeLogKey(computeLogKey(date, meal, items))`, a new-format entry at `k` when free, else `firstFreeLogKey(baseLogKey(k))`, computed against (current keys − `R` keys being removed + keys placed or kept so far);
     - in the SAME slot (only a user edit of an interrupted run's output can be held there: an untouched one is in `R`) → LEFT AS IT IS (its ledger base is the cloud signature, so the edit is dirty and pushed; a concurrent cloud edit resolves by §4.5 rule 4 at the push's conflict);
     - in ANOTHER slot (the user moved it after an interrupted run) → not placed; the push then sends the move (the ledger holds it in the cloud slot, local holds it in the other).
     - Build rows hold fresh ids no cloud row holds, so they never meet a placement.
   - `deleteKeys` = `R` keys being removed − keys placed in this run (a placed key that was in `R` is overwritten by the put, never deleted after it) + the old keys of re-keyed UUID rows.
   - Clear the undo stash; start `putAll(entries + stamped and re-keyed rows + nslot_meta with inflight_sigs = {entry_id: signature} of every entry this run writes)` and `deleteAll(deleteKeys)`; await both.
4. **Commit** — first re-scan the box: (a) no `S0` key is still present unless it is a placed key or in `K`, and (b) no `nlog_` row lacks an `entry_id`. Every row this run wrote or kept is a placed key or in `K` and carries an id, so none blocks the commit (R11 P1, R12 P1-1); only a user write that re-created a removed row while the step-3 writes were in flight does → do NOT commit; the next pass re-runs (idempotent). Else, in this ORDER (R13 P2-2: a kill between writes must never leave `rebaselined: true` over a partial ledger): (i) the WHOLE ledger is replaced (every existing `nslot_ledger_` shard deleted, the new shards written; the 25-slot flush of §4.4 is for push and pull passes only) := every cloud winner (rows and tombstones), and the cursors := `t0` − 5 min, awaited; (ii) THEN `nslot_meta` alone, in its own awaited `put`: `rebaselined := true`, `full`, `inflight_since` and `inflight_sigs` removed. A kill before (ii) leaves `rebaselined` false, so the next pass re-runs (idempotent); `invalidateAfterSync()`. Release; schedule the push (`unawaited`).
- **Build rows** (with `entry_id`, logged while the gate held) are never removed or sent by a NORMAL re-baseline; no cloud row holds them, so the first push sends them as additions (no double count). A FULL re-baseline replaces those present at its step 1 like every other local row (§9 c2); one logged after step 1 is kept.
- **Crash safety**: every write is idempotent by `entry_id`, `R` is recomputed each run, and `inflight_sigs` tells an untouched written row (replaceable, rewritten from the cloud) from a user edit (kept). Kill after `putAll` → the re-run removes the still-present replaceable rows and rewrites the untouched written entries in place. Kill after `deleteAll`, before step 4 → the same, then commits. Nothing reaches the cloud before `rebaselined`, so no partial state can reach another device.
- **Not under the 45 s ceiling**: restore entry points that run the re-baseline call it with the ceiling off (`applyRestoreCeiling(..., enabled: false)`); every await inside is bounded by its own timeout, and pages survive a retry.
- **Fresh device** (no `nlog_` rows) runs the same steps: its re-baseline IS its restore (S13).

### 4.12 Restore (new mode)
- Not re-baselined → `restoreBody` runs `rebaselineLocked` (ignoring any `preFetched` rows: they carry no tombstones and no server time). If a re-baseline is ALREADY running (the launch pull started it), the restore does not queue behind it with a 15 s limit: it awaits that run's shared result future and reports success or failure from it (R12 P2-2: on a fresh install the restore and the launch pull start together, and the multi-page read has no whole-body deadline).
- Re-baselined (steady) → `stampLocked`, then apply the rows read with the ledger as base (§4.5 per slot, `applyLocked`), skipping every slot whose row `rev` <= the ledger's (a snapshot older than the last pull never regresses a slot or its ledger); a slot ABSENT from the snapshot is never treated as deleted (only tombstones delete, through the pull); a steady restore NEVER moves a cursor (S14). It waits for the ticket for at most 15 s (then a failure `restore_nutrition_slots`, retried like today; the abandoned ticket, when its turn comes, is released at once without running the body: abandon-on-turn, tested); its own reads keep today's paging under the 45 s ceiling and EACH page read gets the pull's 20 s timeout (R15 P2-3: `applyRestoreCeiling` abandons a caller but does not cancel its task, so an unbounded page would hold the one ticket for ever and silently stop nutrition sync).

### 4.13 Kill switches (§4.6; default = new mode)
- `configBox['disable_nutrition_slot_sync']` → legacy mode (§4.6): old push, old restore, no pull, no re-baseline, old paths verbatim.
- 1a-i's `restore_nutrition_launch_pull` and `disable_nutrition_phantom_clean` are unchanged.

## 9. Results and residuals, stated (testing accounts only, CLAUDE.md §1; never offered as a founder choice)
- (a) Pre-build history becomes one card per meal slot on every device (the owner's per-meal split of OLD days is not kept; days logged on this build keep it).
- (b) A meal deleted or moved before this build whose cloud row OI-281 kept comes back once (in its old slot); deleting it now reaches the cloud.
- (c) A change to a pre-build row that never reached the cloud is lost at the re-baseline when the slot has a cloud row (before this build every meal write pushed at once, `nutrition_write_service.dart:175, 315, 378, 483, 582`; only an offline-failed, never-retried push is affected). A slot with no cloud row keeps its rows (§4.11).
- (d) When an old client or a device in legacy mode writes a slot after this build ships, every new-mode device that sees that row runs a FULL re-baseline and loses its own unsynced meal changes of that moment (§4.5). Old clients are unsupported and legacy mode is the emergency lever.
- (e) The Dart fake mirrors the SQL contract by hand; the live-verify SQL runs once at apply (CI cannot run live SQL).
- (c3) A change made to a PRE-BUILD row while the gate holds (an offline first launch: `editLog`, `appendItemsToMeal`, `moveMealLog` keep the row id-less) is replaced by the cloud copy at the re-baseline when its slot has a cloud row (after a legacy pass, (c2) covers every local row).
- (c4) The kill switch's legacy push is today's last-writer push: it overwrites the cloud slot with this device's view, so another device's newer meal in that slot can be lost while the switch is on. The switch is the emergency lever only.
- (c2) After any legacy pass the next re-baseline is FULL: every local meal row is replaced by the cloud's content, so any local change the cloud does not hold at that moment is lost when its slot has a cloud row (a failed legacy push, an unsynced edit made around the switch, a meal logged after the switch went off and before the re-baseline's step 1; one logged after step 1 is kept). Legacy mode is the emergency lever (the switch only, §4.6); after it the device is exactly the cloud.
- (j) An interrupted re-baseline re-run leaves an untouched entry that another device deleted meanwhile; its ledger base is the tombstone, so it is pushed back as new (the same class as (g)).
- (g) Deleting a pre-build row before the re-baseline completes (or while it keeps failing) brings the meal back from the cloud copy (same class as (b)). A re-baseline that keeps failing also holds every new meal locally (the gate); the signal is LOW `nslot_push_gated_not_rebaselined` once per launch, plus the step's own failure op.
- (h) A move that races another device's edit can leave the meal in two cloud slots of one date until the next pull's day pass removes one copy; server readers (weekly report, protein alert) may count it twice in that window.
- (i) A synthetic entry holds a whole legacy slot, so it is clamped by `clampRestoredNutritionRow` exactly as today's restore clamps a restored slot row (per meal 15,000 kcal, `nutrition_write_service.dart:190`): no new loss against today; the RPC bounds equal the clamp ceilings, so a clamped entry always fits.
- (c5) A re-run of an interrupted re-baseline uses the stamps of the earlier run; if another device created a slot in between, a meal the earlier run kept in that slot (no cloud row then) is replaced by the new cloud content (the (c) class).
- (k) A cloud edit that replaces a local row carries only the 9 item keys (§1), so item fields kept only locally (e.g. `food_id`) are dropped from that row, as today's restore does.
- (l) A legacy-seen FULL re-baseline replaces this device's unsynced EDITS of meals the cloud already holds for as long as its gate is closed (the stop until the commit; days on a device whose reads keep failing); never-pushed new meals are kept (§4.11 legacy-seen kind).
- (m) The legacy wrapper holds the ticket around the verbatim legacy body, which has no timeouts of its own (as today); a hung legacy request holds nutrition sync in legacy mode until the process ends (emergency mode only).
- (n) An old client's per-item upserts interleaved with an RPC put can leave the slot's items mixed until the next write, and its item write can deadlock with the RPC's row lock (40P01, retried); old clients are unsupported (decision 5, no double count: the next legacy-seen FULL re-baseline takes the cloud's content).
- (o) If the server's revs ever regress (a backup restore, tombstones removed by hand), the pull's stale-skip hides rows until the revs catch up; a push's conflict path still recovers. A pruning or restore job must force a FULL re-baseline (note on OI-280, with (f)).
- (f) Tombstones are never pruned by this batch (one row per deleted slot); a future pruning job must force a full reconcile on any device whose cursor predates it (note on OI-280). The ledger holds one small entry per slot ever synced (about 150-400 KB per year, written per touched date).
