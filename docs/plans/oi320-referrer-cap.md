It covers the NUMBER and the window. It does NOT cover the live apply (own go, CLAUDE.md section 4.3). ## 2. Design

`supabase/migrations/158_referral_referrer_cap.sql`:

1. **Schema (rounds 1 and 2).** Inside `SET lock_timeout = '3s'` ... `RESET lock_timeout`: `ALTER COLUMN referrer_id DROP NOT NULL`, `ALTER COLUMN referee_id DROP NOT NULL`, then ONE `ALTER TABLE` that drops and re-adds both foreign keys as `ON DELETE SET NULL` (the migration 049 pseudonymisation pattern; one statement, so there is no moment without a key even if `apply_migration` does not wrap the file in a transaction). A post-condition `DO` block raises if any foreign key over either column is not `ON DELETE SET NULL` (a second, differently named FK would otherwise survive the DROP and keep a cascade alive; MEASURED: with a planted `..._fkey1` CASCADE key the migration aborts with the key named) or either column is still NOT NULL. The rows survive an account deletion with that party's id NULL and still count; `UNIQUE(referee_id)` tolerates many NULLs, so a referee whose referrer was deleted still cannot redeem a second code; `no_self_referral` passes when either side is NULL. **`referrer_id` is my addition beyond the round-1 P1**: the founder decided the cap, and the cap only holds if the referee side is not the cheaper farm. It is reversible before the apply.
   The whole file is idempotent (MEASURED: applied twice with no error), so a failed apply converges on a re-run. The locks are taken for as long as the statement needs (3 rows) and bounded by the timeout; if the timeout fires, nothing is half-done that a re-run does not finish.
2. **Function.** `CREATE OR REPLACE FUNCTION public.redeem_referral_atomic` with the same signature, return type, security mode and `search_path` (restated, or the replace silently undoes 053), then an idempotent re-assertion of the ACL (exactly one GRANT).
   - An explicit guard first: a NULL referrer or referee raises 23502 with the function's own message (both columns are nullable now, so the refusal must not depend on a later statement failing).
   - `pg_advisory_xact_lock(least(k_referrer, k_referee))` then `pg_advisory_xact_lock(greatest(...))`, with `k_x = hashtextextended('redeem_referral_atomic:' || x::text, 0)`. Both users' keys, lowest first, held to commit. (a) Two concurrent redemptions for one referrer queue (the second's count then sees the first's row). (b) Any two redemptions touching a common user share a key and serialise BEFORE touching a subscription row, and with a fixed order and ONE redemption per transaction no cycle of advisory locks can form: this removes the old body's cross-order deadlock and the lost-update on a subscription row shared between a referrer role and a referee role. (c) A write outside this function (a webhook, a payment verification) takes no advisory lock; its interleaving is unchanged. (d) A caller queued behind a stalled holder waits until the holder ends or a statement/lock timeout (if one is configured) fires; the Edge Function returns any non-23505 error as a 500 "Internal server error" and nothing is half-written. (e) The locks are transaction-level: a session-level lock would leak past the statement and block every later redemption for that user (test PART 1b).
   - `v_credited_in_window = count(*)` of this referrer's rows with `referrer_rewarded` and `created_at > now() - interval '90 days'` (strict `>`: a row exactly 90 days old is out). The count does NOT filter on `referee_id`: rows of deleted referees must keep counting. `v_credit_referrer = v_credited_in_window < 7`.
   - Insert the audit row with `referrer_rewarded = v_credit_referrer`, `referee_rewarded = true`. The flag is written BEFORE the credit, so it records the decision, not the effect: the existing `UPDATE ... WHERE end_date = v_referrer_expires` can still match zero rows if another writer of the referrer's subscription moved `end_date` first (a window the old body also had; not widened).
   - Credit the referrer only `IF v_credit_referrer`, in BOTH branches (a capped referrer whose own subscription has expired is not re-trialled: case J). The referee block is untouched and never gated, in BOTH branches (case R: a referee who already holds PRO is still extended).

Why CREDITED rows only: counting attempts too would make a capped referrer's lock-out grow with every further attempt instead of expiring 90 days after the 7th credit (case F2 of the verify file, with seven uncredited rows in the window). Why the existing flags: they are free, they were never used, and they record exactly "was this side credited"; no new column. The 3 legacy rows keep false on purpose (older than any window). Return type stays `void`: changing it needs DROP + CREATE, which resets the ACL (bug class 2.36), and the Edge Function does not need the answer. The Edge Function is NOT changed or redeployed.

Residuals, stated so nobody reads the cap as stronger than it is: (i) the cap is per ACCOUNT - a referrer who deletes their account and signs up again, or who holds a second account, starts with a fresh count; nothing in the schema ties accounts together. (ii) The referee side is bounded by `UNIQUE(referee_id)` (one code per receiver, ever) and the 7-day signup window, not by the cap. (iii) Rows written by the OLD body carry `referrer_rewarded = false`, so a referrer with redemptions in the 90 days before the apply is not capped on those (section 4 step 2 reads that and stops if non-zero).

**Kill switch (the registry's catastrophic `requires: feature_flag`; CLAUDE.md section 4.6) - position, B-pass finding 5.** None, on purpose. A runtime switch would have to live inside the SECURITY DEFINER function (a config table or a GUC read on every redemption): a second code path in a function whose only caller already serialises on two advisory locks, and its 'off' state IS the abuse this batch closes. The old path is preserved VERBATIM as the inline rollback block, measured byte-exact (`md5` 1066f4cb5b1c36058fd5c0b635e3209d, length 1825), and that block is the revert: one function replacement plus restoring the two CASCADE keys (rows written under the cap keep their flags and nothing reads them after a rollback). Nothing enforces the registry's `feature_flag` entry mechanically (`scripts/safe_push.sh:132-135` records that `check_blast_radius_coverage.dart` never reads the `requires:` list; `scripts/reconcile_ci.dart:41` is the earlier batch whose B-pass raised the same point), so the position is stated here and repeated in the plan-review record rather than satisfied by a flag.

Arithmetic: 7 x 7 = 49 PRO days per 90 days at most, about 54%, roughly Rs 570 per 90 days at Rs 349 a month.

## 4. Review and apply protocol (nothing here runs without the founder's explicit go)
