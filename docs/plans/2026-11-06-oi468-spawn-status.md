## Measured cause, group A (2026-11-06, this machine, SDK 3.11.1 = the Dart in CI's Flutter 3.41.4)

1. **Where the message lives.** `File not formatted as yaml: ` is a string of the Dart front end's `NativeAssetsValidator` (next to `Unexpected root object` and `Unexpected format version`): `grep -a -c` returns 1 for `dart-sdk/bin/dartvm` and for `snapshots/kernel-service.dart.snapshot`, `frontend_server_aot`, `gen_kernel_aot`, `kernel_worker_aot`, and 0 for the `dart` launcher and `dartdev_aot`. Earlier searches read text files only, which is why the origin was "not located".
2. **Writer and reader (strace; two reviewers re-ran it).** WRITER: only `dart run` (never the plain form `dart <script>`), when the package found upward from its WORKING DIRECTORY has a build hook (`objective_c` is in the tree): it opens `<cwd>/.dart_tool/native_assets.yaml` (cwd inside a hook-bearing package) with `O_RDWR|O_CREAT|O_TRUNC` and writes 171 bytes (truncate to write 0.23 to 0.3 ms, the file EMPTY in between), then execs the VM in the same process. READER: any `dart` or `dart run` (plain form included): a front-end thread opens `<SCRIPT's package>/.dart_tool/native_assets.yaml` `O_RDONLY` 245 to 390 ms later and validates it, whatever the cwd. VICTIM: a reader that opens the file while any writer on that same file is between truncate and write. Measured: cwd with no package + script in the package: no hooks line, no write, the file is read (reader-only: 8 of 8 exit 254 under the truncating process, empty stdout, the sightings' stderr); cwd in the package + script elsewhere: hooks run and the file is rewritten, no read; cwd in a subdirectory of the package: the writer writes `<subdir>/.dart_tool/` (a different file), the reader still reads the root file. The writer's file and the reader's file are the same file only when the cwd IS the package root. So every spawn of a repo script is a possible victim, and every `dart run` whose cwd is the repo root is a possible writer. `--packages=<elsewhere>` does not move the file.
3. **The race, in the repo.** The blast-radius CLI tests are victims AND writers (script and cwd both the repo root); the sot test is a victim only. The fifth sighting's log fits it: `blast_radius_progress_map_writer_paths_test.dart` (spawns `dart run scripts/blast_radius_from_diff.dart`, `:45`, no cwd) ran in the same second; CI runs `flutter test ... --reporter expanded` with default concurrency (`.github/workflows/test.yml:182`) and partitions whole files round-robin.
4. **Reproduced.** (a) A process re-opening the file with `O_TRUNC` in a loop: 40 of 40 `dart run` exit 254 with the identical two lines (the 40 had no saved log; an 8-of-8 and an 11-of-12 repeat followed, and a reviewer's repeats). (b) NO truncating process: six concurrent loops of the unmodified `dart run <script>`, two cores plus three CPU burners, 100 s: 1 of 265 runs exit 254, identical output (a minimal package with `objective_c` as its only dependency); a reviewer's repeat: 1 of 554. (c) The real gate scripts in this worktree under the same load: 1 failure in 195 `dart run` (`check_no_deferral_euphemism.dart`, 254, identical stderr). One event per stress run proves the race is real; it gives no rate, and WHY it is rare (the writer descheduled inside the 0.3 ms window under load) is an inference, not measured.
5. **The child never reached `main`.** Measured: a script whose FIRST statement writes a marker file, run 12 times under the truncating process: 9 exits of 254 and the marker existed after none of the 9 (a reviewer's repeat: 11 of 12, marker absent after all 11). strace of a failing run: the read returns 0 bytes, then the stderr line, `exit_group(254)`, no stdout write from the script. So when the helper's child IS the `dart` process, a retry cannot repeat a side effect of the script. It does not hold for a SCRIPT that itself runs a nested `dart run` and forwards its stderr and status (`scripts/check_two_user_cross_account.dart:26-39` does; it does nothing before the call and no test spawns it today): the signature could then reach the helper after work was done.
6. **Plain form.** `dart <script>` never writes the file and prints no `Running build hooks...`; it is still a reader, and a victim while any writer runs (4 of 4 and 8 of 8 under the truncating process). Converting spawns to it removes writers, not victims; its 0 of 222 under load is guaranteed by the absence of a writer in that loop.

## Decisions

D1. **Retry the cause-known signature, only for a `dart` child.** When the child executable is the Dart binary and an attempt exits exactly 254 AND its decoded stderr contains `File not formatted as yaml`, the attempt is run again, at most twice. "The Dart binary" is decided by the pure `isDartExecutable(exe)`: the basename (split on both `/` and `\`), lower-cased, with one trailing `.exe`, `.bat` or `.cmd` removed, equals `dart` (yes: `dart`, `/a/b/dart`, `C:\a\dart.exe`, `DART.EXE`, `dart.bat`, `dart.cmd`; no: `sh`, `/bin/sh`, `mydart`, `dart-wrapper`, `dart.exe.exe`, `/opt/dart/bin/sh`, `git`, `dartaotruntime`, an empty exe, a trailing-separator exe); `runInShell` with exe `dart` is included (the sot and blast-radius sightings spawn a bare `'dart'` with `runInShell: true`). Both conditions are required (a bare 254 is a compile error and stays a failure; the text with another status stays a failure; the text on stdout only stays a failure). It covers the victim side whatever the cwd. Why scoped: the "never reached `main`" measurement holds for the `dart` process itself; a `sh -c "<work>; dart run ..."` wrapper that forwards a nested 254 could repeat work done before the nested call, so wrapper children are NOT retried (residue R1). stderr may arrive as `List<int>` (`stderrEncoding: null`, `sync_resolver_fixtures.dart:27-35`): decoded as UTF-8 with malformed bytes allowed.
D2. **Retry an impossible status once, and say what that does.** On POSIX, an exit code above 255 or below -255 is not a process status; the helper runs the child once more. This applies to any child. Honest effect: for an idempotent child (`git push`, `config`, `add`, `merge`) a red becomes a green; for a non-idempotent child whose first attempt actually ran (`git worktree add -q <dir> -b wt` of sighting 3, `git commit`, `git commit --allow-empty`, `git clone`, `checkout -b`) one red becomes a second red with the child's own message ("already exists", "nothing to commit"), or its effect is duplicated when the caller ignores the status (`oi_numbering_lib_test.dart:257/264` `--allow-empty` commits). It never changes a CORRECT result: a spawn that returned a real status is untouched, and an assertion such as `exitCode isNot(0)` that a garbled status satisfied by accident now sees the real status. Both attempts are reported whole and the note names the first status, so a different red reads next to its cause. Not applied on Windows (exit codes above 255 are legitimate there). Net effect on the two sightings: group B sighting 2 (`push`) is cured; sighting 3 (`worktree add`) is diagnosable, not necessarily green. The OI asks for this retry; it is a containment for the idempotent case and a diagnostic for the rest, never an explanation.
D3. **One pure decision, a pure formatter, thin loops.** `spawnRetryDecision({exe, exitCode, stderr, raceRetriesUsed, lostStatusRetriesUsed, isWindows}) -> SpawnRetryReason?` holds all the arithmetic (budgets: race 2, lost status 1, per reason and independent, worst case 4 attempts: the sequence 254sig, lost, 254sig, lost stops at attempt 4 and returns the second lost result, with 4 reports and 3 notes); `spawnRetryNote({reason, k, cap, why, exitCode, stdout, stderr, ms})` is the pure public formatter (D4); `retryingSpawn` (sync) and `retryingSpawnAsync<T>` (async; accessor lambdas for exit code, stdout and stderr, because the `ProcessResult` and the `runSpawnWithInput` record share no type) time each attempt, report it, ask the decision, count, note and loop. Both loops take `bool? isWindows` (`?? Platform.isWindows`), `DateTime Function()? clock` (`?? DateTime.now`) and `note`; the three public entry points forward `note` only and never pass `isWindows` or `clock`. Tests table-test the decision and the formatter and run the same fake-driven sequences against BOTH loops.
D4. **A record that survives a passing test.** Before each retry runs, ONE line is printed with plain `print` (shown by `flutter test` in the CI log even when the test passes): `[spawn-retry] <reason> retry <k> of <cap> <why> | exit=<n> (0x<hex of n.toUnsigned(32), unpadded>) | <ms> ms | stdout(<len>)=<excerpt> | stderr(<len>)=<excerpt>` where k is the retry about to run for that reason, `<why>` the spawn's own label WITHOUT the attempt suffix, `<ms>` the failed attempt's own time (from the `clock`), `<len>` the character count of a String and the byte count of a `List<int>`, `<excerpt>` the decoded text (UTF-8, malformed allowed, NOT the `_render` form with its `N bytes` prefix) with `\r` and `\n` escaped first and the first 300 characters taken after that; `<why>` is escaped the same way, so the line is one line. Every attempt is also reported whole through the existing `report` channel (`printOnFailure`: shown only when the test fails); attempt 1 keeps today's exact `why`, attempt n>1 appends ` [attempt n]` (n is the overall attempt number). Nothing else survives a passing test; the printed line is the only durable record. Counting recurrences: `gh api repos/<owner>/<repo>/actions/jobs/<id>/logs | grep -c '\[spawn-retry\]'`; no alert watches it and GitHub keeps job logs about 90 days, so a reopen trigger that needs two runs can only be evaluated inside that window (an annotation was considered and not added because it cannot be verified without a CI run). The helper's own tests never let a real `[spawn-retry]` line reach stdout (a `note` seam or a zone that captures `print`) and use synthetic statuses (not the two real garbage values), so the count stays clean.
D5. **Not in the helper; every residue has a ledger row.** R1: children that are not the `dart` process (`sh -c` wrappers such as `claude_hooks_cwd_independent_test.dart:508-519` and `discipline_hook_local_indexes_e2e_test.dart:386`, hook scripts that run `dart run` inside), and `startSpawn` sites (the caller drives the streams; a retry cannot be made safely on a streaming Process). Per-site exposure is decided by where the SCRIPT lives (reader side), not the cwd: `discipline_hook_main_sync_e2e_test.dart:241` runs `dart run '$src/scripts/discipline_hook.dart'` with `src = Directory.current.path` (`:63`, `:81`): an exposed reader that the helper cannot retry; `batch_close_hook_e2e_test.dart:224` copies the scripts into its fixture (`:70-73`): not exposed; `land_pr_e2e_test.dart:275`, `:590`, `land_pr_replay_test.dart:189` (`fx.landCli`) and `claude_hooks_cwd_independent_test.dart:190` are classified in the diagnose doc by where their script lives. Harness hooks that run `dart run` on the same checkout while a suite runs also write the file: not fixable from a test helper. R2: group U (`a7f3d1`). R3: group B cause. R4: the hook race (D7).
