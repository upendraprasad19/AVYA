## Problem (from OI-520 and PR #314)

The three Dependabot lock commits of 2026-11-21 wrote a `pubspec.lock` that is not what Flutter 3.41.4 (Dart 3.11.1), the version CI, Vercel and `.fvmrc` pin, writes. CI stayed green on them because every one of its six `Install dependencies` steps runs a plain `flutter pub get`, which re-resolves such a lock instead of failing, while every developer tree went dirty after `pub get`. PR #314 re-committed a lock the pinned SDK writes. Nothing prevents a repeat: the Dependabot exemption of the merge gate checks the branch prefix, the commit authors and manifest-only paths (`scripts/check_plan_review_record_exists.dart:611-621`), never whether the lock is what the SDK writes.

## Claims the reviewers must try to break

C1. After this change a PR whose `pubspec.lock` is changed by `pub get` under the pinned Flutter (or is not tracked at all) fails `Analyze` at the verify step (diff exit 1 with the diff in the log, or the pathspec error), and `safe_pr_merge.sh` then refuses it; a PR whose lock `pub get` leaves unchanged behaves as before (F3: diff exit 0). The check is "unchanged by `pub get`", not "byte-identical to a fresh resolve": a lock committed with CRLF line endings under a `.gitattributes` `eol=lf` rule is left untouched by `pub get` and passes (round 2 measured it; that is the symptom OI-520 names, a dirty tree after `pub get`, so the behaviour is right and only the earlier wording overclaimed).
C2. The guard cannot be pre-empted or neutered inside the job: the job has only `name`, `runs-on`, `timeout-minutes` and `steps`, wherever they are written in the job block (before OR after `steps:`; comments, quotes and `key :` spacing do not hide a key); before the resolving step only `actions/checkout` and `subosito/flutter-action`; exactly one resolving step, exactly `flutter pub get`; the verify step directly after it with exactly `git ls-files --error-unmatch -- pubspec.lock && git diff --exit-code -- pubspec.lock`; the job's `flutter-version` equals every other job's; one job of the workflow file, and no job of any OTHER workflow file, carries the check name `Analyze`. The test pins each (31 mutants).
C3. Nothing else changes: five install steps stay plain, Vercel and `/build-apk` are untouched, the Dependabot exemption and the record gate are untouched (F5, F7).
C4. The test fails when the guard is weakened in any of the 31 ways it lists, each for its own named reason, and a REAL mutation of `test.yml` (not only the in-memory ones) reddens it (Verification plan).
C5. `Analyze` stays a merge-wrapper requirement only while it is in `requiredSuccessJobs`; the test pins that, so the guard cannot silently become advice.
C6. The change closes OI-520's option (a) as its Outcome will state: a CI check exists on the pinned SDK and fails a lock that would change (stronger than the flag, F10); the mutation proof is the test's mutants plus the real mutation run (CLAUDE.md §4.4 rule 24 governs new `scripts/check_*.dart` GATES and its ledger `scripts/check_gate_test_ledger.dart` enumerates only those, so this adds no ledger row; OI-520's "a new gate" is read as "a new CI check"); a Dependabot PR whose lock is already what the SDK writes still passes and keeps the record exemption (F7). ## Risks stated, not hidden

R1. **A Dependabot `pub` PR whose lock is not what Flutter 3.41.4 writes goes red and has no lightweight fix.** The obvious fix, regenerating the lock on the PR branch and pushing it, is a dead end (F12). The working routes: (i) a normal branch that applies the dependency change and the regenerated lock, a `platform`-tier change that needs the full plan-review record (PR #314 was exactly this); (ii) move the Flutter pin to a version whose Dart resolves what Dependabot resolves, in one batch (`scripts/check_ci_flutter_version.dart` pins the literals), after which Dependabot's own PRs pass and the exemption works again; (iii) hold the dependency below the version that needs the newer Dart with a Dependabot `ignore` rule (`.github/dependabot.yml`, a `platform`-tier file). The guard therefore turns "a silent bad lock" into "a bad-lock Dependabot PR needs a platform-tier PR or a Flutter pin bump". Frequency so far: 13 PRs in six months (F4), bursty. This consequence was not visible when option (a) was chosen and is reported to the founder.
R2. A merge in the GitHub web UI is not stopped (F2): `main` would run red on `Analyze`, and `scripts/reconcile_ci.dart` warns at the next session start; `build-apk.md:149-187` reads the run-level conclusion, so `--from-green` is blocked, which is intended. Branch protection with a required `Analyze` check is the founder's GitHub setting and is not part of this change.
R3. A `pub.dev` outage or a transient network error fails `Analyze` as it already would at a plain `pub get`.
R4. A green CI run on this PR does NOT discriminate: with a good lock the old step and the new check both pass. The discriminating evidence is F3 (the SDK's behaviour) and F11 (red runs on a real runner). The throwaway PR for the current mechanism skips the pre-push sweep with the sweep's own documented knob `CONTRACT_SWEEP_SKIP=1` (a warn-only advisory step, not `--no-verify`); it is closed unmerged and its branch deleted.
R5. Only the `Analyze` job enforces. A bad lock still lets the other required jobs run on a re-resolved lock, so a red PR can look "mostly green"; the red job's name is the signal.
R6. Not pinned by the test, accepted: workflow-level `env:` / `defaults:` (`test.yml:27` sets `TZ`), the runner image, a retargeted version tag of an allowed action, a `pubspec.lock` that is a symlink (UNVERIFIED: this Windows machine cannot create one), exotic YAML the hand-written reader does not parse: a flow-style job mapping or an anchor on the job line makes the job invisible and the test fails loudly (`[job-missing]`), but a complex key (`? key`), a merge key (`<<:`) or an alias that smuggles a key in is NOT read and would stay silent; none of these is used in the repo, and the compensating controls below cover a PR that introduces one. A YAML library was not used: `yaml` is only a transitive package, and declaring it would change `pubspec.yaml` and the very lock this change guards. The compensating controls are `--allow-workflow-change` plus the record gate on `test.yml` (`platform`), which any PR changing the workflow must pass (F13).
R7. The verify step compares the lock with what `pub get` writes on the Linux runner; the F3 measurements are on Windows. The lock content is OS-independent as far as PR #314 measured (byte-identical results), and this PR's own CI run is the Linux evidence: a red `Analyze` on the good lock would be a finding. Observed: run `44990058448` on `800debb9` is green end to end (all five required jobs success), `Analyze` included, so the verify step passes on the good lock on the runner (and F11 shows it failing on the drifted one).
