## 1. Decision, and what this plan does NOT claim

The app stops opening any Realtime channel. The code is deleted, not switched off.

**Accepted regression (founder, 2026-11-04):** after this batch (PRO only: the stream was PRO-gated, so a free user loses nothing) a weight logged on another client (the web app, a second device) that is older than 24 h at the phone's next cold start does not reach a phone that already has data, until OI-279's pull-on-resume ships or the app is reinstalled. Weight thereby joins the class every other log type is already in. In-session loss, stated too: a PRO phone that stays foregrounded or resumes used to receive another client's weight live, including rows inside the 24 h window; it now gets them at its next cold start (`splash_screen.dart:203`, the single `checkAndSync` caller). No compensating code is added (a weight-only 90-day window was offered and declined, because it would give weight a protection no other log has while OI-279 is the real fix). OI-279's entry gets a scope note for `weight_logs` in this batch (§8).

The plan does NOT claim to fix the PGRST reload or the cold-start stall. The founder's account (phone and web app; the code is platform-agnostic) is the only client observed opening the channel (the repo cannot rule out another subscriber, for example a dashboard inspector; §7 has an UNRESOLVED branch for that), so removing it also removes the only thing that wakes a Realtime tenant; a quiet period afterwards is consistent with the theory and proves nothing by itself (§7).

Out of this batch and filed with a terminal state (§8): the `weight_logs` publication membership (a live DDL that itself fires one more PostgREST reload, so it needs its own go), the redeploy of the `log-client-error` Edge Function (needs a go), and the paywall/Telegram copy (needs a copy decision).

Then I read `realtime_logs` for the hour after it. PASS means exactly "the new build did not wake the Realtime tenant in that session": no "Tenant ... is initializing", no "Creating partitions for realtime.messages", and (expected, NOT evidence, because the emitting code is deleted) no `realtime_*` row in `client_errors` from that build; only the two log lines discriminate.
