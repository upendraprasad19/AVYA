## 2. Design

One migration, one transaction, `SET lock_timeout = '3s'` first (as 159), idempotent where it can be.

### 2.1 Close the stale-credit window (OI-344 item 1, ledger N1)
`CREATE OR REPLACE FUNCTION private.process_referral_conversions` with ONE change: the credit select gains `AND rr.referee_id IS NOT NULL`. Every other line of the 159 body is kept; the test extracts 159's body from the immutable file and compares the new body to it with exactly that one line added. ACLs survive `CREATE OR REPLACE`.

### 2.2 The credit order stays as it is (OI-344 item 2, ledger N2): residual ACCEPTED by the founder, 2026-10-16 ("accept")
Rows locked by someone else do not consume batch slots (the candidate select is `SKIP LOCKED`); only in-loop skips (a referrer key or subscription row held) and permanent failures can pin the head of the 50-row batch, and starvation needs 50 or more of them at once (today 0). They are visible: a permanent failure raises `referral_conversions_failed` (once per 23 h), a hold for days raises the stall alert at 10 days (`159:198-205` counts `converted_at <= now() - 10 days` regardless of order, so the alert does not depend on the order). The real reason to change nothing: every credit attempt runs in a sub-block and takes a subtransaction id, which is what bounds the batch at 50, and any rotating order (a column or `random()`) is new behaviour in a catastrophic job for a state that has 0 rows today. So there is NO change, pinned by C13 and mutants ME/MF. The founder accepted the residual in chat on 2026-10-16 (answer: "accept"): ledger N2 is `verified_clean` with that answer as the evidence (risk acceptance, not a mechanical verification), so OI-344 item 2 closes and OI-344 can be archived once items 1, 3 and 5 ship; item 4 (promo ceiling, N5) is closed by 2.6. The X7 residual is appended to OI-336's text (which Unit C narrows rather than archives), so it keeps a board owner.

### 2.3 The redeem path no longer errors on a momentarily locked subscription row (item 5, N3)
`redeem_referral_atomic` replaces the single `PERFORM private.grant_referral_days(...)` with a bounded retry: up to 3 attempts, each in its own `BEGIN ... EXCEPTION WHEN lock_not_available THEN ...` sub-block (ONLY that exception; any other error propagates at once), `pg_sleep(0.25)` between attempts, the third failure re-raises. The sub-block rolls back only the grant attempt; the audit INSERT before it stays in the outer transaction and a final re-raise aborts the whole RPC call, rolling it back (no audit row, no subscription row). The helper and the job keep `NOWAIT` (the job must never wait). Everything else of the redeem body is byte-identical to 159. Worst case adds 0.5 s. The final 55P03 still reaches `redeem-referral` as a generic 500 (`index.ts:168-175`); NO Edge Function change is intended. The ledger says **"bounded retry"**, never "eliminated": after three attempts the caller still gets the generic 500.

### 2.4 Narrow what a client can read and remove what it can never write (item 3, N4)
```
REVOKE ALL ON public.referral_redemptions FROM PUBLIC, anon, authenticated;
GRANT SELECT (id, code, referrer_id, referee_id, days_granted_each, created_at)
  ON public.referral_redemptions TO authenticated;
```
Hidden from every client: `converted_at`, `referrer_reward_days`, `referrer_credited_at` AND `referrer_rewarded`, `referee_rewarded` (no reader needs them; leaving the flags readable would let a referrer see which named friend paid and, by polling, when). `REVOKE ALL ON TABLE` also removes column-level privileges, and re-running leaves the same state. The policy needs only `referrer_id` and `referee_id`, both granted. `service_role`, `postgres` and the SECURITY DEFINER functions are unaffected; the FK `ON DELETE SET NULL` actions run as the table owner. `anon` loses everything (it has no `auth.uid()`, so the policy already returned nothing).
**The migration verifies itself (a REVOKE can silently under-revoke when a grant was made by a role other than the one revoking).** After the REVOKE/GRANT, a `DO` block inside the same transaction raises (aborting and rolling back the whole migration) if `has_table_privilege` for `anon` or `authenticated` on the table is true for any of `INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER, SELECT`, or if `has_column_privilege('authenticated', ..., 'SELECT')` is true for any of the five hidden columns or false for any of the six granted ones, or if `has_function_privilege('anon', 'public.referrer_summary()', 'EXECUTE')` is true (anon inherits PUBLIC, so this also catches a PUBLIC grant) or if `aclexplode(coalesce(proacl, acldefault('f', proowner)))` has a `grantee = 0` EXECUTE entry for that function, or if `has_any_column_privilege` is true for `anon` on any verb or for `authenticated` on INSERT/UPDATE/REFERENCES (a column-level grant passes `has_table_privilege`). Nothing in it touches `service_role` or `postgres`, so a legitimate live ACL cannot trip it. The pre-apply read also records the table OWNER (`relowner`) and the applying role: if the owner is not the applying role the REVOKE is a no-op and the self-check aborts the apply, which is safe but must not surprise the founder. The pre-apply `relacl::text` (with grantors) is recorded so a failing block can be understood, not just rolled back.
**Residual, stated plainly (ledger X7 carries it):** a referrer's client can still read, per friend row, an opaque `referee_id` UUID (`users` is own-row-only, so a client cannot join it to a person) and `created_at` (the join time). And any aggregate that changes can be polled: two reads of `referrer_summary()` show a `days_earned` step of +7 or +30 on each credit (the plan class) and `subscribed`/`pending` steps on each payment, so for ONE friend the aggregate is the individual. That is inherent to the founder-approved fields; "no payment time, no plan class" means the app and the table never hand them over directly. The friend-facing disclosure (Unit C) says what is true: the referrer can see how many of their friends joined and subscribed.

### 2.5 The aggregate the app reads (U2 server half)
`public.referrer_summary()` returns `jsonb`: `SECURITY DEFINER`, `STABLE`, `SET search_path TO 'public', 'pg_temp'`, every relation schema-qualified (`public.referral_redemptions`), reads `auth.uid()` (raises `28000` when NULL), counts the caller's rows AS REFERRER:
`joined` = all rows (including rows whose referee was later deleted); `subscribed` = `converted_at IS NOT NULL`; `credited` = `referrer_rewarded IS TRUE` (a row credited under 158, `converted_at` NULL, counts as credited and not subscribed: 0 such rows live); `pending` = `converted_at IS NOT NULL AND referrer_rewarded IS NOT TRUE`; `days_earned` = `coalesce(sum(CASE WHEN referrer_rewarded IS TRUE THEN coalesce(referrer_reward_days, days_granted_each) END), 0)` (0, never NULL, for a referrer with no rows). No timestamps, no ids. `REVOKE EXECUTE ... FROM PUBLIC, anon`; `GRANT EXECUTE ... TO authenticated`. It is the only door to those aggregates.

### 2.6 The promo-discount ceiling (OI-344 item 4, ledger N5): founder decision 2026-10-16, 90 percent
The founder wants percent-off codes for marketing and chose a ceiling of 90 percent (free-access codes are a separate feature, OI-347). `ALTER TABLE public.promo_codes ADD CONSTRAINT promo_codes_discount_pct_check CHECK (discount_pct BETWEEN 1 AND 90)` (guarded by a `DO` block so a re-run is a no-op), added in this migration. Live check before the apply: the three existing rows are 30, 20 and 15, so `ADD CONSTRAINT` validates; a pre-apply `SELECT count(*) WHERE discount_pct NOT BETWEEN 1 AND 90` must return 0 or the apply aborts. The readers (`validate-promo`, `create-razorpay-order`, both writers' `derivePlanFromAmount` tolerance) need no change: they read `discount_pct` and already handle any value. Tests: a live-verify case (rollback block) that an INSERT of 91 and of 0 are refused with 23514 and 90 and 1 are accepted; a mutant that drops the constraint, one that makes the bound 100, and one that makes it `< 90`. This closes ledger N5 (`closed_in_commit`) and OI-344 item 4; the OI-342 text drops its reference to a ceiling that was never built. NOTE: the addition is reviewed by the B-pass and the hermes pass at build (catastrophic tier); the schema effect is a single CHECK on a 3-row table.

### 2.7 Explicitly NOT in this migration
The webhook `notes.source` check and the attribution race (N6, N7; catastrophic payment-function work), purchase during the trial (OI-341), any change to `anon` access to other tables, any Edge Function or client change.
