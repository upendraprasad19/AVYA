## Problem (measured 2026-11-21)

The `pubspec.lock` on `main` (changed by the Dependabot PRs #20, #21 and #9, merged 2026-11-21) cannot be honoured by Flutter 3.41.4, the version CI, Vercel and `.fvmrc` pin. On a clean checkout `flutter pub get --enforce-lockfile` exits 65 and a plain `flutter pub get` rewrites it: "Changed 31 dependencies", 127 insertions / 47 deletions, 19 version changes, 11 additions and 1 removal, nothing else touched.

**Cause, measured (F15, F16):** the lock `main` held at `2c2b3496`, before the Dependabot PRs, passes `--enforce-lockfile` (exit 0); at `a6c1825d`, the PR #20 merge, it fails (exit 65, "Would change 31 dependencies"). The committed lock asks for `riverpod` and `flutter_riverpod` 3.4.3, which pub.dev lists with `sdk: ^3.12.0`, while Flutter 3.41.4 bundles Dart 3.11.1; it also asks for `meta` 1.19.0 where the SDK's own `packages/flutter/pubspec.yaml:18` pins `meta: 1.17.0` (`:19` `vector_math: 2.2.0`; `packages/flutter_test/pubspec.yaml:20,21` `test_api: 0.7.10`, `matcher: 0.12.19`, against the committed 0.7.14 / 0.12.20). So a Dart 3.12 resolver wrote it and 3.4.3 could never be built with the pinned toolchain.

Consequences observed in this session: the `/build-apk` run for `1.0.0+50` left a dirty tree after `pub get`; `retire_worktree.dart` printed `KEEP [1 uncommitted file(s)]` for a worktree whose pre-push analyze had run `pub get`; and the dependency set of the `+50` AAB was whatever `pub get` resolved that day, not a committed file.

## Claims the reviewers must try to break

C1. After this change `main`'s lock equals what every writer in F10 already resolves on the pinned SDK (CI, Vercel's production web build, the `+50` AAB), so no behaviour of CI, the web deploy or a build changes; what changes is that the committed file says so and a clean checkout stays clean after `pub get`.
C2. Of the 31 changed packages, only `flutter_riverpod`, `meta` and `test` are imported directly (F11). `riverpod_annotation`, `build_runner` and `riverpod_generator` are DIRECT dependencies (`pubspec.yaml:40,99,100`) with zero imports, and `flutter_riverpod` is direct at `:39`; the rest are transitive. No `*.g.dart` file is tracked and no `lib/` file uses `@riverpod`, so the generator downgrade changes no generated output. App code already runs against `flutter_riverpod` 3.3.1 / `riverpod` 3.2.1 (the code cites that version, e.g. `lib/features/ai_coach/providers/ai_coach_provider.dart:2046`), and 3.4.3, the committed version, requires Dart 3.12 (F16), so it was never buildable or tested here. So no Gradle or Podfile input changes.

## Risks stated, not hidden

R1. The tool that wrote the committed lock is unnamed (the commits are authored by `dependabot[bot]`); what is proven is that it resolved with Dart 3.12 or newer (F16), not Dart 3.11.1.
R2. The regenerated lock freezes pub.dev's contents as of 2026-11-21 for the 31 packages `pub get` had to change; that is the purpose.
R3. Recurrence is expected: the next scheduled Dependabot pub run is Monday 2026-11-23 06:00 IST, and it also produced PRs on Saturday 2026-11-21, outside that schedule (F13). The Dependabot path exemption checks only which files changed, not whether the lock honours the SDK (`plan_review_record_lib.dart:200-202`), and neither this PR nor CI prevents it, because CI re-resolves. Terminal state: OI-520, `blocked_on_user` (the founder's choice of guard: CI `--enforce-lockfile`, Dependabot configuration, or a stated manual step). Not part of this change.
R4. `test` and `meta` are imported but declared nowhere (F11, F12). The regenerated lock holds `test` only through `riverpod` 3.2.1, and `riverpod` 3.4.3 depends on `test_api`, so the lock loses `test` as soon as a toolchain upgrade lets riverpod move up, and 53 test files then fail to resolve it. Terminal state: OI-521, `blocked_on_user` (declare both, or move the imports to `flutter_test`). Declaring them here would change `pubspec.yaml` and make the lock differ from the one the AAB was built from, so it is not part of this change.
R5. A green CI run does NOT discriminate between the old and the new lock: every job re-resolves before any test runs, and CI was already green on `main` with the old lock (`0907ee0d`, `baf90416`, `a00f3376` all `success`). The discriminating checks are the two in the Verification plan.
R6. Any later push re-runs CI (about 25 minutes) and `safe_pr_merge.sh` requires the final head to be green, so the order below matters.
