# OI-523: library v28, drop the Forward Lunge -> "Reverse Lunge" alias (rev 4, converged after plan-review round 3)

> **Execution mode (§4.12.7): inline.** One worktree (`oi507-lunge-alias`, base `70add5cf` = `origin/main`), one writer.
> Reviewers and the B-pass are fresh Sonnet subagents. Tier **L** (schema + library seed), blast radius `platform`.

## Why

OI-507 unit A (branch `oi507-formcues`, PR #329) adds an alias stage to the coach tool `getFormCues`: a name that matches no
row is looked up in `name_aliases`, and the matched row's cues are answered. Today `Forward Lunge` (G3470) carries
`name_aliases = {Reverse Lunge}`, so a user asking for "Reverse Lunge" cues would be answered with the cues of a FORWARD lunge
(wrong movement). Founder decision 2026-11-23: remove that alias, so "Reverse Lunge" answers `found: false` and the coach
answers from general knowledge in the library's short style.

The other questionable alias, `Bodyweight Standing Calf Raise` (G1373) `{Donkey Calf Raise}`, is **kept** (founder
2026-11-23, after the readers were listed): removing it would orphan the client name lookup for old plan rows and 4 logged
sets, and it is pinned by the OI-147 merge decision (diagnose c3e8f1, migration 175). Unit A's tool description already tells
the coach to name the exercise whose cues it gives on an alias match.

**BINDING ORDER (merge order, not only deploy order).** This unit merges and its migration is applied live FIRST. Only then does
unit A merge and only then is the `ai-proxy` deploy go requested. Unit A also drops its own copy of the OI-523 board entry
(section 5), otherwise its later merge would re-open the entry this unit closes.

## Risks

- The data change rides the existing removals-file path (no new importer code), so the risk is the test chain, not the tool: the digest helper and version pins (D2/D4) are the part most likely to be mis-edited.
- The UPSERT rewrites all 870 rows, so a drift between the asset and the cloud in ANY other column would be written too. The
  generator's `previousTuples` only validates a record's `before`; what proves the other 869 tuples is the tuples-match test
  (generated(asset) equals the newest migration at base; a simulation shows exactly one differing line after the flip) plus the new
  v28 pin "the generated file differs from 176 on exactly the G3470 tuple", and the rehearsal diffs the post-state against a live
  read of the cloud table (per-row md5 over the seeded columns).
- A device that already ran v28 cannot be re-bumped; a mistake found later is a v29.
