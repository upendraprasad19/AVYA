## Unit B1 — every meal logged in the last 24 h is counted twice after a launch

**Symptom.** Nutrition screen (phone and web) shows each meal and the day total at exactly 2× the cloud value after a restart (Upendra: breakfast 1033 → 2066, apple 95 → 190; brand-new Chintamani: lunch 280 → 560, snack 360 → 720). Each card shows an extra line named after the slot ("Lunch", "Snacks"). Doubles once, then stays.

**Writer (the defect).** `SyncService._pullNutritionLogs` (`lib/core/services/sync_service.dart` ~2658), called from `pullRecentCrossChannelLogs()` (~2602) on every `checkAndSync` (~1038). It selects `nutrition_logs` (no items join) created in the last 24 h and `nutritionBox.put(<cloud UUID>, {...row, source})` when that UUID key is absent. The user's real meal lives at `nlog_<date>_<meal>_<hash>`, so the same meal now exists twice; the UUID copy has totals and no `items`. Unchanged since 2026-03-31 (`8a5df734`): not a +49/+50 regression; visible only for meals logged < 24 h before a launch.

**Readers that double.** Every reader that walks `nutritionBox.values` by `date` without a key filter: `nutrition_provider.dart:440` (meal breakdown), `todays_meals_card.dart:149` (sums each row's `total_calories`), `nutrition_read_service.dart:126`, `nutrition_repository.dart` (77/105/169/287/468), `home_provider.dart:816`, `ai_snapshot_builder.dart` (875/935/998/1228). The display name of the copy falls back to the slot (`NutritionReadService.deriveMealDisplayName`: no `items` → `meal_type`).

**Recurrence.** Writer/reader drift class (cloud key vs local key) — the same shape as APK Test #12.8 Bug #1 (restore keyed by cloud UUID, fixed in `_restoreNutritionLogs` by deriving the `nlog_` key). Related: `b9d3f1` (Telegram dropped, its code left dormant, OI-476). Not a recurrence of a specific diagnose-doc.

**Fix.**
1. `_pullNutritionLogs(userId, since)` becomes a call to the existing `_restoreNutritionLogs(userId, since)` (`sync/sync_nutrition.dart` ~609): same 24 h `created_at` window, but items joined, `nlog_` key derived by `_nlogKeyForRestore`, 3-way local-wins merge (`nutritionLocalSlotIsSuperset` skip / multiset union). This keeps cross-device freshness (a meal logged on the web still appears on the phone at the next launch) — the pull is the ONLY launch-time path that brings another device's meals (`_restoreNutritionLogs` otherwise runs only from the restore entry points).
2. One-time per-user cleanup of copies already on devices: delete every `nutritionBox` entry whose KEY is UUID-shaped (`^[0-9a-f]{8}-[0-9a-f]{4}-…$`), whose value is a Map with `meal_type` and `date`, and which has NO `items` key (the pull's exact shape; a restored or locally written meal always has `items` and an `nlog_` key). Runs from the restoring-screen migrator list (next to `migrator=nlog`), guarded by a per-user flag in a per-user box (NOT `migrationBox`/shared `configBox`, see `ScheduleHybridRepairMigrator`). Telemetry `nutrition_pull_copies_removed count=N`.
3. Kill switch `configBox['disable_nutrition_pull_via_restore']`: true = the old `_pullNutritionLogs` body (kept verbatim). Removal tracked on a new OI after the device check (§4.6.4).

**Open risk for review (pre-existing semantics, now run more often).** The union merge keeps both an old and an edited item when another device changed a quantity (`roti|100` + `roti|150`) — an over-count for edited meals. Today this only happens at sign-in restore; routing the launch pull through it applies it to any meal created in the last 24 h at every launch. Options: (a) accept (edits are rare, same as restore); (b) for the launch pull only, skip a cloud row whose slot already has ANY local row (pure local-wins; a cross-device edit is then not pulled, but nothing double-counts). Draft choice: (b), via a `localWinsWholeSlot: true` parameter used only by the pull. Reviewers: confirm.

**Tests.** `test/sync/nutrition_pull_no_double_count_behavioral_test.dart`: Hive has `nlog_…` lunch (roti+dal); stub cloud returns the same meal (with items, id UUID); run the pull; assert exactly one row for the slot and day total = cloud total; second launch unchanged; a cloud-only meal (web log) appears once with its items; kill switch ON reproduces the old UUID copy. Cleanup: a box holding the phantom shape + a real `nlog_` row + a saved meal → only the phantom is removed; flag makes it run once; a UUID key WITH `items` is kept. Mutation: restore the old pull body → the double-count test reddens.

## Unit B3/B7 — Train history sheet drops completed days; phase date ranges are wrong

**Symptom.** Phase I week 2 "Completed history" shows Sun + Mon only; cloud has Tue 29 Sep–Fri 2 Oct completed (Oct 1 PULL + CORE). Phase chips show Phase II "APR 27–MAY 3…", Phase 3 "ends 28 June", Phase 4 "from 12 Oct".

**Reader (the defect).** `WorkoutScheduleReadService.bucketPastRows` (`workout_schedule_read_service.dart:2020`) groups ALL past rows by the stamped `phase` (carry-forward), ignoring dates; a block's bounds are min/max date of its rows. **Writer of the stray stamps.** Not yet identified (candidates: a phase regeneration that rewrote workout rows over past dates — `generateAndScheduleFromDate`, the coach `RegeneratePlanPlanner`, the dev simulation harness, `PlanIntegrityReconciler.mergeScheduleEntry`). Step 1 of the unit: trace it with `git log -S"'phase'"` on the schedule writers and the account's history; if a live writer still stamps past dates, fix it in this unit; if it was a removed path or the simulation harness, say so in the diagnose-doc.

**Fix.** DISPLAY ONLY — the strict `pastPhaseBlocks()` that feeds `PhaseProgressReconciler` (monotonic `current_phase`, "an over-advance is unrecoverable") is NOT touched. Add `bucketPastRowsForDisplay(rows)`: sort by date; split into segments at any gap > 10 days between consecutive rows (a break in plan use); inside a segment cut consecutive 28-day windows from the segment start; stamps are ignored for grouping. `pastPhaseBlocksForDisplay` uses it in both branches. Week chips and the sheet keep `entriesForWeek` (now always within a 28-day block). Numbering stays "last `currentPhase-1` blocks".

Mutation: group by stamp in the new function → test 1 reddens.

## Unit B5 — dictation keeps only the last fragment of a long sentence

**Symptom.** Coach mic, one long sentence: the field ends with "or the coming week" only.

**Writer (the defect).** `SpeechInputController.engineResult` (`lib/core/services/speech_input_controller.dart:397-398`) sets `_liveText = result.words` (replace) for every partial; a final replaces again at :393 (`_finish(auto, result.words)`). `SpeechInputService.listen` (`speech_input_service.dart:261-262`) passes `recognizedWords` through; nothing accumulates. When Android's recognizer starts a new segment mid-utterance, the earlier words are lost. Readers: `CoachComposer` `_onSpeechEnd` (`input_bar.dart:151-166`), live bar (`input_bar.dart:453`), `FoodLoggerSection`.

**Recurrence.** Not a recurrence (abe150 is the first-use start timeout).

**Fix.** Keep `_committed` (finished segments). On a partial that is NOT a continuation of the current segment (the new text does not start with the current segment's first word AND is shorter than half of it), fold the current segment into `_committed`; `_liveText = join(_committed, segment)`. A final is appended to `_committed`, never replaces it. `_start` resets `_committed`. Add LOW telemetry per session end: `speech_segments count=N` (counts only, never words). Kill switch `configBox['disable_speech_segment_accumulate']`.

**Unproven without a device.** Whether Android resets `recognizedWords` mid-utterance (vs. a short final). The telemetry answers it on Monday's walk.

**Tests.** Extend `test/core/speech_input_controller_behavioral_test.dart` with the fake engine: partials "I want a plan", "I want a plan for", reset "or the coming week", final "or the coming week" → transcript holds all words once; a normal growing sequence is not duplicated; a revised partial ("I want a plant" → "I want a plan") is not treated as a new segment. Mutation: revert to replace → reddens.
