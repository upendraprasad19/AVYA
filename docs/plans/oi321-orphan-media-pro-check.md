## 1. Ground truth (file:line, base d363553e; live facts read-only on 2026-10-11, project `dedsavbjuwgarrhphgnl`)

**The deleter.** `supabase/functions/clean-orphan-media/index.ts:91-98`: for each candidate `{user_id, path}` it calls `rechecksIsPro` (`:120-129`), `continue`s when true, otherwise `storage.from('chat-media').remove([obj.path])` (`:96`) and `deleted++` (`:97`). The `remove` result is never read, so a failed removal is counted as deleted.

**The recheck.** `rechecksIsPro` selects `end_date` from `subscriptions` (`user_id`, `status='active'`, `end_date > now`) ending in `.maybeSingle()`; it destructures only `{ data }` and returns `!!data`. Two ways to get `data == null` for a user who IS PRO: (a) `.maybeSingle()` yields PGRST116 when more than one row matches (two unexpired active rows: the ordinary shape of a renewal bought before the old term lapses); (b) ANY read failure (`error` is never read). Both read "free" and the next line deletes the file. (b) is the larger hole and is not what OI-321 names.

**How narrow each hole is.** Candidates come from `public.find_orphan_chat_media` (`supabase/migrations/071_rename_orphan_media_rpc.sql:18-39`, `NOT EXISTS` over `subscriptions` at `:33-38`; migration 090 only added `SET search_path`, 117 only REVOKE/GRANT). **Live body read with `pg_get_functiondef`: identical to 071 plus the search_path** — it pre-filters every user with an active unexpired subscription. So at scan time every candidate is non-PRO; the recheck exists for "the user upgraded between the scan and the delete" (`index.ts:93`). Both holes therefore need a mid-run upgrade, and (b) also a read error in that window. Exposure is small; the harm is irreversible (a PRO user's chat photo deleted; `test/contracts/coach_media_repository_test.dart:18` records "PRO users must keep BOTH copies", `coach_media_repository.dart:14` the 30-day TTL for FREE users). This corrects the OI text and my earlier summary, which did not account for the pre-filter. Live `subscriptions.status` values: `active`, `cancelled`, `expired`; rows with NULL `end_date`: 0.

## 2. Design

**D1 `readProState(client, userId, now = new Date()): Promise<ProState>` appended at END OF FILE of `_shared/subscription.ts`** (after line 276; nothing above line 262 changes its line count, because `scripts/check_sot_registry_parity.dart:160-190` raises `[stale-line-range]` when a registered symbol leaves its range and `docs/sot_registry.yaml` registers `fetchLatestActiveEndByUser` at 236-262). `type ProState = "pro" | "free" | "unknown"`. Reads `subscriptions` with `user_id`, `status='active'`, `.gt("end_date", nowIso)` where `const nowIso = now.toISOString()` (a token DISTINCT from the other two copies, see D6), `.limit(1)`, never `.maybeSingle()`. `error` -> `"unknown"` (logged: `error.code`/`error.message`, no user id); a thrown rejection -> `"unknown"`; `data` not an array -> `"unknown"`; empty or non-string `userId` -> `"unknown"` WITHOUT querying; array length > 0 -> `"pro"`; length 0 -> `"free"`. `isProUser`, `fetchProUserIds`, `fetchLatestActiveEndByUser` are NOT changed (callers' semantics preserved, `isProUser` feeds `consume-day-swap`'s quota tier). The warning that `isProUser`'s `false` is unsafe before any destructive action lives in `readProState`'s docblock.

**D2 `supabase/functions/clean-orphan-media/logic.ts` (new; the `consume-day-swap/logic.ts` pattern — `index.ts` is a `serve()` shell reading env at import, so everything testable is extracted; `_shared/subscription.ts` imports only `paged_fetch.ts`, which has no imports, so `logic.ts` stays import-safe).**
- `removeFromBucket(storage, bucket, path) -> {error, removed}`: the ONE `.remove(` in the function folder. A THROWN storage call becomes `{error, removed: null}`; `removed` is the length of `data` when it is an array, else `null`.
- `sweepOrphans(candidates, deps) -> SweepResult` with injected `readProState(userId)` and `removeObject(path)`. Per candidate `scanned++`; a candidate whose `user_id` or `path` is not a non-empty string, or whose `path` does not start with `user_id + "/"`, is `skippedUnknown` (the PRO check keys on `user_id`, the removal on `path`; the RPC derives one from the other, this keeps drift from separating them). The state read is wrapped (a throwing dependency reads `unknown`) and the object is removed ONLY when the state `=== "free"` exactly; `"pro"` -> `skippedPro`; anything else (including a value outside the union) -> `skippedUnknown`. A removal result with `error` -> `failed` (not `deleted`); `removed === 0` -> `alreadyGone` (the object vanished between scan and removal; Storage is believed to answer an already-missing object with success and empty data — not verified here); otherwise (`removed > 0` or `null`) -> `deleted`. One read per candidate, no per-run cache (keeps the "recheck at delete time" freshness). Also records `firstFailure` (the first distinct failure code: an error `code`, or `read_unknown` / `remove_error` / `invalid_candidate`), never a user id or path. Returns `{scanned, deleted, skippedPro, skippedUnknown, failed, alreadyGone, firstFailure}`.
- `runSweep(client, candidates)`: composes `sweepOrphans` with `readProState(client, userId)` and `removeFromBucket(client.storage, 'chat-media', path)`. This is where the bucket literal lives, so the wiring is behaviourally testable with one fake client.
- `runErrorSummary(result) -> string | undefined`: set when `failed > 0 || skippedUnknown > 0`, e.g. `skipped_unknown=2 failed=1 first=read_unknown`; counts and a code only.

**D3 `index.ts`.** Delete `rechecksIsPro` and its `SupabaseClient` import if unused; after the candidate fetch (unchanged) call `runSweep(supabaseClient, candidates ?? [])`, log one line with all counts (`console.warn` when `skippedUnknown + failed > 0`), end with `logCronEnd(logId, status, { httpStatus, requestId, errorSummary: runErrorSummary(result) })` and return the counts (`skipped_pro`, `skipped_unknown`, `failed`, `already_gone` are additive to `scanned`, `deleted`; the only reader is the cron's `net.http_post` result row, which does not parse counts). The `catch` and the candidate-RPC leg keep the literal `logCronEnd(logId, 'failed'` (`test/contracts/cron_telemetry_adoption_test.dart:117-121`). **Telemetry decision (revised after the B-pass, finding 1):** an unreadable subscription or a failed removal is always recorded on the `cron_call_log` row (`error_summary`), the log line and the response, and the objects are RETAINED. The run ends `success`/200 EXCEPT when it could not do its job: `isSystematicFailure` (at least 5 candidates undecided, `skippedUnknown + failed`, AND a majority of `scanned`) ends it `failed`/500, which pages through `alert_cron_failures` (migration 147 -> 133 -> the founder's Telegram). Round 2 had removed any escalation because the naive form pages on one transient blip or, every day, on one permanently unremovable object; the ratio-with-a-floor form does neither, and without it a systematic outage (a revoked grant on `subscriptions`, a rotated service key, a PostgREST outage at 03:00) would end `success` with zero deletions every day and the free tier's 30-day TTL would silently stop. In-repo precedent for the ratio idea: `weekly-recalc/index.ts:415-420` (`errors > processed` => `failed`/500); the earlier cited precedent `re-engagement` was WRONG (its success legs pass no `errorSummary`). The residual gap is only the PARTIAL case: a persistent unknown state below the threshold (fewer than five, or not a majority) is visible on `error_summary`/the log but raises no alert.
