## 2. Design

**D1 Repository (`progress_photo_repository.dart`).**
- Delete `_freeDailyCap`, the `isPro` read and every tier branch: one cap (5 per IST day), one quality (3000 / 95). `capture` becomes PRO-only by construction (the screen gates the call; the server refuses the rest).
- `PhotoQuotaException` loses `isPro` (always true now) and its upgrade wording; the screen shows the come-back-tomorrow snackbar only.
- New `ProgressPhotoProRequiredException` thrown by `capture` when the failure is a PRO refusal. Classifier `isProgressPhotoProRefusal(Object e)` (top-level, pure): true for a `PostgrestException` with `code == 'P0001'` whose message contains `progress_photo_pro_required`; true for a `StorageException` whose `statusCode` is `'403'` (the shape the live Storage API returns for an RLS refusal is NOT yet verified, stated). Because the Storage shape is unverified, `capture`'s catch has a second leg that does not depend on it: for any OTHER upload/insert failure it asks the server (`SubscriptionService.instance.verifyFromServer(force: true)`); a `false` answer is a refusal, a `true` answer (including the offline "trust local" answer) leaves the generic failure. Never the reverse: a refusal is never inferred from an unknown error alone.
- OI-322: the row's `taken_at` is sent as `takenAt.toUtc().toIso8601String()`; the cap window is the IST day (`istMidnightUtc(now)`), per the project's IST-throughout rule, so the count and the stored instant agree. Two top-level pure helpers carry both (`progressPhotoTakenAtWire`, `progressPhotoCapWindowStartUtc`). Existing rows stay as stored (an IST user's old `taken_at` is 5.5 h late): nothing reads the value except the cap window and the sort, so the only effect is a one-day wobble at the cap edge that ends the day after the deploy; no backfill (a backfill would have to guess each user's zone).
- The cap-check's own swallow (`catch` falling through to the upload) stays; the server rule is now the real bound for PRO state, the 5/day cap remains client-side (OI-315, unchanged).

**D2 Screen (`progress_photos_screen.dart`).** `_Access` gains `readOnly`:
- `_enter`: `gateAndVerify`. `onPro` -> `granted` + `_load()` (unchanged). `onFree` -> read the user's own photos (`list()`): none -> `denied` (the existing locked card, so a never-PRO user still sees the upsell and NO write is offered); one or more -> `readOnly` (the gallery with delete, and an Add button that goes to the gate, never to a picker). The free user's `list()` is one RLS-scoped read of their own rows.
- `readOnly` shows the gallery, long-press delete (unchanged `_delete`), and the same `FloatingActionButton` whose tap runs `_onAddPhoto`; its gate's `onFree` now calls `_downgrade()` (to `readOnly` when photos are held, `denied` when none) and opens the paywall, instead of always going to `denied` (which would hide a lapsed user's photos mid-session).
- `_capture`: `on ProgressPhotoProRequiredException` -> `_downgrade()`; if `SubscriptionService.instance.isPaymentInFlight` show "Your PRO is still activating - give it a minute and try again." (the just-paid window: the row is written by the webhook / `verify-payment`, seconds to about 20 minutes), else open the paywall. Any other failure keeps "Upload failed".
- The upgrade listener (`ref.listen`) re-runs `_enter` for `denied` AND `readOnly` when `next.isPro`.

**D3 Hub (`user_photos_screen.dart`).** The Progress row stops gating: it pushes `/profile/progress-photos` for everyone (the screen owns the decision). The subtitle keeps the free hint. This is the one place the b7c1e4 behaviour changes on purpose: before, a free user got the paywall from the hub; now a never-PRO user lands on the screen's locked card (same upsell, one tap deeper) and a lapsed user lands on their photos.

**D4 Docs.** Nested `lib/features/profile/CLAUDE.md` (the two bullets, the SoT row, the two pitfalls rows), `docs/architecture/subscription.md` if it states the old behaviour, SoT registry entries for the repository and screen lines, ledger rows C6 and C7 of `docs/audit/progress-screen-pro-gate.closure.yaml` -> `closed_in_commit`, OI-314 and OI-322 close (`closes-oi:` trailers, moved to `closed_issues.md`), diagnose-doc (FULL template if the commit is `fix:`; a `feat(profile):` commit needs none, but the OI-322 part IS a bug fix: the commit is `fix(profile):` with `closes-diagnose:`), bug class entry only if a new class appears.

**D2'' Single-writer screen.**
- ONE async method `_reload({bool keepGallery})` is the only code that assigns `_access`, `_photos`, `_error`.
