## 2. Design (Piece A)

### 2.1 One shared module, decision AND error mapping in it, OFF by default
New `supabase/functions/_shared/subscription_stacking.ts`:
- pure `stackedEndDate(latestActiveEnd: Date | null, now: Date, days: number): Date` = `base + days`, `base = max(now, latestActiveEnd ?? now)`, with the SAME `setDate(getDate() + days)` the writers use today (no active row -> byte-identical to today's `now + days`).
- `readLatestActiveEnd(db, userId, paymentId, nowIso)`: `.eq("user_id", userId)` (without it a payment would stack on ANOTHER user's PRO end), `status = 'active'`, `end_date > now`, **excluding the caller's own payment** (`.or("razorpay_payment_id.is.null,razorpay_payment_id.neq.<id>")`: a plain `neq` drops NULL-payment-id rows such as trial and admin grants under SQL NULL semantics, so the `is.null` arm is required), `order end_date desc`, `limit 1` read as an ARRAY (never `.maybeSingle()`: a user can hold several active rows, bug f2b9d4); returns `{ ok: true, end: Date | null }` or `{ ok: false }` on a database error, on an unparseable `end_date` (skipped like `reduceLatestEndByUser` does; if every candidate is unparseable the result is `ok:false`, so `toISOString()` never throws a RangeError inside a writer) and on a `paymentId` that fails the strict format check `^pay_[A-Za-z0-9]{1,64}$` before it is interpolated into the `or()` logic-tree string (`,` `(` `)` are structural there; the group is ANDed with the `user_id`/`status`/`end_date` filters, so the blast radius of an unchecked id is bounded to the caller's own rows, but the check fails closed anyway). The exclusion makes the helper immune to the sibling writer's row for the SAME payment (verify-payment and the webhook can race; today the `razorpay_payment_id` UNIQUE constraint, migration 010, discards the loser's value, and a later refactor to upsert/ignore-duplicates would otherwise double-stack).
- `resolveEndDate(db, userId, paymentId, now, days, env)`: the ONE function the writers call. It returns `{ ok: true, endDate }` or `{ ok: false }` and **catches thrown rejections** (a transport failure must reach the same `ok:false` arm and the reconcile log, not the outer generic catch). **The switch is an ENABLING secret `ENABLE_SUBSCRIPTION_STACKING` (CLAUDE.md 4.6 / 4.12.4: the new path is closed by default, the old path is reachable and verbatim):** unless the value is exactly the string `"true"` (the repo's own switch rule, `prediction_quota_switch.ts:16-18` reads `Deno.env.get(name) === "true"`; the earlier trim/lower-case leniency is dropped: for an ENABLING secret the strict form is the safe one) it SKIPS the read and returns exactly `now + days`; no query is issued and no new failure mode exists. Read per call through an `env` reader parameter (the file `_shared/prediction_quota_switch.ts` reads `Deno.env` directly; the parameter is the test seam). Whether a dashboard secret change reaches warm isolates without a redeploy is NOT claimed; Piece B's flip step verifies it before relying on it. Logged in `docs/ship_dark_pending_review.yaml` in the build commit with the ledger's own fields (`flag`, `branch`, `build_commit` null until the stamp commit, `build_date`, `flip_reviewed: false`, `flip_commit: null`, `note`; there is no `tier` field there); the flip is a Piece B action that needs B's full x2 review, and the entry moves to `resolved:` with a `flip_review_record:` only once that record shows full x2 plus `bpass: accepted`.

### 2.2 Writer call sites, minimal
Each writer calls `resolveEndDate` ONLY inside its insert branch, after the idempotency pre-SELECT found nothing (so a replay never reads its own row), and the stored `end_date` is its result. For `verify-payment`, `canonicalEndDateIso` is assigned from the stored value on a first insert (round-2 finding 9), so the response `end_date` (which the client writes to Hive) equals the stored one. For the webhook, `endDate` is reassigned to the stored value so its first-insert response `expires_at` (`:637`) equals the stored row too; its replay/23505 arms and the H-19 early return are unchanged. `start_date` stays `now`.
**A read error fails the call, it does not guess.** `verify-payment` answers its existing insert-failure response (`:581-601`: `{ verified: false, error: "Could not record subscription; please retry", request_id }`, 500, no insert) and the client retries (Phase 2 failure, then the 60 s / 5 m / 15 m schedule); the webhook answers its existing 500 (`:595-603`). A silent `now + days` fallback would under-deliver paid time. **Money-taken-no-row is made reconcilable:** on this path each writer logs `console.error("[<fn>] stacking read failed request_id=%s payment_id=%s user_id=%s code=%s", ...)` (the error CODE, never the message), so the founder can find and fix the row by hand. This is a plain log with the platform's log retention (not an alert row); because the switch is OFF, the path cannot run until the flip, and Piece B adds an alert row (`public.alerts`, which the Telegram trigger already forwards) as a PRECONDITION of the flip. The retry statements make no claim about the webhook's retry window (round-2 finding 11: `payment.md` rule 5 and the code comment at `razorpay-webhook:312-313` disagree about `payload.created_at` vs the payment entity; Piece A verifies which is true and corrects `payment.md`, it does not rely on either).
Race determinism and "not improved for two different payments racing past the guard" are unchanged from v2.

### 2.3 Testability: a fetch-level fake, no handler body change
`verify-payment` and `razorpay-webhook` change ONLY their opening and closing wrapper lines (`serve(async (req: Request) => {` at `verify-payment:171` / `razorpay-webhook:236` -> `export async function handler(req: Request): Promise<Response> {`, and the closing `});` -> `}` plus `if (import.meta.main) serve(handler);`); the body between them is changed only by the call sites of 2.2. Handler tests import the module dynamically after `Deno.env.set(...)` of every module-scope variable, and replace `globalThis.fetch` with a router (a fake Supabase PostgREST + auth + Razorpay), so the REAL supabase-js client generates the REAL query strings. Stub list (stated, exhaustive): `GET /auth/v1/user` (JWT), `GET/POST/PATCH /rest/v1/subscriptions` (select with the exact filters, insert, 23505), `POST /rest/v1/rpc/consume_quota`, `POST /rest/v1/rpc/increment_promo_used_count` and the `promo_code_uses` insert (`redeemPromo`, `verify-payment:142-152`, `razorpay-webhook:220-230`), (`users` is NOT stubbed: neither function reads it since OI-202; the webhook has no `auth/v1/user` call and needs a test-computed HMAC of the body keyed with `RAZORPAY_KEY_SECRET`), and `https://api.razorpay.com/v1/payments/<id>` (+ order). The router records every request so a test can assert "no insert", "helper read happened once", "promo redeemed once". It is a small in-memory PostgREST evaluator for the subset the code uses (`eq`, `gt`, `neq`, `is.null`, `or`, `order`, `limit`, `select` column lists) over fixture rows, so "expired row ignored", "latest of several", "own payment excluded" and "NULL-payment-id trial row kept" are proven by semantics and not only by the query string. **The evaluator models SQL three-valued logic:** `neq` against a NULL column does NOT match (otherwise the mutant 'bare neq' stays green), `is.null` matches NULL, `gt` compares parsed instants (not strings; PostgREST may render `+00:00` or `Z`, `_shared/subscription.ts:164-168`), and the fixture holds a NULL-payment-id trial row that must be KEPT and the caller's own-payment row that must be DROPPED; it also emulates the postgrest-js quirks the code meets (a `.maybeSingle()` GET over more than one row answers PGRST116; an insert conflict answers a 23505 body with a `code`; `rpc` scalar returns). The same file asserts the exact query string. **Stated gaps:** the fake proves the string and the semantics, not that LIVE PostgREST accepts the query (the read-only MCP `SELECT` in section 3 covers only the SQL equivalent); that proof is the first enabled call and is therefore a Piece B flip step. **Test hygiene:** the first handler test is written and run alone to see whether Deno's default sanitizers object to the supabase-js auth/realtime timers (if so: per-test sanitizer options or closing the client); `Deno.env.set` of every module-scope variable is undone in teardown (the process-wide leak class of `reference_deno_test_env_leak_daily_snapshot_2026_10_11`); the TZ equivalence test runs one subprocess per TZ because `Deno.env.set("TZ")` may not re-detect the zone mid-process.
**Precondition (round-2 finding 7):** the `import.meta.main` premise is recorded for `redeem-referral` v20 only as "deployed" (ledger U1 lists the authenticated smoke as not done). Before the first deploy of Piece A the anon-key boot probe of `redeem-referral` (503 = broken; the module's own 4xx = booted) is run and its HTTP code and body written into the build record (this probe is a request, not a change; it still waits for the founder's go with the deploys). If it is 503, Piece A does not wrap and the tail change is redesigned.
Deploy flags (round-2 finding 8): `verify-payment` `verify_jwt=true`, `razorpay-webhook` `verify_jwt=false`; a wrong flag makes Razorpay webhooks 401 at the gateway. The CLAUDE.md "deploying from a branch behind `main`" check applies before each deploy.

### 2.4 verify-payment: a strict payment-id format check (found during round 4, coordinator-verified)
`verify-payment/index.ts:304-317` only checks `paymentId` is non-empty, then interpolates it UNVALIDATED into `https://api.razorpay.com/v1/payments/${paymentId}` (and `/capture`, `:349-350,:385`) with the account's Basic credentials, and stores it verbatim in `subscriptions.razorpay_payment_id`, whose UNIQUE constraint (migration 010) only dedupes the exact string. If Razorpay's API ignores a trailing query/fragment (UNVERIFIED here, and not testable without a live Razorpay call), one captured payment could be claimed under several distinct strings, each creating a row (and, with stacking enabled, each adding time). Live data (read-only, 2026-10-16): 14 `subscriptions` rows; every real Razorpay id is `pay_` + 14 alphanumerics (9 of 9, all 18 characters); 4 rows have a NULL id (trial and grants); ONE non-conforming row is an admin grant (`manual_...`, 41 chars, not created by this function). No evidence of abuse, and no legitimate id can fail the check. The fix: right after the non-empty check, `if (!/^pay_[A-Za-z0-9]{1,64}$/.test(paymentId))` answer 400 `{ error: "Invalid payment_id" }`. NOT switch-gated (it is validation, and its absence is the hazard). Handler tests: a conforming id passes, and `pay_X?y=1`, `pay_X/capture`, `pay_X#1`, `../x`, an empty string and a 65-character id are rejected with 400 BEFORE any Razorpay call (the router records zero Razorpay requests); mutants: drop the check; anchor removed; wrong class. The webhook takes the id from an HMAC-verified payload and is unchanged. Whether the unvalidated form was ever exploitable is reported to the founder as an open, unverified question; it is not asserted.
