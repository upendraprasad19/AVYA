## 4. Root cause (calibrated)

MEASURED on the stub chain (2.2): **a restored canonical exercise row is rewritten by `ExlogKeyMigrator`, which invalidates the fingerprint the restore just recorded, so the next exercise push re-uploads every restored row.** The migrator's own "0 changed" log hides it.
CODE-VERIFIED: **confirmations are persisted once, at the end of a pass** (a retry, a reload, a killed app or an owner abort redoes the pass); and on a fresh device two entry points push the same domains right after restore (the daily sweep, because `last_full_sync` is null, and the migrator-triggered `syncWorkoutData()`).
Bug history (§4.1.5): recurrence class. Direct recurrence: **`f3d2a7`** (`2026-10-09-restored-exlog-pushed-back-f3d2a7.md`: restored rows pushed straight back; fixed by recording fingerprints at restore, which the migrator then defeats). Same class: **`f1c6b4`** (a per-launch restore writer rewrites unchanged rows; fixed by comparing with `canonicalJson`), `a8c4e5` / `f3d2a7`-era overlapping-pass commit (`2026-10-09-skip-index-overlapping-passes-a8c4e5.md`), OI-204 / OI-237 (write amplification), e5b2a9 / class 2.82 (retry controller), c4f8d2 / b4f7e2 / e7c1a9 / class 2.43 (fan-out), L1a-3. Each fixed one trigger; none made the confirmation durable per row, and none noticed the migrator. (v2/v3 cited `e6a2d4` as the restore-fingerprint diagnose; that is the rep-validation doc and was a copy slip from the L1a-3 file header.) FULL diagnose template.

## 5. Design A1 (`restoring_screen.dart` is not edited: Gate 43, at 798/800 lines, is untouched; Gate 50 phase 2 DOES apply to the new `fresh_device_` key prefix, handled in section 8)

**W1 — the migrator stops rewriting what is already right** (`lib/core/services/exlog_key_migrator.dart`; kill switch `disable_exlog_migrator_skip_unchanged`, getter `SyncFlags.exlogMigratorSkipUnchangedEnabled`).
In the group loop build `candidate` = `{...base, 'sets', 'set_number', 'weight_kg', 'reps_completed', 'volume_kg'}` exactly as today but WITHOUT `updated_at_ms`. `unchanged = enabled && group.length == 1 && group.first.key == newKey && _sameContent(candidate, base)`; `_sameContent` compares `SyncFingerprint.canonicalJson` of both inside a try/catch that returns `false` and reports the first throw of the run through `ErrorTelemetry.recordNonFatal(reason: 'sync_exlog_migrator_compare')` with the DEFAULT `skipServerPost` (no `_reportSyncFailure` pair exists here, so the H-42 exception does not apply: `error_telemetry.dart:275-277`; a Crashlytics-only report would be silent on web) (a NaN/Infinity weight makes `jsonEncode` throw; today's code never encodes, so a throw here must fall back to the rewrite, not abort the run; a catch that only `debugPrint`s would fail `no_silent_debugprint_in_services_test`). When `unchanged`: no `box.put`, `updated_at_ms` untouched. EVERYTHING ELSE stays byte-identical, including `PendingExlogDeletes.cancelFor` (kept: its arguments come from `base`, so an unchanged canonical row with a queued time-less delete is cancelled exactly as today and the registry/CLAUDE.md `cancelFor` caller rows stay true), the old-key deletes (none exist for an `unchanged` group), the `exercise_log_index_` rebuild and the flag write. Return type stays `Future<void>`. The final log line becomes `rekeyed=… merged=… unchanged=… rewritten=… total_after=…` (no test or script greps the old line; verified with `git grep`). A single rogue-keyed row (`first.key != newKey`) is still re-keyed even when its aggregates agree. The first clause `group.length == 1` is explicit defence: with `.first` a multi-entry group can never satisfy `_sameContent` anyway (a second entry always adds a set), so dropping it is an equivalent mutant (declared in section 7).
**Known residual shapes (disclosed, tested, measured in section 9, ledgered as OI (i))**: a restored row is still rewritten as today, and pushed once, when the migrator's recomputed aggregates differ from what the restore wrote: (1) a timed/cardio row with a cloud NULL `weight_kg`/`reps`: MEASURED in T-R0 case 4, the restore records NO fingerprint for it (`restoredBundleEqualsCloud` is false: the push does not reproduce its metric-less set), so it pushes once with or without the migrator and W1 neither helps nor hurts (the migrator also adds `0.0`/`0` and stamps it); (2) a **summary-only** row with a canonical key and no `sets` (per-set fetch failed `:1006-1015`, or an older account): the migrator synthesizes a set with `logged_at_ms = now` and forces `set_number = 1`, so the candidate can never equal the base, and the following push sends summary `set_number = 1` instead of the cloud's N (pre-existing; SUSPECTED effect on the cloud value, to be inspected in section 9); (3) a cloud summary whose `reps` or `weight_kg` is not what the per-set rows add up to (`restoredBundleEqualsCloud` compares `set_number` but not weight or reps, `exlog_restore_rules.dart:146-153`). Timezone: the migrator parses the IST date string with `DateTime.parse` in local time, so under a UTC offset above +5:30 the computed key can differ and the row is re-keyed as today (pre-existing; tests run under `TZ=Asia/Kolkata`).

**W2 — "row sent" is persisted as the pass goes** (`sync_skip_index.dart`; kill switch `disable_skip_index_incremental_flush`, getter `SyncFlags.skipIndexIncrementalFlushEnabled`, reached through a static `SyncSkipIndex.flushEnabledResolver` that defaults to it and falls back to enabled in Hive-free tests).
New top-level `const kSkipIndexFlushEvery = 25`; new optional named constructor parameter `flushEvery = kSkipIndexFlushEvery` (tests use a small value for compact sequences; every production construction keeps the default). Fields `_pendingConfirm: Map<String,String>`, `_pendingForget: Set<String>`, `_sinceFlush`, `_flushErrorReported`, and a `final bool _flushOn = flushEnabledResolver() && !disabled` read once at construction (switch engaged or `disabled` => nothing is ever recorded as pending and the pass is byte-identical to today).
- `pushIfChanged`, at the point a push is confirmed with `fp != null` (today's `:251-255`) and `_flushOn`: also `_pendingConfirm[rowKey] = fp; _pendingForget.remove(rowKey)`, then `if (++_sinceFlush >= flushEvery) { _sinceFlush = 0; await _flush(); }`. Skipped rows, failed or unconfirmed rows, and `fp == null` confirmations never advance the counter.
- `_forget(rowKey)` additionally `_pendingConfirm.remove(rowKey); _pendingForget.add(rowKey)` when `_flushOn` (it does not flush: the removal is persisted by the next flush or by `commit`).
- `_flush()` returns at once when `_ownerChangedNow()` or both pending collections are empty. Otherwise: `final read = readIndex(...)` (a COPY; the stored object is never mutated), `next = copy of read` minus `_pendingForget` plus `_pendingConfirm`; if `next` differs from `read`, `await _box.put(domain.indexKey, next)` with NO await between the read and the put (same rule as `commit`). On success, or when `next == read` (already persisted), clear both pending collections. On a throw: keep pending, and report ONCE per instance through `ErrorTelemetry.recordNonFatal(reason: 'sync_skip_flush_<domain>')` (never `_reportSyncFailure`: a `sync_`-prefixed op type would be classified as a swept push op by `sync_retry_controller.dart`). It never prunes (`liveKeys` stays in `commit`). `HiveService.workoutBox` is a raw `Box` (no ownership assertion at `put`), so `_ownerChangedNow()` plus the no-await rule is the whole guard, exactly as in `commit`.
- `commit` is unchanged (idempotent over `_confirmed`/`_forgotten`; it still resurrects a mid-pass `clearAll` exactly as today). `_stored` is NOT refreshed from the box by a flush: W2 makes a LATER pass (a retry, the next launch after a kill or reload) resume from the flushed state; it does NOT make two LIVE passes skip each other's rows (OI (a); refreshing `_stored` at flush time is recorded there as the cheapest candidate mitigation).
- Cost: a flush copies and rewrites the whole map, about `n^2/50` entry copies per pass (`n/25` flushes of average size `n/2`): negligible at tester scale (262 exercise rows ≈ 1.3k copies), ~0.5M copies and ~30 MB appended at 5,000 rows. Stated, not hidden.

**W3 — the first sweep waits when the device was EMPTY at its first launch** (`sync_service.dart` + new pure file `lib/core/services/sync/first_sweep_decision.dart`; kill switch `disable_first_sweep_postpone`, getter `SyncFlags.firstSweepPostponeEnabled`). This is a POSTPONEMENT, and says so: the sweep still runs, ≥24 h after the first launch, and re-uploads every domain that has no download-recorded fingerprint (the 15 domains of OI (b)) as one single pass (resumable with W2). What disappears on day 0 is the duplicate: the sweep pushing the workout-side domains at the same time as the migrator-triggered `syncWorkoutData()`, and the sweep re-uploading nutrition/health rows the device just downloaded while the backend is busiest. The founder scope call above names it ("skip the first full sweep on a fresh device").
- State is **durable and keyed by user, nothing in memory**: `syncBox['fresh_device_<userId>']` = ISO-8601 UTC time of the first launch that found the device empty. (`syncBox` is shared across accounts, hence the user id in the key; an explicit sign-out clears the box.)
- Pure (`first_sweep_decision.dart`, standalone library like `sync_skip_index.dart`; no `??` before `DateTime.now()` anywhere in it — Gate G2): `enum SweepAction { none, run, postponeAndStamp }`; `SweepAction decideSweep({required bool due, required bool owed, required bool freshWithinWindow, required bool enabled})` = `none` if `!due`; `postponeAndStamp` iff `due && !owed && freshWithinWindow && enabled`; else `run`. `bool shouldMarkFreshDevice({required bool hasLocalHistory, required DateTime? lastFullSync, required bool markerExists, required bool enabled})` = `enabled && !hasLocalHistory && lastFullSync == null && !markerExists`. `bool isFreshWithinWindow({required DateTime? marker, required DateTime now})` = `marker != null && !marker.isAfter(now) && now.difference(marker) < kFreshDeviceWindow`, `kFreshDeviceWindow = Duration(hours: 1)` (a marker from the future, i.e. a changed device clock, is stale; the window is short on purpose: the only hazard is the launch RIGHT after restore, where two pushers overlap; an hour later the sweep runs alone as a single pass).
- Service: extract `_restoreIfNeeded`'s key loop (`:1553-1560`) into a PURE-READ `bool _hasLocalWorkoutHistory()` (no catch, so `_restoreIfNeeded` keeps today's throw semantics; a `has*` name is covered by the CQRS naming gate, which a pure read satisfies). `Future<void> _markFreshDeviceIfEmpty(String userId)`: no-op unless the kill switch is not engaged, `HiveUserSession.currentOwnerFullId == userId` AND `!ownerChangedSince(userId)` (when the live Supabase uid differs from the Hive owner, `wrapUserScopedBox` serves `GuardedBox.empty` and `_hasLocalWorkoutHistory()` would report a populated box as empty: `guarded_box.dart:243-250`); reads `_getTimestamp(_lastFullSyncKey)`, the marker, `_hasLocalWorkoutHistory()`; when `shouldMarkFreshDevice` is true it does `await _hive.syncBox.put(key, nowUtcIso)` with NO await between the marker read and the put (Hive applies a `put` to its in-memory store before its first await, verified in hive-2.2.3 `box_impl.dart` `_writeFrames`/`keystore.beginTransaction`, so two interleaved callers cannot both write); the whole body in try/catch reporting through `ErrorTelemetry.recordNonFatal(reason: 'sync_fresh_device_mark')` with the default `skipServerPost` (a failure only means "not marked", i.e. today's behaviour). Called **twice, first-wins**: in `checkAndSync` right after `_ensureSessionOpen` (before health sync and before `_restoreIfNeeded`), and in the restore core right after its `openForUser` try-block (before any restore op) with that method's `userId`.
