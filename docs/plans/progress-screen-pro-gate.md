## 3. Design (the decisions)

- **D1 — The screen runs the same gate as the door, on entry.** `_Access { checking, granted, denied }`. `_enter()` calls `SubscriptionService.instance.gateAndVerify(AppConstants.featureProgressPhotos, onPro: ..., onFree: ...)`. `onPro` -> `granted` and `_load()`; `onFree` -> `denied`. Each callback opens with `if (!mounted) return;` (the hub's pattern; for a locally-PRO user the gate awaits the server for up to 10 s, so the screen can be gone by then). `_load()` is called ONLY from `onPro`: a free user triggers no read.
- **D2 — `initState` calls `_enter()` directly (no post-frame deferral).** v1 of this plan deferred the gate with `addPostFrameCallback` on the theory that `isPro()` can fire `onStateChanged` (a Riverpod invalidation, `app.dart:45`) inside the build phase. That theory was wrong: `_downgradeLocally` calls `onStateChanged` only AFTER an awaited Hive write, so it never runs inside the build phase; and `writeSubscriptionState` is reached from verify/purchase flows, not from a synchronous `isPro()`. Round 1 (question 1) re-checked the Flutter sources (`setState` in `initState` is legal) and found no hazard. A locally-free user's `onFree` then runs synchronously inside `initState`, so the first build already shows the locked card (no spinner flash; a test pins it).
- **D3 — The denied state is an inline locked card, not a pop-and-paywall.** The body shows `ProLockedOverlay(featureLabel: 'Progress Photos', description: ..., onUpgradeTap: () => showPaywallSheet(context, feature: 'Progress Photos'), child: <placeholder>)`; no floating button; no photo read. The app bar's back arrow is unchanged.
- **D4 — `checking` reuses the existing spinner**, so a PRO user inside the 5-minute cache sees no change; outside it the same wait the hub row already imposes.
- **D5 — The write action is gated again, and cannot be entered twice.** The Add button's handler runs `gateAndVerify(featureProgressPhotos, onPro: <the picker + capture>, onFree: <denied + paywall>)`. Rule 19's reason is the Storage WRITE; the entry gate does not cover a subscription that lapses while the screen stays open (then `capture` would silently take the free 2/day branch). The cache is a 5-minute cache only after a 200 answer (section 1 item 4), so a tap can wait up to 10 s: `_gating` makes a second tap a no-op and the button shows the busy spinner meanwhile (the existing `_uploading` look).
- **D6 — The door stays.** The hub row's gate is unchanged: a free user still gets the paywall over the hub without ever seeing the locked card. The screen gate is the second, independent lock.
- **D7 — The repository changes by a comment and a test seam only.** The free branch (2/day, 2048/85) stays as a backstop, documented as reachable only if PRO lapses between the Add button's gate and `capture`'s own `isPro()` read. Deleting it is a product call (row C6). The seam, `debugOnListForTests`, is null in production.
- **D8 — Docs repointed in the same commit** (section 1 item 8), plus a short rule in `docs/architecture/subscription.md`: a PRO-only screen gates ITSELF.
- **D9 — Soft-lock mismatch, stated not decided.** `subscription.md` says a downgraded user is "read-only on PRO content". The hub door already blocks a lapsed user from viewing (it did before this change: the old Profile row gated the same way, `git show 7678f783^:lib/features/profile/screens/profile/profile_content.dart`), and the founder's decision is that the screen enforces PRO, so entry is blocked. Consequence to name for the founder: the only in-app way to remove a lapsed user's progress photos is Delete Account (a DPDP point). If the founder wants a lapsed user to VIEW and delete old photos, the entry gate would become a write-only gate: row C7.
- **D10 — Server side is NOT in scope.** A screen check stops honest users and a typed address; it cannot stop a client calling Storage/PostgREST directly (`progress_photos` RLS is own-row only; the bucket policies are not in the repo). The real lock is a database rule: a migration plus a live apply, which needs the founder's separate go (row C5).
- **D11 — A refused user who upgrades gets the gate re-run.** `showPaywallSheet` cannot be awaited, and a purchase flips `subscriptionInfoProvider` (`writeSubscriptionState` -> `onStateChanged` -> `ref.invalidate`). `build` listens (`ref.listen`): when the screen is `denied` and the new value is PRO, it goes back to `checking` and calls `_enter()` (the same server-verified gate, so a spoofed provider cannot grant). Only a LOCKED screen reacts.
- **D12 — The locked card is hardened where this change first uses it.** `ProLockedOverlay`'s text column is centred while it fits and scrolls when it does not (a short window, a landscape phone, 2x text); its CTA is a `Material` + `InkWell` inside `Semantics(button: true)`, 44 dp tall, so a keyboard user on web can focus and activate it. Same look (Wardroom "primary button": accent fill, black w900 text, pill). The widget has no other user, so nothing else moves.
- **D13 — One test seam.** `ProgressPhotoRepository.debugOnListForTests` counts `list()` calls so "a free user triggers no photo read" is proven by behaviour, not only by source pins.
- **D14 — The regression test lives in `test/contracts/` (root section 4.1: a fix lands with its regression test there; round 2, finding 8e).** A first version sat in `test/profile/` beside the hub's behavioural tests; it is a mixed file (pumped-widget behaviour plus comment-stripped source pins), and a contract sweep only reaches `test/contracts/`. Every citation was repointed.
