## 2. Design

**D1 — Two enforcement points, ONE predicate, one migration statement.**
(a) a `BEFORE INSERT … FOR EACH ROW` trigger on `public.progress_photos`;
(b) the Storage `INSERT` policy for the bucket.
Why both: the Storage object is the cost (rule 19's stated reason is "persist private photos onto infrastructure we pay for"), and `capture` uploads FIRST (F6), so only (b) stops the cost; the table row is what the gallery lists and what a direct PostgREST call could forge, and (a) is this repo's established idiom with a distinguishable error (F9). Either alone leaves the other door open. Residuals the rule does NOT close, named so they are not mistaken for closed: (i) a PRO caller's uploads are uncapped on the server (the 5/day cap is client-side only); (ii) a signed upload URL minted while PRO stays usable until it expires (the client does not use signed upload URLs); (iii) an object uploaded whose row insert then fails is an orphan, and the sweeper that should remove it (`cleanupOrphanedStorage`) has zero callers; (iv) **the bucket and its policies were born in the dashboard (F3), so the likeliest future regression, a dashboard edit of `progress_photos_insert_own` or a new unscoped policy, is invisible to every repo pin; the live-verify catches it once and nothing recurring does (the OI-283 class)**; (v) the out-of-repo Telegram bot (F6). (i), (iii) and (iv) are filed as OIs by B0 (section 5), (v) is a ledger row owned by the founder.

**D2 — INSERT-only, stated and pinned ACROSS ALL MIGRATIONS.** SELECT, DELETE and UPDATE policies on both `public.progress_photos` and `storage.objects` are NOT touched, because decision 6 says a lapsed user may view and delete. The migration alters exactly one policy on `storage.objects` and one on nothing else; the tripwire (D3b) fails on ANY later statement that creates, alters, drops or renames a policy of these two objects' progress-photo set, including a narrowing one such as `USING (false)` (round 2, finding 4e: the v2 pin only flagged policies that carried a PRO condition).

**D3 — The predicate is COPIED, not wrapped in a helper.** `EXISTS (SELECT 1 FROM public.subscriptions … WHERE user_id = <uid> AND status = 'active' AND end_date > now())`. `<uid>` is `NEW.user_id` in the trigger and `(SELECT auth.uid())` in the policy. A SECURITY DEFINER helper taking a user id would let any signed-in caller read any user's PRO state over RPC (class 2.32), a no-argument helper cannot serve the trigger, and a SECURITY INVOKER helper adds a function without removing a copy. The cost is more copies of the predicate; the tests pin each copy as a WHOLE normalised expression (D3a) and against `verify-subscription`'s predicate (the writer/reader drift between the client's gate and the server's rule is the repo's default suspect class).

**D3a — Pins compare WHOLE normalised expressions, never clauses (round 2, finding 1, P1).** v2 asserted that the function body "contains, in order" `IF NOT EXISTS (`, `user_id = NEW.user_id`, `status = 'active'`, `end_date > now()`, … and that the policy's `WITH CHECK` contains its conjuncts. Changing an `AND` to `OR` keeps every clause and the order, so those pins pass. The Storage-policy form is the dangerous one: `(bucket AND own-folder) OR EXISTS(active subscription)` makes any PRO user able to INSERT into any bucket under any user's folder, which widens access. The agent's own memory carries this class (`feedback_compound_boolean_connective_mutation_target.md`). So: the test extracts (a) the complete `CREATE OR REPLACE FUNCTION` statement including its header and body, (b) the complete `CREATE TRIGGER` statement, (c) the complete `WITH CHECK ( … )` expression of BOTH the `ALTER POLICY` and the `CREATE POLICY` branch (balanced-parenthesis extraction), normalises each (strip `--` and `/* … */` comments with a string-literal-aware stripper, collapse whitespace, trim spaces inside parentheses) and requires EQUALITY with an expected literal held in the test. Any change inside them, a connective swap, an exception swallow, an early `RETURN NEW`, an `AND false` guard, a dropped conjunct, reddens, and no reviewer has to think of the mutation. The expected literals are written independently in the test (not generated from the migration), and the predicate piece is additionally cross-checked against `verify-subscription` (E3).

**D3b — The later-migration tripwire replaces v2's effective-state resolver (round 2, findings 4 and 11).** v2 tried to model the effective state of each object across migrations; round 2 listed five ways that model is blind (a default-ALL policy with no `FOR` clause, `DROP FUNCTION … CASCADE`, `RENAME` then drop, `REVOKE ALL`, role or `USING` narrowing, a RESTRICTIVE policy). Chasing statement kinds is the "Nth wider guess" class (2.53). The design that does not depend on guessing the next mutation: **any file newer than this migration that touches the protected set at all fails the test until it is acknowledged in an allow-list in the test (file name → reason), and acknowledging forces a human to re-verify the rule.** The allow-list is EMPTY at B1. The protected set P (matched on the comment-stripped text, deliberately wide):
1. any mention of `trg_progress_photo_pro` or `enforce_progress_photo_pro`;
2. any `CREATE|ALTER|DROP POLICY` naming `progress_photos_insert_own|progress_photos_select_own|progress_photos_delete_own|progress_photos_update_own`, and any `ALTER|DROP|CREATE POLICY … ON storage.objects` at all (an `ALTER`/`DROP` carries no bucket text to inspect, so all are flagged, and a policy on `storage.objects` without a `FOR` clause is the default-ALL case);
3. any `ALTER TABLE storage.objects`, and any statement on `public.progress_photos` that is `DROP TABLE`, `ALTER TABLE … (RENAME|DISABLE TRIGGER|ENABLE|DISABLE ROW LEVEL SECURITY|FORCE ROW LEVEL SECURITY|DROP COLUMN|ALTER COLUMN)` or `ALTER TRIGGER`;
4. on `public.subscriptions`: any `CREATE|ALTER|DROP POLICY`, any `REVOKE` or `GRANT`, `DROP TABLE`, and `ALTER TABLE … (RENAME|DROP COLUMN|ALTER COLUMN|ROW LEVEL SECURITY|SET SCHEMA|OWNER)`;
5. any `DROP (FUNCTION|TABLE|COLUMN|TRIGGER|POLICY|SCHEMA)` carrying `CASCADE`, because a cascade can silently delete the trigger or the policy that depends on the dropped object.
**File set and order (finding 11):** the files are `supabase/migrations/*.sql` filtered with the same rule as `numberedMigrations()` in `test/helpers/cron_job_body_reader.dart:22-31` (`^(\d{3})[a-z]?_.*\.sql$`), plus `docs/drafts/*.sql`, sorted by (number, file name) with an explicit tie-break (two files share number 146 and Dart's sort is not stable). "Newer" means number greater than this migration's. `all_migrations_combined.sql` (it re-creates the subscriptions write policies at `:622-625` and is never applied) and the three timestamp-named files are an explicit unnumbered-baseline list; a NEW `.sql` file that is neither numbered nor in that list fails (so a timestamp-named file cannot dodge "newer"). The tripwire's honesty: it proves nothing about a later migration's correctness, it forces the review the plan relies on.

**D4 — ONE statement: the whole migration is a single `DO` block (new in v3; round 2 finding 16 and the unverified-atomicity fact F11).** `apply_migration` may or may not wrap a file in a transaction; a `DO` block is one statement, so every change inside it commits or rolls back together whatever the applier does, and a failure at any step leaves the database exactly as it was. The order inside it is chosen so that even a partial result would fail safe: **(1) the Storage policy first, (2) the function, (3) the trigger, (4) the `subscriptions` self-grant drop.** The lock budget is set inside the block with `PERFORM set_config('lock_timeout', '5s', true)` (transaction-local, so nothing leaks to a pooled session and no `RESET` is needed; a lock wait longer than 5 s aborts the whole block and nothing is applied, a re-run is idempotent).

```sql
DO $mig$
BEGIN
  PERFORM set_config('lock_timeout', '5s', true);

  -- (1) the cost gate: the Storage INSERT policy, altered IN PLACE (keeps name, roles,
  --     command and PERMISSIVE flag). The ELSE branch exists for a fresh database only (F3).
  IF EXISTS (SELECT 1 FROM pg_policies
             WHERE schemaname = 'storage' AND tablename = 'objects'
               AND policyname = 'progress_photos_insert_own') THEN
    ALTER POLICY "progress_photos_insert_own" ON storage.objects
      WITH CHECK ( <EXPR> );
  ELSE
    CREATE POLICY "progress_photos_insert_own" ON storage.objects
      FOR INSERT TO authenticated
      WITH CHECK ( <EXPR> );
  END IF;

  -- (2) the trigger function (invoker rights, pinned search path)
  CREATE OR REPLACE FUNCTION public.enforce_progress_photo_pro()
  RETURNS trigger LANGUAGE plpgsql SET search_path = public, pg_temp AS $fn$
  BEGIN
    IF NOT EXISTS (
      SELECT 1 FROM public.subscriptions
      WHERE user_id = NEW.user_id
        AND status = 'active'
        AND end_date > now()
    ) THEN
      RAISE EXCEPTION 'progress_photo_pro_required' USING ERRCODE = 'P0001';
    END IF;
    RETURN NEW;
  END;
  $fn$;

  -- (3) the row-level door
  DROP TRIGGER IF EXISTS trg_progress_photo_pro ON public.progress_photos;
  CREATE TRIGGER trg_progress_photo_pro
    BEFORE INSERT ON public.progress_photos
    FOR EACH ROW EXECUTE FUNCTION public.enforce_progress_photo_pro();

  -- (4) close the repo's own self-grant path (D12): a no-op live (E21), idempotent
  DROP POLICY IF EXISTS "users_own_subscriptions" ON public.subscriptions;
END
$mig$;
```

`<EXPR>` is, identically in both branches: `bucket_id = 'progress-photos' AND (storage.foldername(name))[1] = (SELECT auth.uid())::text AND EXISTS (SELECT 1 FROM public.subscriptions s WHERE s.user_id = (SELECT auth.uid()) AND s.status = 'active' AND s.end_date > now())`. The first two conjuncts are the live policy's, unchanged apart from the `(SELECT …)` wrap (migration 100's initplan idiom). A `BEFORE` trigger fires before the row's RLS `WITH CHECK`, so a row with ANOTHER user's id is refused here too, for a PAYER as well as a free user (the trigger reads the OTHER user's subscriptions under the CALLER's RLS and sees none: `P0001` where the table's own-row policy gave `42501` before the rule; live-verify V3f pins that it is never accepted). NOT NULL is checked after BEFORE triggers, so a NULL `user_id` raises the P0001 first, which is harmless. `SECURITY INVOKER` like F9; `SET search_path = public, pg_temp` is kept although F9's three do not carry one (it closes schema shadowing and the mutable-search-path advisory). The `has_function_privilege` check that `supabase/migrations/CLAUDE.md:185` requires after a new public function is inert for a function that returns `trigger` (it cannot be called over RPC); the diagnose-doc says so instead of skipping it. The migration text never needs the two-word definer phrase because no definer function is added (the tier no longer depends on that, D-tier above).

**D5 — The apply-role risk, stated and bounded (finding 8 / Q2 and E18, E23).** Whether the session that `apply_migration` uses may `ALTER POLICY` on `storage.objects` (owner `supabase_storage_admin`; `postgres` is NOT a member, E18) is evidenced only by migration 116 having CREATED a policy there through the MCP path (E23); ALTER has no precedent. **A founder-authorised always-aborting dry run decides it before the real apply:** the exact bytes of the `DO` block with ONE extra final statement `RAISE EXCEPTION 'dry_run_rollback';` before `END`, run through `execute_sql` (a `DO` block's own exception undoes every statement inside it whatever the surrounding transaction handling is; this is the technique of migration 152's prod dry run, recorded in `docs/diagnoses/2026-09-29-subscription-mirror-columns-dropped-c7e3b9.md` tier 3 and specified in `docs/plans/oi-182-202-subscription-state.md:90`, which also records why an explicit `BEGIN … ROLLBACK` is NOT used for a live dry run: on a mid-message error through `execute_sql` the trailing `ROLLBACK` is skipped and the aborted session keeps the locks already taken, here ACCESS EXCLUSIVE on `storage.objects` and `public.subscriptions`). Expected result: SQLSTATE `P0001`, message `dry_run_rollback`, which proves every earlier statement executed without a privilege or syntax error; any other error is the finding.
