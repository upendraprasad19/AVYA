## 2. Design (the decisions)

**D1 — one row.** The REPORTS card's last two rows become ONE row: `title: 'Photos'`, `subtitle: 'Progress timeline and photos saved from AI Coach'` (D10), `icon: photo_library_outlined`, `onTap: context.go('/profile/photos')`. `go` matches the other REPORTS rows (Progress Comparison, Weekly Report); other Profile rows use `push` (Notifications → `/profile/notification-settings`, AVYA's Promise → `/avya/promise`, `danger_zone.dart` → `/profile/delete-account`) or `Navigator.of(context).push` (Credits & Licences) — v1 wrongly said "every other row uses go" (R1-05; round 2 caught that the line numbers cited for these in v2 were wrong, so they are now cited by row). The row is not gated.
**D2 — the hub.** New `lib/features/profile/screens/user_photos_screen.dart`, `UserPhotosScreen extends ConsumerWidget`: AppBar header like the sibling sub-screens (eyebrow `DOSSIER · ARCHIVE` in `AppTypography.monoXs` gold, title `Photos` `AppTypography.h3`), one `WardCard` with two `ProfileRow`s:
  - **Progress** (`timeline_outlined`): `gateAndVerify(AppConstants.featureProgressPhotos, onPro: push('/profile/progress-photos'), onFree: showPaywallSheet(feature: 'Progress Photos'))` — the call the old row made, with `push` instead of `go` and a `context.mounted` check in each callback (D9).
  - **Saved** (`bookmark_border`): `push('/profile/saved-coach-photos')`, ungated, subtitle `Photos you saved from AI Coach chat` (the old row's).
  The hub only routes; each destination keeps its own bucket and delete behaviour. **The PRO check is NOT in the destinations:** the Progress row's `gateAndVerify` is the ONLY gate on the way to `ProgressPhotosScreen` (the screen does not check the subscription itself; its one paywall is the daily-cap one), and Saved is ungated by design — v3 wrote "each destination keeps its own gate", which B-pass B showed is the sentence that invites a second, ungated way in (D14). It is static: no loading / error / empty states exist to handle (§4.4 rule 13); the destinations keep theirs.
**D3 — keep the PRO hint (a decision, not in the founder's words).** The old Profile row told a free user `PRO — visual progress timeline`. Folding the row behind a hub would drop that hint, so the hub's Progress subtitle keeps the old two strings, read display-only with `ref.watch(subscriptionInfoProvider).isPro` — the pattern `lib/CLAUDE.md` pitfall row 2 and the `subscription_state` concept in `docs/sot_registry.yaml` (its display-only reader rows) name. It is not a gate (round 1 Q2: consistent with rule 5). **Known trade-off:** a free user now needs one extra tap (Photos) before seeing the hint or the paywall.
**D4 — navigation.** Profile → hub with `go`, hub → destinations with `push`, so the back arrow returns to the hub, then to Profile. The destination routes stay registered at their existing paths and names (no deep link or bookmark breaks). Evidence for push-inside-the-shell (round 1 Q1, go_router 17.2.3 source): `RouteMatchList.push` inserts the imperative match into the existing shell match, so the page is built by the branch navigator inside `_MainShell` with the NavigationBar shown; the shell's `PopScope(canPop: matches.length == 1)` keeps system back inside the branch; production precedent for the same push-into-this-branch: `danger_zone.dart:26` and the Notifications row's `context.push` in `profile_content.dart`. On web (hash strategy, `optionURLReflectsImperativeAPIs` default false) the URL bar stays `#/profile/photos` while a pushed destination shows, each push is its own history entry, and a reload on a pushed destination lands on the hub.
**D5 — route.** `GoRoute(path: 'photos', name: 'userPhotos', builder: (context, state) => const UserPhotosScreen())` as a sub-route of `/profile`, in the same `routes:` list as `progress-photos` and `saved-coach-photos`, so the bottom navigation shell stays visible.
**D6 — SHARE & GROW.** The whole block (header + card) moves to sit after the AVYA block and before SUBSCRIPTION: new order REPORTS, SETTINGS, AVYA, SHARE & GROW, SUBSCRIPTION. No row is added, removed or edited; the code is byte-identical (rounds 1 and 2 each diffed the base block, `377-477`, against the moved block: the only difference is its header comment, 3 lines → 4). **One deliberate edit inside the block:** its leading comment said "Health Sync row added into SETTINGS (see below)", which is wrong once SETTINGS is above — reworded (comment only, D11).
**D7 — what does NOT change.** No Hive key, cloud column, Edge Function, migration, feature constant, gate semantics, destination screen (one doc comment aside, D11), or plan-generator file; the only deletion is the dead `ProgressPhotosCard` chain (D13). No new analytics event. No feature flag.
**D8 — docs and glossary (each marked required by a rule or judgment).** `lib/features/profile/CLAUDE.md` (screens list: the hub + the profile bullet; the "Tests pinning the rules here" list; *required*, §5 nested-CLAUDE.md row) · `docs/architecture/functionality-flow.md` PROF-01 and PROF-09 (the entry path, the order, the new verify pointers; *required*, the charter must match the screen) · `docs/architecture/ai-coach-detail.md` (the Unit 8 test list names the router test; *required*) · `docs/naming_conventions.md` glossary row **Photos hub** (§4.7: a new domain term; *required*) · `docs/sot_registry.yaml` (the `postSessionRedirect` reader range `800-811` → `808-819`, the router moved +8 lines above it; *required*, `check_sot_registry_parity.dart` fails otherwise — round 1 R1-05c found v1's D8 omitted it; plus a display-only reader row for the hub under `subscription_state`, round 2 R2-05, root §4.5; plus the deleted card's allow-list line, D13) · `testing/web_test_plan.md` row 6.5 (the manual path now goes through the hub; *judgment*) · the closure ledger, this plan, the plan-review record, the B-pass review file (*required*, §4.2 / §4.12 / §5.1).
**D9 — hub robustness (round 1 R1-08; reworded by the B-pass).** For a user who is PRO LOCALLY, `gateAndVerify` awaits a server verify (up to 10 s) before it calls either callback for this high-value feature; a locally-FREE user gets `onFree` synchronously inside the tap, and `onFree` also runs after the await when the server disagrees with the local PRO flag (`verify_failed`). The user can leave the hub in that window, and `context.push` / `showPaywallSheet` on a dead context would throw and be reported only as `subscription_gate_callback_threw`. Both callbacks start with `if (!context.mounted) return;`. Proof: `onPro` at runtime (the gate test unmounts the hub inside the verify), both by a position-aware source pin (the callback OPENS with the guard; a count of guards could not tell a guard after the push from one on another row). `onFree` has no runtime proof — no unit test can make the server disagree. Accepted, documented in the hub: (a) a double tap stacks two destination pages (`go` was idempotent; like every other `push` row; the destinations are read-only views on open); (b) the guard asks "still mounted", not "still on top", so a user who taps Saved while the verify is pending gets Progress pushed above Saved (back returns to Saved, then the hub); (c) the gate logs `exit=onPro` before it runs the callback, so a push the guard drops still reads as a routed user in telemetry.
**D10 — copy, icon, eyebrow (round 1 R1-09; Wardroom soul checked, `lib/shared/widgets/wardroom/CLAUDE.md` has no voice rule for these).** Row subtitle `Progress and saved from AI Coach` parsed as "[Progress] and [saved from AI Coach]" → `Progress timeline and photos saved from AI Coach`. The hub's Progress row used the same icon as the Profile umbrella row → `timeline_outlined` (the Profile row keeps `photo_library_outlined`, the icon the old Progress row had at that spot). The eyebrow repeated the title (`DOSSIER · PHOTOS` over `Photos`) while siblings use a flavour word (`PLATES`, `COACH LOG`) → `DOSSIER · ARCHIVE`.
**D11 — stale text the move left behind (round 1 R1-02/03/07).** Reworded in this commit: `profile_content.dart` REPORTS comment ("still PRO-gated at tap" was false: the gate now lives in the hub) and the Plan-D line naming "Progress Photos"; the SHARE & GROW header comment (D6); `progress_photos_screen.dart:14` ("see `ProgressPhotosCard` + profile menu" — the card has no references; the entry is now the hub); the reason string in `profile_screen_layout_test.dart`. **D13 — dead code beside the moved row, deleted (round 1 R1-12 and round 2 R2-09 both found it).** `lib/features/profile/widgets/progress_photos_card.dart` (235 lines), `ProgressPhotosData` / `ProgressPhotosNotifier` / `progressPhotosProvider` in `profile_provider.dart`, the one `ref.invalidate(progressPhotosProvider)` in the Profile screen's `invalidateOnRetry`, and the card's allow-list line in `docs/sot_registry.yaml` had no reader at the base or now (`git grep` of every name: only the files themselves, two dated historical records — `docs/diagnoses/2026-05-12-cross-account-riverpod-cache-c4055a.md` and `docs/superpowers/plans/2026-05-12-apk-test-15-3-cross-account-plan.md`, both left as written — and the stale comment D11 rewrote). The Hive key the provider read, `progress_photo_count`, has NO writer anywhere and stays in `user_config_migrator.dart`'s key list and its test, which this batch does not touch. §4.2 forbids parking a surfaced finding behind a founder question when the fix is mechanical.
**D14 — one gate, many possible doors (B-pass B, P1).** `ProgressPhotosScreen` has no PRO check of its own, exactly as at the base, where the Profile row was the only gate and the route was open by URL (ledger row R1-04, a founder decision).
