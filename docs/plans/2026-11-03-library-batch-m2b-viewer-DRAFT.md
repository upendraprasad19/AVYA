## Why the route is not opaque (the round-1 P0)

`MaterialPageRoute` is opaque. Under an opaque top entry the overlay builds covered entries with `tickerEnabled: false` (`flutter/lib/src/widgets/overlay.dart:877-885`, wrapped in a `TickerMode` at `:419-420`), and flutter_riverpod 3.3.1 PAUSES every `ref.watch` subscription of a `ConsumerStatefulElement` while `TickerMode` is off (`flutter_riverpod-3.3.1/lib/src/core/consumer.dart:390-413`; OI-378 `docs/audit/open_issues.md:6444` records the same pause and an upstream debug assertion on resume). `ActiveWorkoutScreen` and `_ExerciseCard` are both consumers, so under an opaque viewer neither would rebuild: the viewer's `+` would change the provider and no row would appear (`didUpdateWidget` is the only place the controller lists resize, `exercise_card.dart:335`), and every card method that reads `widget.data` would read a stale snapshot. So the viewer route is a `PageRouteBuilder<void>(opaque: false, maintainState: true)` (precedent: `lib/features/profile/widgets/profile_identity.dart:56`): the covered screen stays live, its tickers stay on. A non-opaque route also means: only the viewer's own `Scaffold` paints a background (so the `Scaffold` is the ROOT of the viewer and the `SafeArea` goes INSIDE its body: a `SafeArea` above it would leave transparent status-bar and gesture-bar strips through which the covered header and the shell's bottom bar show and take taps), the viewer wraps itself in `BlockSemantics` (a non-opaque route does not hide the covered semantics), the covered tile must not keep playing (the viewer is on the ROOT navigator, which does not flip the branch route's `isCurrent`, so Part A's `ModalRoute` freeze does not see it: this part adds `_viewerOpen`), the covered `ListView` can drop a card that falls outside viewport + cache when the keyboard shrinks it (the card holds a keep-alive), and the route goes on the ROOT navigator so it covers the shell's bottom bar.

## Review Focus

1. **Two fields, one controller.** Framework fact (verified): `onChanged` fires only in the field that received the input, the sibling only rebuilds. So the tests assert the OBSERVABLE result (the card's box shows the viewer's text, the mirror fills sets 2 and 3, `setInputValues` / `suggestedInputs` are right), never "fires once" (a second call is invisible: `_mirrorFrom` skips unchanged text, `recordCardEdit` returns before `state =`).
2. **Liveness under the viewer** (the P0): `+` / `-` through the REAL pushed route show the new row, the stepper digit and the `LOG n SETS ✓` label, and keep the card's controller count equal to the data. The viewer is shallower than the card, so `BuildOwner` rebuilds it FIRST with the new count and the old controller list.
3. **LOG and back for a card that is not focused** (D9): the viewer opened from a collapsed card focuses it; LOG logs THAT exercise and pops once, only when the outcome is `LogOutcomeKind.logged`; back pops without logging and leaves the card open.
4. **States the viewer opens in:** move mode and superset-grouping mode (no door), review mode (`data.isSaved`: LOG disabled), the LOG flag off (no rows), a row whose file is not on the phone (the still stays), the exercise swapped / removed under the open viewer (it pops), the card or screen DISPOSED under the open viewer (web browser Back, a redirect), the keyboard up on a 640 dp phone with a notch, a 1200 dp web window, a 40-character name at 320 dp.
5. **The viewer is a second host of the LOG path:** LOGGED inside the viewer re-opens in place (no pop); a dead card is inert.
