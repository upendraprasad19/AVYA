## 2. Design

The referrer's reward is computed by a database job from rows that already exist. No payment function is edited, no trigger is placed on `subscriptions`, and referral logic cannot block or roll back a friend's payment write. (What DOES change: the job updates a paying referrer's `end_date` when it credits them, exactly as 158's redemption did.)

### 2.1 Unit S1 (server): one migration, its tests, its docs

**Migration conventions.** Header tags `Intent`, `Destructive?: no` (three nullable columns, two CHECKs, two functions, one function body replaced, one cron job; no row rewritten), `Rollback strategy: inline` (a commented block: unschedule the job, drop the two private functions, restore the 158 body verbatim, drop the CHECKs and columns), `Linked diagnose-doc: n/a`. The DDL runs inside `SET lock_timeout = '3s'` ... `RESET lock_timeout` (the convention of 152/157/158; `ADD COLUMN` and `ADD CONSTRAINT` take ACCESS EXCLUSIVE on `referral_redemptions`). The file is idempotent so a half-applied recovery is a re-run: `ADD COLUMN IF NOT EXISTS`; each CHECK is `DROP CONSTRAINT IF EXISTS` then `ADD CONSTRAINT` in one `ALTER TABLE`.

**New columns on `referral_redemptions`** (nullable): `converted_at timestamptz` (the qualifying payment's `start_date`; set means "the friend subscribed", pending until credited), `referrer_reward_days integer`, `referrer_credited_at timestamptz`; `CHECK (referrer_reward_days IS NULL OR referrer_reward_days IN (7, 30))` and `CHECK ((converted_at IS NULL) = (referrer_reward_days IS NULL))`. There is deliberately NO payment-id column: the SELECT policy shows a row to its referrer, and a referee's Razorpay payment id must not become readable by the referrer. What each party can read from the new columns (both can, through the existing policy) is the product's intent: that a friend subscribed, roughly when, and (7 vs 30) which plan. `referrer_rewarded` is KEPT and its MEANING CHANGES from "credited at redemption under the cap" (158) to "the reward has been credited" (true only after the job credits). Rows created under live 158 between its apply (2026-10-11) and this apply hold `referrer_rewarded = true` when they were credited at redemption; the job excludes them, correctly, and Unit C must tolerate `referrer_rewarded` true with `referrer_reward_days` NULL. The column is nullable, so every test of it in the job is `IS NOT TRUE` / `IS TRUE`, never `NOT referrer_rewarded` (which hides a NULL row).

**`private.grant_referral_days(p_user_id uuid, p_days integer)`** - the ONE implementation of "extend a user's PRO by N days". Rejects `p_days` outside 1..30. It reads the user's latest `status = 'active'` row (`ORDER BY end_date DESC, id LIMIT 1`) with `FOR UPDATE NOWAIT`; if there is none, or its `end_date` is in the past, it INSERTs a `referral_trial` row (`start_date` now, `end_date` now + N days); otherwise `UPDATE subscriptions SET end_date = end_date + N days WHERE id = <that row>`. No retry loop and no compare-and-set: every grant to a user is serialised by the per-user advisory lock (below) and by the row lock, and no Edge Function updates `subscriptions`, so a lost update could only come from a hand edit. A row locked by someone else raises `55P03` at once. `SECURITY DEFINER`, `SET search_path TO 'public'`, schema `private`, EXECUTE revoked from PUBLIC, anon, authenticated, and verified live after the apply. A payment INSERTed between the read and the update can leave the extended row below the new maximum (days wasted for that grant); that window exists in 038 and 158 and is stated, not closed.

**`public.redeem_referral_atomic(p_code, p_referrer_id, p_referee_id, p_days)`** - same signature, RETURNS void, SECURITY DEFINER, `SET search_path`, ACL service_role only (re-asserted). Body: NULL guard (23502); ONE blocking advisory lock, the REFEREE's key (`hashtextextended('redeem_referral_atomic:' || id, 0)`); refuse with `RAISE EXCEPTION 'referee_has_paid_plan' USING ERRCODE = 'P0001'` when the referee has EVER had a paid row (`plan IN ('monthly','yearly') AND razorpay_payment_id IS NOT NULL`, any status); INSERT the audit row (`referrer_rewarded = false`, `referee_rewarded = true`); `private.grant_referral_days(p_referee_id, p_days)`. The referrer is NOT credited. This function CAN wait: for a running job that holds the same user's key (bounded by the run, seconds), and its INSERTs can queue behind an uncommitted deletion of the referee (then fail the foreign key); a `55P03` or foreign-key error surfaces as the Edge Function's generic 500, nothing is written, the client may retry. The 158 count, the cap constants and the two-lock ordering are removed.

**`private.process_referral_conversions() RETURNS jsonb`** - the only writer of the reward. SECURITY DEFINER, `SET search_path`, schema `private`. Constants: window 90 days, vest 7 days, detection scan 97 days (the window plus a 7-day outage grace). The JOB never waits for a lock: `pg_try_advisory_xact_lock`, `FOR UPDATE SKIP LOCKED`, `NOWAIT` on the helper's row and on the users-row pre-check below (the redeem function above may wait; the job does not). One run, one transaction:
0. **Stall watch (added after the B-pass, 2026-10-13).** FIRST, before the job lock: count the redemptions with `converted_at <= now() - 10 days` that are still `referrer_rewarded IS NOT TRUE` with a referrer, and write one `referral_conversions_stalled` warn alert (23-hour dedup) when there are any. It runs before the lock because a returned `{skipped}` run is a `succeeded` row that migration 146 cannot see, so a forgotten session holding the job lock would otherwise stall every reward silently.
1. `pg_try_advisory_xact_lock` on a fixed key: an overlapping run returns `{"skipped":"locked"}` at once.
2. **Reconcile.** Candidates in their own `MATERIALIZED` CTE: redemptions with `referrer_id` non-NULL and `referrer_rewarded IS NOT TRUE` and either `created_at > now() - 97 days` (in the scan; the operator is strict `>`) or `converted_at IS NOT NULL` (already pending, re-checked until credited), locked with `FOR UPDATE OF <redemptions> SKIP LOCKED`. A SECOND CTE joins each candidate to a `LEFT JOIN LATERAL` that returns the referee's EARLIEST qualifying payment (`plan IN ('monthly','yearly')`, `razorpay_payment_id IS NOT NULL`, `status = 'active'`, `cancelled_at IS NULL`, `start_date >= redemption.created_at`, `start_date <= redemption.created_at + 90 days`; order by `start_date, id`; the payment rows are read, never locked). ONE `UPDATE ... FROM` sets `converted_at = payment.start_date` and `referrer_reward_days = CASE payment.plan WHEN 'yearly' THEN 30 WHEN 'monthly' THEN 7 END` (NO `ELSE`: an absent payment yields NULL for both, which the coherence CHECK requires), guarded by `IS DISTINCT FROM` on both columns, so a steady state changes no column value (it still stamps a row lock on the in-scan rows each hour; the table is tiny). A NULL `referee_id` matches no payment, so a row whose referee was deleted is voided here (its payment row cascaded away). A payment cancelled before the vest voids the row; a later qualifying payment re-arms it with a fresh vest. A credited row is never touched. Rows beyond the 97-day scan that were never converted (the three legacy rows) are never touched.
3. **Credit.** Pending rows (`converted_at <= now() - 7 days`, `referrer_id` non-NULL, `referrer_rewarded IS NOT TRUE`), oldest first, `LIMIT c_batch` (50 per run: each sub-block takes a subtransaction id and every lock of the run lives to its end; a backlog clears 50 an hour), `FOR UPDATE SKIP LOCKED`, each in its own sub-block, in this order: (a) `pg_try_advisory_xact_lock` on the REFERRER's key (same key scheme as the redeem function; a miss counts `skipped_locked`); (b) `PERFORM 1 FROM public.users WHERE id = <referrer> FOR KEY SHARE NOWAIT` (a `55P03` counts `skipped_locked`; NOT FOUND skips the row, the referrer is gone) so the foreign-key check of a later INSERT can never queue behind an account deletion (measured, section 1); (c) `grant_referral_days(referrer, reward_days)`; (d) `UPDATE ... SET referrer_rewarded = true, referrer_credited_at = now() WHERE id = <row> AND referrer_rewarded IS NOT TRUE` and a `ROW_COUNT = 1` check that RAISES otherwise (so the grant of (c) rolls back). `55P03` anywhere counts `skipped_locked`; any other error rolls that sub-block back, counts `failed` and remembers the row id; the row stays pending for the next hour. Holding the users-row key share until the end of the run makes a `delete-account` for that referrer queue behind the run (seconds), not the reverse.
4. **Alerts** (THREE sources: failed, stalled, volume; the volume alert's `context_json` also carries the 24-hour redemption count and the largest per-referrer count) into `public.alerts` (`source, severity, summary, context_json, suggested_action`; severity `warn`, which the digest reads and the critical-only Telegram trigger ignores), each INSERT in its OWN sub-block (an alert that cannot be written must never roll back the credits), each with its OWN `source`, and each deduplicated the way migration 145 does (`145:101-114`): an open, unacknowledged alert of the same source from the last 23 hours suppresses a new one. `referral_conversions_failed` when `failed > 0` (the redemption ids in `context_json`); `referral_conversions_volume` when more than 10 credits happen in one run or more than 20 redemptions were created in the last 24 h. The volume thresholds are Phase-1 placeholders (3 redemptions ever, no baseline), entered in `alerts/_thresholds.yaml` like migration 139's.
5. Returns `{reconciled, voided, credited, failed, skipped_locked}` (pg_cron does not store the return value; the alerts are the observable). An UNEXPECTED error propagates, the run is recorded failed and migration 145 pages.

A referrer whose account is deleted leaves rows with `referrer_id` NULL: excluded from reconcile and credit and terminal by absence (the referee can still read their own row; nothing acts on it). Residuals, stated: a cancel that commits between the reconcile and the credit of the same run is missed (seconds); a cancel after the vest has no clawback (`chargeback`, section 6); a row deferred by a lock held for hours would stay pending with no alert (Unit C's summary shows it as pending); a `redeem_referral_atomic` call can wait for a running job.

**Cron**: `SELECT cron.unschedule(jobid) FROM cron.job WHERE jobname = 'referral_conversions_hourly';` then `SELECT cron.schedule('referral_conversions_hourly', '41 * * * *', $$SELECT private.process_referral_conversions()$$);`. The unschedule is by jobid, NOT by a quoted name: Gate 31 (`check_cron_registry.dart`) reads a quoted-name unschedule as "this job is gone" (OI-193; migration 145 `:48-50`). Minute 41 is free. Registered in `docs/operations/CRON_REGISTRY.md`; `backups/live_cron_jobs.json` regenerated in the same commit (the gate's second input). The paid-plan list `('monthly','yearly')` appears in the redeem function and the reconcile; a source pin asserts every occurrence in the migration is identical. The job is live from the first `:41` after the apply: apply right after a `:41` tick and run the live verify inside that hour; with no qualifying row in the table today (the three legacy rows are out of scan) a premature run credits nothing.

**Section 4.6 / `feature_flag` position (catastrophic tier, recorded after the B-pass and the hermes pass).** There is no runtime flag, on purpose: the redeem change is a refusal plus the removal of a credit, and a flag inside a SECURITY DEFINER function would be a second code path whose "off" state is the abuse this batch closes. The switches that exist are (1) the reward job: `UPDATE cron.job SET active = false WHERE jobname = 'referral_conversions_hourly'` (pending rewards stay and keep vesting; migration 146 re-surfaces a switched-off job weekly), and (2) the inline rollback block, which restores the 158 body byte for byte (verified on a fresh replica) and tells the operator to list pending rewards first because dropping the columns loses them.

### 2.3 Unit C (client) - after S1 is merged AND applied (it reads the new columns)
