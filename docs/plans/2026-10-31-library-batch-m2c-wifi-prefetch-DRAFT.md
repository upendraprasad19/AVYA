## Findings from M2a review round 4 that apply here (all must be satisfied by the real plan)

Verified by the coordinator against the plan text; the reviewers' line numbers refer to M2a r4.

1. **The 10-minute spacing DROPS events instead of deferring them** (4B-1, 4A-2). Wi-Fi up, run starts at t=0, drops at 2 min (`aborted=wifi`), returns at 5 min: `becameAllowed` fires inside the spacing and nothing re-arms, so C6 "resumed when it returns" is not met. The background-restore tick about 20 s after the Train tab first builds is swallowed the same way, leaving the pin on the pre-restore window. Fix: trailing-edge deferral (a pending flag plus a timer cancelled on dispose), with a test that a blocked event runs once the spacing elapses.
2. **No test seam for the trigger** (4A-1, 4B-2). Extract the logic out of `_TrainScreenState` into a class (`PlanWindowPrefetchTrigger`: injectable clock, gate, runner, schedule reader) with its own tests and mutations: spacing, in-flight flag reset in `finally` (a runner that throws after `setPlanWindow` must not wedge later runs), subscription cancelled on dispose, no `ref.read` after dispose. The State takes its gate and repository from overridable providers (for example `prefetchGateProvider`), because a real `Connectivity` stream in a widget test reports to `FlutterError.reportError`. Add ONE widget test with a media-row window and a fake gate and repository that asserts `setPlanWindow` and `prefetch` on first mount and again on `restoreCompletedTick`, and a mutation that removes the `initTab` override.
3. **Mutation (f) of M2a r4 Task 8 can stay green** (4B-3): a `reader` that calls `fail()` throws a `TestFailure` that the gate's own catch turns into `allowedNow = false`. The reader increments a counter and the test asserts the counter is 0.
4. **The doubling back-off has no defined scope** (4B-7). Per-name scoping makes "reset by a success" meaningless (a stored name is never retried); run-wide scoping lets one absent object stall the window. Pick the scope, state it, and split mutation (m) into the cap and the reset.
5. `PrefetchGate.start()` races `dispose()` (4B-9, 4A-3): add a `_disposed` flag checked after every await, make `start()` idempotent (the runner awaits it on every re-run), and report a teardown as `aborted=disposed`, not `aborted=wifi`.
6. Window staleness (4B-10): nothing re-runs the trigger at midnight or after a plan swap while the Train screen stays mounted; add a daily re-run or a window-hash check on resume.
7. The override of `invalidateOnBackgroundRestore` must call `invalidateOnRetry(ref)` first (`hive_tab_scaffold.dart:119`; `_TrainScreenState` overrides `invalidateOnRetry` at `screen.dart:82-85`; the correct pattern is `home_screen.dart:199-204`) (4A-5).
8. Do not re-implement the schedule-row exercise-name parser: `_exerciseNamesOfRow` is private and static (`workout_schedule_read_service.dart:869-873`); expose one public static and call it (4A-7).
9. Mutation (p) of M2a r4 Task 7 (counters keyed by `now().toLocal()`) stays green under `TZ=Asia/Kolkata`, and the Dart VM on Windows ignores `TZ`: use `now().toUtc()` as the mutation (reddens everywhere); mutation (r) (skip `await ready` in `prefetch`) needs a case with counters pre-loaded at `ceiling - 1` and a slow `list()`, or it reddens nothing (4B-12, 4B-13).
10. Layering: the policy file imports `ExerciseMedia` (in M2a it lives under `lib/core/services/exercise_media/`) and `resolveMedia` (widgets folder). Keep `core/services` free of widget imports: pass the resolver in as a function (4A-4).
11. The Train tab's first-visit limit must be written into `EXERCISE_MEDIA.md` (see above).

**Behaviour:**

Behaviour: **the kill switch guards the SINK (`feedback_pause_flag_guard_the_sink.md`): `ensure` and `prefetch` check `enabled()` first and, when it is false, return null / return at once with ZERO client calls (Review Focus 10); `prefetch` also re-checks `enabled()` before each file and stops with `aborted=disabled`.** **`ensure` is total (G15):** its whole body is inside try/catch; any failure of `ready`, `store.read` or telemetry is a miss (the bytes just fetched are still returned), reported once through `ErrorTelemetry.recordNonFatal`; the in-flight entry is removed in `whenComplete`, so a throw can never wedge a name. It awaits `ready`, then returns stored bytes at once when present (the store's `read` verifies them). Otherwise ONE in-flight download per `objectName` (concurrent callers share a `Future`); on `fetched` it calls `store.put(name, bytes, pinned: _planWindow)` (**every put carries the window set last given to `setPlanWindow`, on-demand puts included**); a `put` that throws sets the store-unwritable back-off (`kStoreUnwritableBackoff`); **while it is armed NO `put` is attempted (a full disk is not drained one evicted file per open); on-demand still returns the fetched bytes for this view, but a prefetch run ABORTS as soon as the back-off is armed** (one `exercise_media_prefetch_run` event with `aborted=unwritable`; a store that cannot keep files is not downloaded into). On `refused` or `unreachable` it returns null and records the failure time per name; on `unauthenticated` it returns null, records NOTHING (no back-off survives into the next account) and a prefetch run aborts with `aborted=unauthenticated`. **The two arms keep SEPARATE bookkeeping:** an on-demand failure never advances the prefetch doubling counter and a prefetch failure never blocks an on-demand open under the 10 s rule (each arm tracks its own last-attempt time per name). Back-off arms: **prefetch** obeys the doubling back-off (30 s to 10 min, reset by a success); **on-demand** ignores the doubling but makes at most one attempt per name per `kOnDemandMinInterval`. `evict(media)` deletes the blob and its entry AND adds the name to a per-session decode-failure ban: `ensure` returns null for a banned name without a request, and prefetch skips it (Review Focus 9). `prefetch` skips names for which `store.has(name)` is true (no read, no download). An on-demand fetch is counted but never blocked by the ceiling (C13). Counter writes go through ONE in-memory snapshot updated synchronously and persisted by `store.writeExtra` (the store's queue serialises them, so two workers finishing together cannot lose an update).
