## 1. What happened and what exists at the base (file:line, all at `01a34097`)

1. On 2026-10-04 the push CI of the Photos-hub merge (`01a34097`, run `37203140849`, attempt 1) failed ONE test: `test/contracts/sot_registry_citations_test.dart`, "gate subprocess (main() wiring) a POST-cutoff doc DECLARING non-applicability in prose is accepted": `Expected: <0> Actual: <254>`, empty `stdout`. The failing declaration was the 2nd of 4 sequential spawns (the 1st passed about 0.45 s earlier). Re-running only that job passed (7628 tests, 0 failed), as did the pull-request run and the local pre-push on the same tree. 200 of 200 concurrent local spawns exit 0; the last 30 failed CI runs contain no unit-test failure and no `Actual: <254>`.
2. `dart run x.dart` exits **254 on a compile error** and **255 on an uncaught exception** (checked locally with a syntax error, an unresolvable package import, a `throw` and a missing file; the Dart SDK documents the same, `dart-sdk/lib/io/process.dart`). `scripts/check_sot_registry_citations.dart` only calls `exit(0)` / `exit(1)` and imports `dart:io` and `sot_citation_lib.dart`, and it reads no environment variable, so a 254 means the Dart VM failed to LOAD the script, and the reason is on stderr.
3. **The defect this plan fixes:** the failing assertion (`test/contracts/sot_registry_citations_test.dart:284-285` at the base) printed only `stdout`. Of the nine `expect(r.exitCode, ...)` sites in the file (eight gate runs and the `git` setup command), `:256`, `:266`, `:307` and `:335` printed stdout and stderr; `:232` (the `git` setup) printed stderr; `:284`, `:297` and `:316` printed stdout only and `:326` printed neither. So the one failure we have ever seen could not be explained from the CI log. Round 1 added the measure that matters: a per-site `reason:` is not a cure, because any site can omit it again (this file mentioned stderr at 5 of its 9 sites and the failing one printed none).
4. **Prior art (bug-history lookup, §4.1.5; round 1, finding 5).** The same shape has been seen once before and never explained: diagnose `a7f3d1` (2026-07-27, `docs/diagnoses/2026-07-27-keystone-gate-derives-inputs-from-controllable-state-a7f3d1.md`, tier-12 evidence) records "one non-reproducible run with 5 spawn-level failures (exit 254, not assertion failures); green on every subsequent run, flagged as a possible parallelism flake rather than claimed clean". The neighbouring causes are each excluded for THIS test by reading it: `4f2a9e` (a `GIT_*` environment leak into a nested `flutter test`, `Expected: <0> / Actual: <254>`) is not it, because `runGateOn` removes the whole `GIT_*` namespace and passes `includeParentEnvironment: false`; `c3f8e1` (CI's `GITHUB_EVENT_PATH` leaking into a spawned gate) is not it, because the gate reads no environment variable; `c3f9a7` (`TimeoutException after 0:00:30` under suite parallelism, zero assertion failures) is not it, because this failure was an exit-code mismatch 0.45 s after the previous spawn. **Statement: the second sighting of an unexplained spawn-level 254 (a7f3d1 was the first); not a recurrence of 4f2a9e, c3f8e1 or c3f9a7; the cause is unproven.** Hypotheses nobody has tested: a concurrent implicit `pub get` or `.dart_tool` rewrite from another test's `dart run` in the repo root; startup races in the `dart` launcher under load. Round 2 added two facts. a7f3d1's sighting (2026-07-27) predates THIS test file (added 2026-08-08, `d4a8de00`), so it happened in a different spawn test (a7f3d1's own contract test is `test/scripts/gate_input_family_e2e_test.dart`; which test the five failures hit is not recorded). And OI-158 (TEST-3) already names THIS file for a missing `@Timeout` (the c3f9a7 class): that is a hang, not an exit 254, and it is not touched here. That is why the message, not a retry, is the fix (D4).

## 3. Design (the decisions)

- **D1 — One call at the choke point, through a replaceable reporter.** `runGateOn` (the only producer of the `ProcessResult` every gate-run assertion reads) ends with `report(gateDiag(r, <which spawn>)); return r;`, where `gateDiag` is a top-level `String gateDiag(ProcessResult r, String why)` returning `'$why\nexit=…\nstdout=…\nstderr=…'` and `report` is a parameter, `void Function(String report) report = printOnFailure`. `printOnFailure` (package `test_api`, re-exported by `flutter_test`) queues the text and prints it under the CURRENT test only if that test fails, so a passing run is silent, every current and future site is covered under any variable name, and the eight assertions keep their base text (no ledger trap, no per-site discipline to forget). The parameter exists so that a test can SEE what would be printed: two cases run the real gate with `report: reports.add` (round 2, finding 1). The "which spawn" label is `[<script>, ...<args>, 'on <doc name>: <first line of the doc body>'].join(' ')`, so the 4 spawns of the declaration test are told apart. This is why the change is about 100 lines and not one: the builder is tested (D2), its wiring is pinned and proven on a real run (D3).
- **D1b — Lessons recorded from the dropped designs.** (i) Wrapping the whole assertion in a helper hid the literal red-path text `check_gate_test_ledger.dart` matches (`scripts/gate_test_ledger_lib.dart:68-69`, over the RAW text, comments included), and failed the pre-commit loop. (ii) A per-site `reason:` plus a source scan was brittle for the reasons of round-1 findings 1-3.
- **D2 — The builder is itself tested.** A synthetic `ProcessResult(1, 254, 'out-text', 'Error: boom from stderr')` must produce the caller's why, `exit=254`, `stdout=out-text`, `stderr=Error: boom from stderr`; distinct stdout / stderr values pin each label to its own stream; a 60-line, over-1000-character stderr must come out whole (a compile error is many lines).
- **D3 — The wiring is proven on real runs and pinned from `runGateOn`'s own body.** (i) Two cases call `runGateOn(report: reports.add)` against the real gate: a failing run (exit 1; the gate's own `[sot-citations] FAIL` stderr is asserted non-empty first, so the check cannot pass vacuously) must be reported ONCE, beginning with the label, `exit=1` and `stdout=`, and ending with the run's whole stderr; a passing run must be reported too (what is SHOWN is `printOnFailure`'s decision, not `runGateOn`'s). They kill a trimmed report, an empty label, a conditional report, a report moved into the git loop and a `report` parameter that is ignored. (ii) A source pin on the comment-stripped file slices from `ProcessResult runGateOn({` to `const goodRegistry` and requires, inside that slice, ONE regex in order (the `dart` spawn statement, then only whitespace, then `report(gateDiag(r, …);`, then `return r;` and the closing brace) and that the default reporter is `printOnFailure`. (iii) The whole file may contain exactly two `Process.run*` / `Process.start` calls (the git setup loop and the dart run): a new spawn must be added on purpose and routed through `runGateOn`. A whole-file `contains` would be satisfied by the pin's own text (the trap recorded in the code-review tuning history); the slice is not, and the pin fails loudly if either marker moves.
- **D4 — Nothing else changes.** No retry, no timeout change, no skip. A retry on exit 254 would hide the evidence the next failure should produce, and the cause is unknown.
- **D5 — Not in scope:** the cause of the 254 (unexplained, not reproduced); the other subprocess tests of the repo (a repo-wide census of exit-code assertions that omit stderr was NOT measured); any `scripts/` or `lib/` change.
- **D6 — Where the text appears, stated plainly.** The founder asked that "the failure message includes the error text". The text is printed directly under the failing test in the log, after the `Expected` / `Actual` / stack lines, not inside the `Expected` / `Actual` block itself (that is a `TestFailure` field a test cannot append to without a per-assertion `reason:`, the dropped design). In CI's expanded reporter it is in the same block of the log, one scroll below the failure line.

## 4. Tests and proof

- **New tests (5; the file goes from 28 to 33 tests):** in `group('gateDiag (the failure report of a spawned gate)')`: the builder names why / exit / stdout / stderr (distinct stdout and stderr values pin each label), and a long multi-line stderr comes out whole; inside `group('gate subprocess (main() wiring)')`, where `runGateOn` lives: a REAL failing run is reported in full, a REAL passing run is reported too, and the `runGateOn` wiring pin (D3). Round 1's stream-label test was removed in round 2 (redundant with the builder test).
- **Measured, the mechanism (scratch test, deleted):** `printOnFailure('MARKER-FAIL…')` before a failing `expect(254, 0, reason: …)` printed the marker under the failing test, after the stack, under BOTH the expanded and the compact reporter; a second, passing test's marker did not appear.
- **Measured, the whole chain (sandbox copy, restored and `cmp`-checked):** with `scripts/check_sot_registry_citations.dart` made uncompilable (a syntax error), the 10 tests that call `runGateOn` (the 8 gate-run cases and the 2 real-run cases) failed, 10 of 33, and each failing test's log block ended with `<script> on <doc>: <first line>`, `exit=254`, `stdout=`, `stderr=` and the Dart compiler's own error lines. Measured on the first design (8 of 32) in round 1 and repeated on the final file in round 2. Before this change the declaration test would have shown `Expected: <0> Actual: <254>` and `stdout=` only.
- **Mutation round 3 (rule 21; 20 mutants in a sandbox copy, each confirmed applied by a marker count, restored, `cmp`-checked), all red:** K01-K07 `gateDiag` drops stderr / stdout / the exit code / the why, swaps the streams, ignores the result, cuts stderr at 200 characters; K08-K10 `runGateOn` stops reporting, the default reporter is `print`, a blank result is reported; R01-R07 (the round-2 reviewer's survivors and their variants) the report moved into the git loop, only a passing run reported, only a failing run reported, an early return before the report (when the run passed, when it failed, always), the report trimmed to its first line at the call site, an empty label, a second `dart` spawn outside `runGateOn`, `printOnFailure` hard-wired so `report` is ignored. The trim and the empty label are killed by the real-run cases only, the second spawn and the default reporter by the pin only: the two halves cover each other. (Rounds 1 and 2's earlier mutant sets, against the dropped designs, are superseded.)
- **Gates:** `check_gate_test_ledger.dart` sees FIVE real red-path assertions in this file: the four base ones (now at lines 287, 328, 347 and 357) and the new failing-run case's own `expect(r.exitCode, 1)` (378); no comment matches. The full file stays green; the full gate loop runs on the final tree.
