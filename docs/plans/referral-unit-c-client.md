## 2. Design

### 2.1 `ReferralRepository.referrerSummary()`
`await SupabaseService.instance.ensureFreshToken()` then `SupabaseService.instance.client.rpc('referrer_summary')` (an RPC goes through the client, not `functions.invoke`; the invoke gates do not apply). Returns `ReferrerSummary?` (`joined, subscribed, pending, credited, daysEarned`, all `int >= 0`). `fromJson` accepts a `Map` and a one-row `List` of maps, and treats a missing, non-int or negative field as UNKNOWN for the whole object. Any throw, a NULL or a malformed body returns `null` ("unknown"): the surface hides itself, it never shows a wrong number and never shows zeros that were not read. A network-only read is acceptable for a non-critical line (the repository already documents network-only reads and `hasRedeemed` fails soft). Failure telemetry: a transport/other failure goes to `ErrorTelemetry.recordNonFatal` with `reason: 'referral_repository_summary'`, EXCEPT the expected "function not found" shapes (PGRST202 / HTTP 404), `28000`, `42501` and HTTP 401 (a revoked EXECUTE or a lapsed session) and plain OFFLINE transport failures (`SocketException`, timeout, AND the web shapes `ClientException`/`XMLHttpRequest error`; the build reuses the outage-shape classifier the sync code already has, `SyncRetryController`, rather than a new list), which return `null` silently (before migration 160 every Home session would otherwise write a `client_errors` row, and an offline phone must not flood telemetry). Documented as deliberate exceptions to "error states have a retry" (rule 13: this is a non-critical decoration, hidden on failure, refreshed on the next trigger) and to Hive-first (rule 1: the figures are cloud-only aggregates with no local store; nothing blocks on them). ONE fetch is shared by the counters block and the notice provider (single-flight, section 2.3) so the sheet and Home never double-call.
Definitions shown to users: `joined` = friends who used the code; `subscribed` = friends who subscribed; `pending` = subscribed and not yet credited (the 7-day hold); `daysEarned` = PRO days credited to you.

### 2.3 The in-app credit notice
`referralCreditNoticeProvider` (a `Notifier`; it watches `authUserIdTokenProvider` and yields nothing for `'<anon>'`, and rebuilds on an account swap). **Single-flight and swap-safe, keyed PER ACCOUNT:** one in-flight fetch per auth token is shared by every trigger (the in-flight future, the 6-hour resume stamp and the "verified for N" memory are all keyed by the token and reset in `build()`, because a `Notifier` instance survives a rebuild: account B's Home-mount during A's in-flight fetch starts its OWN call, and A's throttle never suppresses B); the provider captures the token/uid BEFORE the `await` and compares it to the current one before EVERY `state =` and every Hive write, dropping the result if they differ (account A's late summary never reaches B; a test completes the summary AFTER a swap). The counters block reads the same fetch through a thin `referrerSummaryProvider` (autoDispose; it, the notice notifier and the flag provider ALL watch `authUserIdTokenProvider`, per `auth_invalidation_provider.dart:16-25`, and `auth_invalidation_contract_test` is run for the new files) so the sheet and Home share one call. Triggers: Home mount (`home_screen.dart`, next to the measurement slot), the invite sheet opening, the app resuming (`home_screen.dart:91-99` `didChangeAppLifecycleState`, at most once every 6 hours, the throttle stamp lives in the notifier), and the sync-restore completion/`invalidateOnRetry` tick. It calls `referrerSummary()` and decides with a PURE function `creditNoticeFor({required int daysEarned, required int? seen})` (a stored non-int scalar counts as no scalar) and the Hive scalar `referral_credit_seen_days`:
- no stored scalar (first evaluation on this device, a reinstall, a new phone, or a sign-out/sign-in): store `seen = daysEarned` SILENTLY and show nothing (a lifetime total is never announced as "new"). **Founder decision 2026-10-16: stay silent.** Nothing is lost by it: the invite sheet's counters block ("PRO DAYS EARNED", shown when at least one friend has joined) always shows the running total; only the one-time announcement of a credit that landed before this device's first check is skipped;
- `daysEarned > seen`: show ONE notice for `daysEarned - seen` days ("You earned N PRO days from friends who subscribed."); the scalar is written only when the user dismisses it or taps through ("taps through" = tapping the card body, which opens the invite sheet; dismiss = the close affordance), after an uid check;
- `daysEarned < seen` (a lower total after a void or a repair): re-baseline `seen = daysEarned` silently;
- `daysEarned == seen`, or unknown: nothing shown, nothing written.
Two devices racing both show it once and write the same value: harmless, documented. When a credit is detected the provider calls `ref.read(subscriptionServiceProvider).verifyFromServer(force: true)` ONCE per detected total (it remembers "verified for N"), so the notice never precedes the entitlement and a repeated trigger never refetches. The dismissal write captures the uid BEFORE its await, drops the write if the uid changed, and guards `HiveUserSession.currentOwnerFullId == null` before `MigratedKey.write` (otherwise the shared `configBox` would take it). The key `referral_credit_seen_days` is added to `UserConfigMigrator.userScopedKeys`; the per-user box is cleared with the others on sign-out; NO existing test fails if the registration is forgotten (`user_scoped_hive_keys_behavioral_test.dart` exercises `MigratedKey` routing with throwaway keys only), so the protection IS a new sign-out lifecycle test for `referral_credit_seen_days` (template `test/contracts/measurement_sign_out_lifecycle_test.dart:50-85`: the key is in `userScopedKeys` and `clearAllData` clears it), mutation-proven by removing the registration. After a sign-out then sign-in the key is re-baselined silently on the next check (the per-user box is cleared on sign-out); an undismissed notice re-shows on every launch because the scalar is written only on dismiss/tap-through: stated and accepted. Copy is count-neutral and singular/plural-safe ("1 PRO day" / "7 PRO days"); `Semantics` mirrors it.
Surface: a dismissible Wardroom card slot on Home (`ReferralCreditSlot`, same shape as `MeasurementDueSlot`, `SizedBox.shrink()` when nothing shows), not a modal, no push, no sound.
**Founder decision (2026-10-16):** first run stays silent (above).
**Kill switch, stated honestly.** `disable_referral_credit_notice` is a LOCAL `configBox` flag read the way `measurement_flag_provider.dart` reads its flag (default false = on). It is a test/diagnostic seam, NOT a remote kill: no remote-config path exists for it. The real remote off-switch is server-side: `REVOKE EXECUTE ON FUNCTION public.referrer_summary() FROM authenticated` (every client then gets 42501 and hides silently, which is why 42501 is in the silent set). The flag, when true, makes BOTH the notice and the counters block yield nothing and skips the network read. It is a documented, tested exception to "ship dark behind a default-OFF flag": the surfaces are dark by construction until the RPC exists, and a default-OFF flag would need a second x2 review at the flip.
**What is and is not dark before migration 160:** the counters block and the notice are invisible (the RPC call returns unknown, silently). The corrected description, the disclosure lines and the `_applyCode` repair are visible immediately; they are true today (the server rule is live) and are not hidden.
