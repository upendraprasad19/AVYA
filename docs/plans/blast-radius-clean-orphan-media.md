## 2. Design

One registry rule, in the catastrophic block: `{ glob: "supabase/functions/clean-orphan-media/**", tier: catastrophic }`, with the reason in a comment. The whole directory, not exact paths, so a new sibling inherits the tier with nobody deciding. (The registry's writer note in `docs/sot_registry.yaml` prefers exact paths over globs for ENGINE files that many features share, because a glob there auto-promotes files nobody reviewed. This directory belongs to ONE function and its siblings are exactly what should inherit the tier, as with `delete-account/**` and `razorpay-webhook/**`.)

Three inputs to the delete decision stay **platform on purpose**. This is recorded as a decision, with its trade-off: an edit to any of them is reviewed at platform (a B-pass and a plan-review record; no hermes pass and no commit-time review file).
- `_shared/subscription.ts`, home of `readProState`, the function whose answer decides every removal. Seven other non-test files import it (`founder_digest_content`, `admin-dashboard-data`, `consume-day-swap`, `expiry-reminder`, `morning-alert`, `telegram-admin-bot`, `weekly-recap-ready`) and none of them deletes anything. Promoting it would raise the tier of an edit to that file only, not of its importers. (An earlier draft said "27 readers share it": 27 is the number of NON-TEST `from("subscriptions")` call sites, in 16 files (28 in 17 with `_shared/subscription_test.ts`); round-1 finding F1, B-pass finding 7.)
- `_shared/paged_fetch.ts` (pages the candidate list) and `_shared/cron_telemetry.ts` (writes the run status that pages the founder), both platform (round-2 finding P3-8).
- The candidate RPC `find_orphan_chat_media` (migration 071), which decides what is a candidate at all, and the cron definition of `clean_orphan_media_daily`: both `supabase/migrations/**` (platform). Widening either widens what the catastrophic function deletes (round-1 finding F9). A migration is lifted to catastrophic anyway when its text mentions SECURITY DEFINER (`blast_radius_content_rules_lib.dart`) or its filename matches a catastrophic glob; the RPC is SECURITY INVOKER, so an edit that does not mention the phrase stays platform (round-2 finding P3-7).
- Relevant to whoever first edits the directory: the tier's `rollback_documented` requirement meets a rollback gap for this `verify_jwt=false` function (OI-334). OI-334 is filed on the unmerged branch `oi321-deploy-close` (its number is reserved as `origin/oi/334`); until that branch merges, its entry and the deploy skill's section 6.13 are not on `main`.

Two scoping decisions, recorded so the merge ratifies them (B-pass findings 3 and 4):
- **The pins on the delete path stay `feature`.** `test/contracts/clean_orphan_media_pro_recheck_test.dart` (the single `.remove(`, the `chat-media` bucket, the RPC name), the `clean_orphan_media_pro_recheck` entry in `docs/sot_registry.yaml` and the backup payloads under `backups/edge_function_payloads/clean-orphan-media/` classify `feature`, so weakening one of them needs no B-pass and no plan-review record. That is the same shape as every other catastrophic function: `test/contracts/delete_account_*_test.dart`, `razorpay_webhook_*_test.dart` and `verify_payment_*_test.dart` are `feature` too. Promoting this function's pins alone would make it the odd one out, and the founder's decision named the function directory. If the founder wants the pins promoted, that is an exact-path rule (section 2 above prefers exact paths for shared files) and a separate call.
- **`feature_flag` (the platform tier's `requires:`) is not met, on purpose.** The change is registry data; its "off" state is deleting the one rule line; and nothing enforces the requirement mechanically (`scripts/safe_push.sh:132-135`, `scripts/reconcile_ci.dart:41`: the reviewer, not a gate, catches its absence). Same waiver as the registry batch OI-282 (`docs/plan-reviews/oi282-blast-radius-globs.md`, "Waivers").
