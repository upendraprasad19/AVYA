## 2. Design

Two rules in the catastrophic block, next to `_shared/cron_auth.ts`, with the reason in a comment:

1. `{ glob: "supabase/functions/rolling-context/**", tier: catastrophic }` - the whole directory (`index.ts`, `index_test.ts`, anything added later, docs included), the same shape as `delete-account/**`, `razorpay-webhook/**` and `clean-orphan-media/**`: the directory belongs to ONE function, so a new sibling should inherit the tier with nobody deciding.
2. `{ glob: "supabase/functions/_shared/purge_user_storage*.ts", tier: catastrophic }` - one rule that covers the module, its Deno test `purge_user_storage_test.ts` (six behavioural tests of the recursion, pagination and error isolation, plus the list-equality test) and any file later split off it by name. A glob and not two exact paths: the registry's writer note in `docs/sot_registry.yaml` prefers exact paths for ENGINE files that many features share, because a glob there auto-promotes files nobody reviewed; this name is single-purpose, so the only thing the wildcard can promote is more of the purge. The test is included for the reason `clean-orphan-media/logic_test.ts` is: a weakened test of the delete path is the same risk as a weakened delete path. Either half is one deleted line if the founder wants it narrower.

Inputs that stay **platform on purpose**, recorded as a decision with its trade-off (an edit to any of them is reviewed at platform: a B-pass and a plan-review record, no hermes pass and no commit-time review file):
- `_shared/user_owned_buckets.ts`, the list of buckets the purge walks. Round-1 correction of the first draft ("stays platform for every edit"): `purge_user_storage_test.ts:60-65` asserts the list equals exactly the five names, and that file is catastrophic through the purge glob, so **a change to what the list CONTAINS (adding or removing a bucket) also edits a catastrophic file and lands catastrophic**; only a comment-only edit of the list file stays platform. Removing a bucket the client still writes also reddens `test/contracts/delete_account_purges_all_user_buckets_test.dart` (it requires every bucket the client names to be on the list, and its positive control fails if discovery goes blind); adding one needs no Dart edit (the Dart test only checks that the client's buckets are a subset). Its only production importer is `delete-account/index.ts:30`, already catastrophic.
- The shared helpers `rolling-context/index.ts` imports and that other functions import too: `_shared/embeddings.ts`, `gemini.ts`, `gemini_failure_alert.ts`, `paged_fetch.ts`, `cron_telemetry.ts`, `sanitize_for_prompt.ts`. Promoting any of them would raise the tier of every function that shares it, not of the delete. That includes `_shared/paged_fetch.ts`: its ordering decides which rows `rolling-context` deletes (section 1), so a defect there changes the victim set, and an edit to it is reviewed at platform only. That is the trade-off, stated rather than hidden. (`_shared/cron_auth.ts`, the sixth import, is already catastrophic.)
- The cron definition `rolling-context-nightly` (`supabase/migrations/**`, platform; lifted to catastrophic when its text mentions SECURITY DEFINER or its filename matches a catastrophic glob).
- The pins on the delete paths (`test/contracts/rolling_context_excludes_app_event_test.dart`, `delete_account_purges_all_user_buckets_test.dart`, the SoT entries, the backup payloads) stay `feature`, exactly as for every other catastrophic function (`delete_account_*_test.dart`, `razorpay_webhook_*_test.dart`, `clean_orphan_media_pro_recheck_test.dart`). Promoting them would make these paths the odd ones out; it would be an exact-path rule and a separate call.

Three scoping decisions, recorded so the merge ratifies them:
- **The rules are wider than the two paths the founder named** (`_shared/purge_user_storage.ts` and `rolling-context/index.ts:522`): the whole `rolling-context/` directory (so a new sibling inherits the tier) and a wildcard for the purge family (its Deno test, and a file split off it by name). `rolling-context/index_test.ts` is a source-grep wiring test for the Gemini-exhaustion alert, NOT a pin of the delete (the delete's pin is `test/contracts/rolling_context_excludes_app_event_test.dart`, which stays `feature`), so it is in the tier because of the directory shape, not because it guards the delete. Narrowing either rule is one deleted or edited line.
- **`feature_flag` (the platform tier's `requires:`) is not met, on purpose.** Registry data; its "off" state is deleting the rule lines; nothing enforces it mechanically (`scripts/safe_push.sh:132-135`, `scripts/reconcile_ci.dart:41`). Same waiver as OI-282 and `blast-radius-clean-orphan-media`.
- **No SoT registry entry and no migration:** nothing is deployed, applied or migrated; no live system is read or written. The SoT entry for the registry writer carries `line_range: 39-506` (`docs/sot_registry.yaml`, writer `docs/blast_radius.yaml`); that already stopped before the base catch-all (:519) because the registry grew in earlier merges without it, `scripts/check_sot_registry_parity.dart:160-165` only bounds-checks it (start < 1, end beyond the file), and the previous registry batch (`blast-radius-clean-orphan-media`) kept it current, so this batch moves it to `39-536` (`paths:` at :39 to the catch-all at :536).
