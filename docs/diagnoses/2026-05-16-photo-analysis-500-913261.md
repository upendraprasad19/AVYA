# Bug 913261 — ai-media-proxy returned 500 for upstream-class failures, chat bubble showed broken-image icon

## Symptoms

Founder sent a photo via AI Coach at 13:32 IST 2026-05-15. Edge Function logs show:

```
POST | 500 | ai-media-proxy | execution_time_ms: 14587 | version: 16
```

User-side: "Sorry, I couldn't analyse that photo. Please try again." toast + broken-image placeholder where the photo should have been.

The 14.5 s execution time strongly suggests a Gemini upstream timeout (the inner call has `timeoutMs: 25_000`) caught by the bottom-of-handler catch and re-raised as a generic 500. The client's `retryColdStart` retry budget covers `{502, 503, 504}` — 500 falls through immediately, so the warm-start retry budget bumped in `c01d57` doesn't help here.

## Root cause

Two distinct issues compounding the user-visible symptom:

### 1. `supabase/functions/ai-media-proxy/index.ts:487` (bottom-of-handler catch)

```ts
} catch (err) {
  const requestId = crypto.randomUUID().split("-")[0];
  console.error(`[ai-media-proxy] request_id=${requestId}`, err);
  return new Response(
    JSON.stringify({ error: "Internal server error", request_id: requestId }),
    { status: 500, ... },
  );
}
```

Every throw inside the try-block — including `req.json()` parse failures, `fetchImageAsBase64` Storage 404s, image-too-large, SSRF rejects, and Gemini upstream issues — produced a 500. Pre-fix the inner `geminiChat` helper already returned `{content: null}` on its own timeouts (it doesn't throw), so the explicit "no content" path at line 411 already returned 502. But:

- `fetchImageAsBase64` threw raw `Error` on Storage 404 / oversize / SSRF — these reached the catch as 500.
- A malformed `req.json()` payload threw a `SyntaxError` — 500.
- A network blip during Storage `fetch()` (TLS reset, DNS) threw — 500.
- A Postgres failure inside `ai_coach_interactions.insert` would also throw — 500.

Each of these has a different "right" status, and the client retry layer treats them all the same when they share status 500. Pre-fix a Storage 404 (recoverable, user-actionable) looked identical to a real server bug.

### 2. `lib/features/ai_coach/widgets/chat_bubble.dart` `CachedNetworkImage.errorWidget` (pre-fix line ~150)

The only "image failed" surface was the `Icons.broken_image_outlined` icon inside a 120×120 input-color box. No caption, no retry affordance. When the founder's photo URL didn't resolve (Storage upload silently failed, or the URL has not yet propagated to CDN), the user saw a black square with no signal about what went wrong or what to do.

## Fix

### Server (ai-media-proxy/index.ts)

1. New `HttpError` class with `errorType` ∈ {validation, upstream, internal, storage}.
2. `fetchImageAsBase64` now throws `HttpError(400, "storage", "Image upload incomplete — please retry sending the photo.")` on 404; `HttpError(502, "upstream", ...)` on Storage 5xx; `HttpError(400, "validation", ...)` on SSRF / oversize.
3. `req.json()` wrapped in its own try/catch → `HttpError(400, "validation", ...)`.
4. Bottom-of-handler catch checks `err instanceof HttpError` and returns the typed status + `error_type` field. Anything else falls through to 500 internal (the rare "real bug" path).
5. Empty-Gemini path already returned 502 — now annotated with `error_type: "upstream"`.

### Client (ai_coach_provider.dart)

1. New `isStorageFailure` branch in the `sendWithMedia` catch detects `error_type='storage'` / "upload incomplete" in the error string.
2. New `ChatHistoryNotifier.markLastUserMediaFailed()` helper flips the most recent user-side photo bubble's `mediaFailed=true`.
3. New `ChatMessage.mediaFailed` field.

### Widget (chat_bubble.dart)

1. New `mediaFailed` + `onMediaRetry` props.
2. New `_buildPhotoFailedTile()` — 120×120 input-color tile, hairline red border, `image_not_supported_outlined` glyph, "PHOTO FAILED" mono caption, "Tap to retry" DM Sans subline.
3. `_buildContent` routes both the "no mediaUrl + photo-type" path AND `CachedNetworkImage.errorWidget` to the same tile.

### Screen (ai_coach_screen.dart)

1. `ChatBubble` constructor now passes `mediaFailed` from `ChatMessage`.
2. `onMediaRetry` re-opens the gallery picker so the user retries the upload without retyping their caption.

## Verification

- `test/contracts/ai_media_proxy_status_code_classification_test.dart` — source-grep tests pin the `HttpError` class shape, the typed-status mapping, and the absence of "Internal server error" in the validation paths.
- `test/widgets/chat_bubble_photo_failure_test.dart` — widget tests assert the failed-tile renders when `mediaFailed=true`, when `mediaType` is set but `mediaUrl` is null, and that `onMediaRetry` fires on tap.

## Risks

- **Validation 400s used to be 500s** — a small number of legitimately-broken clients (e.g. an old app version sending an unparseable body) will now see 400 instead of 500. Net positive: they get the actual error message instead of a generic "internal server error".
- **Storage 404 as 400** — if a future Storage misconfig (e.g. wrong bucket name) starts returning 404 for everyone, all photo analyses will fail with the user-facing "Photo upload failed" message. The `error_type='storage'` tag makes this trivially greppable in `client_errors`.
- **Backwards compat** — old client builds without the `error_type` recognition will fall through to the existing generic message handlers ("Upload failed — please try picking the photo again." for the "Only Supabase Storage URLs" branch, etc.). No worse than current behavior.
