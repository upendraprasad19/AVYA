# body-measurement values accepted without bounds

## What was wrong

A body-measurement value had no bound but `valueCm <= 0`, at the chat parse (`ai_coach_provider.dart`, `case 'log_measurement'`), at the confirm handler (`conversational_log_handler.dart`, `_logMeasurement`) and at the writer (`health_write_service.dart`, `logMeasurement`). What that cost, in order of evidence:

1. **An absurd finite value** (`3000`, or `32` typed in inches) was stored and handed to the coach as fact. Producer: the model's `<ICBF_LOG>` tag; the prompt says to convert inches to cm, and a model forgets.
2. **A wrong-typed model field.** The parse read `data['value_cm'] as num?` and `data['type'] as String?`. A String `value_cm` survives the proxy's JSON round trip, so `"82"` reaches the app as a String. The cast threw inside `send`'s try (`addActions` is called at `ai_coach_provider.dart:980`), the catch replaced the reply that was shown with "Sorry, something went wrong", marked the stored interaction failed and skipped `addIntents`; the later actions of that response were lost (`addActions` appends per iteration, so the earlier ones were kept). `sendWithMedia` and a third caller have the same exposure.
3. **A future-dated record** from a wrong device clock: the old coach reader kept whichever record had the latest date, so it shadowed every real entry until that day came.
4. **Latent: a stored NaN or Infinity.** `NaN <= 0` is false and `jsonDecode('1e999')` is Infinity, so every guard let them through, and the coach-context reader (`ai_snapshot_builder.dart`, `_getBodyMeasurements`) cast every field and returned them into the snapshot, where the size trim (`jsonEncode(s)`, `ai_snapshot_builder.dart:303`) throws `JsonUnsupportedObjectError`. Both are shared paths: every chat context build goes through `buildAiContext`, and so does the snapshot push (`pushSnapshotNow` -> `compileDailySnapshot`, `sync_service.dart:1149`), so one such value would stop the coach and the snapshot push for that user. **The B-pass found no producer of one in the tree**: the measurement card has one producer (the chat parse) whose input is the proxy's JSON, and in that round trip `JSON.parse('1e999')` is Infinity but `JSON.stringify` writes every non-finite number as `null` and a bare `NaN` fails `JSON.parse` (checked with node 22 on 2026-10-11), `logMeasurement` has one caller, and the restore and pull writers copy cloud values (0 rows exist, G2). The chain is closed anyway, because it is cheap and because the Landing B text field will parse user text: `double.tryParse` returns NaN or Infinity for `NaN`, `Infinity` and `1e999` (checked on the pinned Dart). The reader's numeric-String site and non-String date records are the same: the tests plant them in the box directly and no producer is named; the type tests cost nothing.

## Bug-history lookup (CLAUDE.md section 4.1.5)

`docs/diagnoses/INDEX.md`: no earlier diagnose-doc on unbounded measurement values. Same record, push side: `c8a4d1` (class 2.100). The same class in other domains: `4e8f1b` (the coach's `log_meal_by_text` could persist an absurd calorie or macro value through a WriteService; fixed by a clamp at every write path, `nutrition_calorie_clamp_test.dart`), `a3f6c9` (a second write path, `moveMealLog`, bypassed that clamp: the shape of this record's restore and pull writers), `f8c1a5` (a value no in-app write path can produce, written by restore, fixed by clamping on read: the precedent for the reader tier here) and `b2f7c4` (a forecast with no sanity clamp). The restore and pull writers stay unbounded by design (the `a3f6c9` shape) and are covered at read time (the `f8c1a5` fix) and by ledger row `LEGACY-PUSH`.

## The fix

See `proposed_fix`. Files: `lib/core/constants/body_measurement_specs.dart` (new), `lib/core/services/health_write_service.dart`, `lib/features/ai_coach/providers/ai_coach_provider.dart`, `lib/core/services/health_read_service.dart`, `lib/features/ai_coach/services/ai_snapshot_builder.dart` (the `body_measurement_sites.dart` import is swapped one-for-one for `health_read_service.dart`, so no pin above `_getBodyMeasurements` moves), `lib/features/ai_coach/services/conversational_log_handler.dart` (class doc only).

**No handler-tier bound (plan A5, a recorded departure from the L2a obligation).** The measurement `PendingLogAction` has one producer, the parse, and the handler passes the same `type` and `valueCm` to the writer, so any value that survives the parse survives the writer and any value the writer rejects makes the handler return `false`. A handler-tier bound is an equivalent mutant while the fixed-point test holds (RB-M32 removes the handler's own `<= 0` guard and nothing is observable). The evidence is the handler test in `log_measurement_site_whitelist_test.dart` (3000, waist 40, arms 80, NaN, Infinity all return `false` and write nothing; the zero and negative rows are refused by the handler's own guard, the rest by the writer).

## 4.6 position (founder decision D6, answered 2026-10-11: no kill switch)

Landing A ships with no lever. The change hides values implausible as centimetres (40 inches is a real waist and 40 cm is not one; the floors are the unit-mix-up threshold) and values no body produces; the golden fixture proves the same keys and values in the coach context on clean data; a lever would be a second copy of the validation; and the rejection event, `measurement_value_rejected` (site and below / above / nonfinite / wrongtype, never the value), is the observation. It is a LOW-priority event: `ErrorTelemetry.logEvent` drops such events during a rate-limit cooldown, so its counts are a lower bound. If D6 had been answered "add the lever", A would have gained `disable_measurement_bounds` and gone back to review before it was built.

## B-pass (2026-10-11)

Three context-blind Sonnet reviewers (production code; tests with proposed mutants; documents and claims) read commit `c8bc98e8` with exhaustive read-only command lists. No P0 or P1.
