# body-measurement values accepted without bounds

## What was wrong

A body-measurement value had no bound but `valueCm <= 0`, at the chat parse (`ai_coach_provider.dart`, `case 'log_measurement'`), at the confirm handler (`conversational_log_handler.dart`, `_logMeasurement`) and at the writer (`health_write_service.dart`, `logMeasurement`). `NaN <= 0` is false, so NaN was stored; `jsonDecode('1e999')` is Infinity, which also passes. The coach-context reader (`ai_snapshot_builder.dart`, `_getBodyMeasurements`) cast every field, so a numeric-String site or a non-String date threw a `TypeError`, and a stored NaN went into the snapshot, where the size trim (`jsonEncode(s)`, `ai_snapshot_builder.dart:303`) threw `JsonUnsupportedObjectError`. Both are shared paths: every chat context build goes through `buildAiContext`, and so does the snapshot push (`pushSnapshotNow` -> `compileDailySnapshot`, `sync_service.dart:1149`), so one bad measurement stopped the coach and the snapshot push for that user.

The chat parse also read `data['value_cm'] as num?` and `data['type'] as String?`. `addActions` has no per-item guard, so one wrong-typed action (`"82"`, `true`, `[]`, a numeric `type`) threw out of the loop and discarded the other actions of that response.

### Writer / reader map (before the fix)

| Role | Where | What it did |
|---|---|---|
| Writer (parse) | `ai_coach_provider.dart` `_parse`, `case 'log_measurement'` | cast `type` and `value_cm`; `valueCm <= 0` the only bound; a missing value became `0` |
| Writer (handler) | `conversational_log_handler.dart` `_logMeasurement` | `valueCm <= 0` only, then the writer |
| Writer | `health_write_service.dart` `logMeasurement` | non-empty part and `valueCm > 0`; stored the raw value under the un-normalised part (`partName.toLowerCase()`, no trim); the guard trimmed but the store did not |
| Reader | `ai_snapshot_builder.dart` `_getBodyMeasurements` | cast every field; kept whichever of two equal dates the box iterated first |
| Reader (push) | `sync_health.dart` `_syncMeasurements` | pushes every finite held site (the merge-safe filter drops non-finite ones) |

## Bug-history lookup (CLAUDE.md section 4.1.5)

`docs/diagnoses/INDEX.md`: no earlier diagnose-doc on unbounded measurement values. Same record, push side: `c8a4d1` (class 2.100). The same class in other domains: `4e8f1b` (the coach's `log_meal_by_text` could persist an absurd calorie or macro value through a WriteService; fixed by a clamp at every write path, `nutrition_calorie_clamp_test.dart`), `a3f6c9` (a second write path, `moveMealLog`, bypassed that clamp: the shape of this record's restore and pull writers), `f8c1a5` (a value no in-app write path can produce, written by restore, fixed by clamping on read: the precedent for the reader tier here) and `b2f7c4` (a forecast with no sanity clamp). All are recorded under `related_bugs`. This is the `4e8f1b` class with one stated policy difference: a rejection, not a clamp, because a measurement's usual error is a unit mix-up (a waist of 32 typed in inches) and a clamp would turn it into a confident wrong number. The restore and pull writers stay unbounded by design (the `a3f6c9` shape) and are covered at read time (the `f8c1a5` fix) and by ledger row `LEGACY-PUSH`.

## Verified facts

- **Old reader, run on the exact fixtures of the new tests (2026-10-11, the previous loop copied verbatim into a throwaway test, deleted after the run).** Clean fixture (`measurement_2026-09-20` all four sites; `2026-10-01` waist 82 and hips 97; `2026-10-04` chest 100 and arms 33): `{"chest":100.0,"waist":82.0,"hips":97.0,"arms":33.0}`, keys `[chest, waist, hips, arms]`. This is the literal the golden test pins. Dirty fixture (a numeric-String hips on one record, an integer date on another): `_TypeError: type 'String' is not a subtype of type 'num?' in type cast`. NaN and 3000 only: returned `{chest: 3000.0, waist: NaN, hips: 98.0, arms: 33.5}`, and `jsonEncode` of that threw `JsonUnsupportedObjectError`.
- **Rounding on the pinned SDK (Dart 3.11.1, `/home/ubuntu/fvm/versions/3.41.4`).** `double.parse(v.toStringAsFixed(1))` returns NaN, `Infinity` and `-Infinity` unchanged; `(v * 10).round() / 10` throws `UnsupportedError` on all three. 49.96 -> 50.0, 49.94 -> 49.9, 200.04 -> 200.0, 70.25 -> 70.3. Dart normalises an impossible date (`DateTime.utc(2026, 13, 45)`, `DateTime.tryParse('2026-02-30')`) instead of failing, and `tryParse` also accepts `20261001` and a timestamp, which is why the reader checks the shape with a strict regex and the calendar numerically.

## The fix

See `proposed_fix`. Files: `lib/core/constants/body_measurement_specs.dart` (new), `lib/core/services/health_write_service.dart`, `lib/features/ai_coach/providers/ai_coach_provider.dart`, `lib/core/services/health_read_service.dart`, `lib/features/ai_coach/services/ai_snapshot_builder.dart` (the `body_measurement_sites.dart` import is swapped one-for-one for `health_read_service.dart`, so no pin above `_getBodyMeasurements` moves), `lib/features/ai_coach/services/conversational_log_handler.dart` (class doc only).

**No handler-tier bound (plan A5, a recorded departure from the L2a obligation).** The measurement `PendingLogAction` has one producer, the parse, and the handler passes the same `type` and `valueCm` to the writer, so any value that survives the parse survives the writer and any value the writer rejects makes the handler return `false`. A handler-tier bound is an equivalent mutant while the fixed-point test holds. The evidence is the handler test in `log_measurement_site_whitelist_test.dart` (3000, waist 40, arms 80, NaN, Infinity all return `false` and write nothing).

## 4.6 position (founder decision D6, answered 2026-10-11: no kill switch)

Landing A ships with no lever. The change only hides values no body produces; the golden fixture proves the same keys and values in the coach context on clean data; a lever would be a second copy of the validation; and the rejection event, `measurement_value_rejected` (site and below / above / nonfinite, never the number), is the observation. If D6 had been answered "add the lever", A would have gained `disable_measurement_bounds` and gone back to review before it was built.

## Founder decisions recorded here

- **D5** (answered 2026-10-11, confirm as is): the bounds table is live from this landing; the floors double as the probably-inches threshold.
