# Body

## Symptom

`PostgrestException` SQLSTATE 42P10 raised by PostgREST on every
`upsert(..., onConflict: '<natural_key_cols>')` call against three tables.
Production log evidence — single user, 60-second window on 2026-05-15
04:10 UTC, 47 `client_errors` rows:

- `workout_logs` upserts with `onConflict: 'user_id,date,exercise_name'`
- `workout_log_exercises` upserts with `onConflict: 'workout_log_id,exercise_id,set_number'`
- `nutrition_logs` upserts with `onConflict: 'user_id,date,meal_type'`

## Root cause

The three tables each carry a PARTIAL unique index:

```
uniq_workout_logs_user_date_name
  ON workout_logs (user_id, date, exercise_name)
  WHERE ((user_id IS NOT NULL) AND (date IS NOT NULL) AND (exercise_name IS NOT NULL))

uniq_workout_log_exercises_wlog_ex_set
  ON workout_log_exercises (workout_log_id, exercise_id, set_number)
  WHERE ((workout_log_id IS NOT NULL) AND ... )

uniq_nutrition_logs_user_date_meal
  ON nutrition_logs (user_id, date, meal_type)
  WHERE ((user_id IS NOT NULL) AND (date IS NOT NULL) AND (meal_type IS NOT NULL))
```

PostgreSQL's ON CONFLICT arbiter resolver requires an index whose
definition exactly matches the inferred columns. When the index has a
`WHERE` predicate, the planner only matches the arbiter if it can PROVE
the inserted tuple satisfies the predicate from schema constraints
alone. Because all four predicate columns (`workout_logs.date`,
`workout_logs.exercise_name`, `workout_log_exercises.workout_log_id`,
`nutrition_logs.meal_type`) are NULLABLE in the live schema, the
planner cannot prove non-null-ness and rejects the partial index as
the arbiter — even though the tuple the writer sent is non-null. The
result is 42P10.

This is the same family of bug as the audit 2026-05-12 P0-A/P0-B onConflict
fixes (sync_onconflict_natural_key_test.dart) — natural key arbiter
resolution. Test #14 / Bug B.1 hardened the client side; this is the
schema-side complement.

## Verifications (Supabase MCP execute_sql, project_id dedsavbjuwgarrhphgnl, 2026-05-15)

- V1: `SELECT count(*) FROM workout_logs WHERE date IS NULL`            → 0
- V2: `SELECT count(*) FROM workout_logs WHERE exercise_name IS NULL`   → 0
- V3: `SELECT count(*) FROM workout_log_exercises WHERE workout_log_id IS NULL` → 0
- V4: `SELECT count(*) FROM nutrition_logs WHERE meal_type IS NULL`     → 0

All 4 columns are already effectively non-null in production. The
backfill block in migration 064 is a defensive no-op for any rows that
might slip in between pre-flight verification and migration apply.

## Fix (migration 064)

1. Backfill the 4 columns with writer-contract-aligned values
   (`logged_at::date`, `'unknown'`, `'wlog_' || extract(epoch from
   created_at)`, `'snack'`).
2. `ALTER COLUMN ... SET NOT NULL` on all 4 columns — the schema now
   asserts what the writer has always sent.
3. `DROP INDEX IF EXISTS` for the 3 partial indexes; `CREATE UNIQUE
   INDEX` (non-partial) replacements with the same names + columns.
4. `COMMENT ON INDEX` each new index citing diagnose-id 76c8f4.

PostgREST arbiter resolution now succeeds because the columns are
NOT NULL and the index has no WHERE predicate. No client-side change
required.

## Out of scope

- `workout_log_exercises.workout_log_id` is `data_type=text` rather
  than `uuid`. Separate smell — does not affect arbiter resolution
  (text indexes are valid arbiters). Tracked separately.
- 47 client_errors rows themselves — they remain in the log for audit;
  no need to clean up.
