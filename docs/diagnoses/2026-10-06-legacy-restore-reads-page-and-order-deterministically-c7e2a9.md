# c7e2a9 — the legacy restore reads lost rows past 1000 and paged on a non-unique sort

## What happened

The client has two ways to restore after a reinstall: one Edge Function call (`restore-user-snapshot`, fixed in e4c1d7) and, when that call fails, the legacy per-table restore. The legacy path paged most tables through `_fetchAllRows`, but three reads were bare selects, and the pager ordered by a single column. PostgREST answers every bare read with at most 1000 rows, status 200, no error, so a long-history account restored fewer completions or custom items than it had and nothing said so. Two page requests may also return rows that tie on the one sort column in different orders, so a row on a page seam could be skipped and another served twice.

## Writer / reader map

Writers: `_fetchAllRows` (`sync_service.dart:3073`), `_readScheduleCompletionRows` (`sync_workout.dart:1141`), `_readCustomRows` (`sync_community.dart:324`), the nutrition loop (`sync_nutrition.dart:609`), the flag (`sync_flags.dart:241`). Readers: the `_restoreX` loops listed in the frontmatter; the first-wins readers are the two custom-item restores and `_restoreExerciseLogs`.

## Fix and what it deliberately does not do

See `proposed_fix`. It does not touch the coach read (already newest 1000, descending, one request; a test pins it), does not change any Hive key, and does not claim to keep today's winner among tied rows. It does not make the loop robust to a lowered `db-max-rows`: the loop stops on a short page, and a lowered cap would look like a short page. The plan chose to pin that assumption rather than add one confirming request to every table of the fallback (ledger `B2-SHORT-PAGE-STOP`).

## Verification

A stub that really pages (`SyncStubServer.pagedTables`: `eq`/`gt`/`gte`/`lt`/`lte` filters, the comma-joined `order=` list, `offset`/`limit`, a 1000-row clamp, and a `reshuffleTies` mode that reverses rows tied on every order column on alternate requests; any request shape it does not model throws) drives the real `SyncService`. `test/sync/restore_legacy_paging_behavioral_test.dart`: 2,500 completions land through three owner-scoped pages and a row older than `since` stays out; a tie group straddling each seam is neither skipped nor served twice; a NEGATIVE CONTROL shows the same stub does lose and double rows when only the non-unique column orders the read (2,499 rows = 833 dates x 3, so a tie group straddles BOTH page seams); exactly 2,000 rows cost one empty confirming page; the kill switch restores the single un-paged, still owner-scoped and since-filtered read and its 1000-row loss; 1,500 custom exercises and 1,500 custom foods land; `readiness_daily` (2,500 rows, all tied on `created_at`) orders by `date` and never by `id`; ten tables send their exact unique-last order string with the fix and the old string with the kill switch; the coach read stays one request, descending, `limit(1000)`; a server clamp below the page size ends the read after one page (the assumption, pinned); a table that fills 50,000 rows emits exactly one `restore_row_ceiling_hit` naming only the table, from `_fetchAllRows` (readiness) and from the nutrition loop; 2,500 nutrition logs tied on `created_at` page three times with `id` last and all land; 1,200 approved community foods and exercises tied on `created_at` page 500 at a time with `id` last, each served once; the `cases` group checks every expected order term against `backups/live_schema_columns.json` (a typo, or an `id` on an id-less table, written the same way in test and code cannot pass); the config-box-closed getter returns TRUE. Every test's tearDown also asserts the stub never had to refuse a request shape and that every filter and order column the code SENT is a live column of its table (checked against the recorded requests, so a typo written the same way in code and in a seeded row cannot pass). The stub's own users were re-run green (`sync_stub_server_test`, probe, FK-recovery, coach orphan, freeze-merge, streak-reckon, exercise-log and nutrition-log hash-index tests, plus the source-grep tests that read the edited regions). Review: three fresh context-blind Sonnet seats over two rounds (round 1: A correctness / fidelity / kill-switch revert / source-grep ripples, B test adequacy; round 2: C re-review of what round 1 changed), read-only; findings and dispositions in `docs/reviews/restore-legacy-paging-bpass.md`.

## Limits

The 50,000-row test builds 50,000 stub rows and takes a few seconds. A live read of the real PostgREST cap is not part of the test run (it is a platform setting); the cap was measured at 1000 on 2026-10-06 and the single-call function's live paging proof (e4c1d7) returned all 1431 `food_database` rows exactly once. Not exercised on a device: a device restore that falls back to the legacy path owes the §5 runtime check.
