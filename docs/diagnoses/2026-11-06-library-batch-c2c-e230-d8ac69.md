# Batch C2c: E230 Standing Single Leg Curl becomes a bodyweight row (OI-474)

Plan: `docs/plans/2026-11-06-library-batch-c2c-e230.md` (draft 3; review rounds 1 and 2, round 2 mechanical only). The founder's build go: 2026-11-06, after being shown the effect on gym plans and the alternative (keep E230 as the cable row, no animation).

## What changed

- **E230** now reads: `equipment_needed ["bodyweight"]`, `equipment_tier` all four, `gym_availability "home"`, `logging_type "bodyweight_reps"`, `standard_swap ""`, new cues, mistakes, warm-up and tip (no cable, no load, progression by tempo). The values equal what the 92 other active bodyweight strength rows carry (tier and `gym_availability` 92/92; logging is a member of their set, 81 of 92 bodyweight_reps). Unchanged: tempo, reps, rest, difficulty, `priority_tier`, `met_value`, `breathing_cue`, `variant_family leg_curl`, `core_levels []`, injury tags `["hamstring"]`.
- **The edit is a record.** `scripts/data/library_e230_retag.json` (generated by node from the HEAD library) is applied by a stage of `scripts/add_library_batch_c_v15.js`. The importer accepts the row at `before` (applies), at `after` (no-op) and nothing else.
- **Picture.** gif 0795 (12 frames; six evenly spaced frames read: a standing, equipment-free heel curl behind the body, nothing held or attached) moved from `retag_waits` into `entries` with a `released_by`; the builder reports rows 759, files 758; the still is bundled; the three media keys are on E230.
- **Seed v20**, three older version pins repointed to 20. **Cloud:** one re-seed migration; the inline rollback restores E230's four cloud columns.
- **Generator** (`seed_exercise_library.js`): hard stop on a missing record or a record that drifted from the library; the header and rollback text are for a batch that adds and removes no row; the reactivation and twin lines are written only when their lists are non-empty (an empty `IN ()` is a syntax error).

In bodyweight and home plans it fills `Hamstrings/knee_dominant/isolation`, replacing a fallback pick (Lateral Lunge, Step Up, Sumo Squat, Walking Lunge at `attempt3DropTypeAndTarget`, 298 picks) with a real hamstring isolation at `attempt1Exact` (166) or `attempt2DropSubFocus` (78). The 2 basic_gym changes are `excl:cables` personas: they now get E230 instead of Dumbbell Lying Hamstring Curl.
- **Golden, 998 personas (real `generateV4`):** 574 hashes change (grid 552, injury 16, exclusion 2, owned 3, pins 1), classified by precedence: **338 new pick** (E230 absent before, present after), **215 content-only** (E230 in both: gym tiers; the planned exercise's `logging_type` weight_reps to bodyweight_reps, `notes` first cue, `equipment_needed`; verified field by field on three keys), **21 ripple** (E230 in neither plan), **0** harness bug, **0** plans that lose E230. 116 plans gain an exercise record, none has fewer.

## Accepted behaviour changes (told to the founder before the build go)

(a) E230 enters the hamstring slot of most bodyweight and home plans; (b) a gym plan's loaded cable curl becomes an unloaded curl logged by reps; (c) a set already logged under E230 holds a cable weight under `weight_reps`, the exercise now logs `bodyweight_reps`; no remap is written. What a tester with cable-era E230 history would see, by reader: the LAST line (`exercise_last_try_lines.dart`) and the TRY suggestion (`train_provider.dart:99-107`, which suggests a load for a `weight_reps` row) keep showing the cable load until one bodyweight set is logged; `progression_resolver.dart:239-243` still counts that log as a top set, so a phase carried over through `periodization_engine.dart:108-112` can show the cue "N kg (from last phase + progression)" on a row that now takes no load. The existing repairs do NOT reach it: the a4c7d1 boot heal (`auth_session_bootstrapper.dart:1196-1262`) reaches only rows still in memory as `Map<String, dynamic>` (a restore in the same sign-in) and, for those, flips the stored type but keeps `weight_kg` (`fieldsClearedFor('bodyweight_reps')` clears only duration and distance); a set read from disk throws at its `.cast` (OI-394), the outer catch records the non-fatal telemetry `exlog_format_normalization_heal_failed` and the loop stops, on every sign-in that meets such a row (new telemetry noise, testing accounts only); `logging_type_repair_migrator.dart` is one-shot per device (`logging_type_repair_v3_done`). Why this is accepted and no remap is written: every existing account, web or phone, is a testing account until the Play/App Store launch (CLAUDE.md section 1), so no real-user cohort will hold cable-E230 history; the cost is a stale-looking line on a tester's device until one bodyweight set is logged. (d) an install at v19 keeps the cable row until its next launch after the upgrade, and a plan already generated keeps its old `notes`, `equipment_needed` and `logging_type` until regenerated.
