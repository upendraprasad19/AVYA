# Code Review — 297bae7db41c

## Finding 1 — P3 — function_exception_swallow / guard_without_its_mirror
- **file:line:** `supabase/migrations/134_alert_critical_notify_telemetry.sql:101-114` (the success-path `client_errors` insert, `error_message` value `'request_id=' || v_request_id || ' alert_id=' || NEW.id`).
- **claim:** Postgres's `||` text-concatenation operator returns `NULL` (not a partial string) when *either* operand is `NULL` — `'a' || NULL` is `NULL`, not `'a'` (that NULL-preserving behaviour is `||`; only `concat()`/`format()` treat `NULL` as empty). If `net.http_post(...) INTO v_request_id` were ever to resolve to `NULL` (pg_net queues the request synchronously and returns its row id — this is not expected to happen while the extension is healthy, but nothing in the trigger asserts it), the entire `error_message` string collapses to `NULL`, silently discarding **both** the `alert_id=` fragment and the `request_id=` fragment, not just the missing piece. `error_message` is nullable so the `INSERT` still succeeds (no NOT NULL violation, no abort) — this is a telemetry-quality gap, not a correctness bug: on the one occasion it could matter (something already unusual enough to make `net.http_post` return `NULL`), the diagnostic row for it is the one row that says nothing about which alert triggered it.
- **verification:** `psql -c "select 'request_id=' || NULL::bigint || ' alert_id=' || 42;"` → `NULL`. Confirmed the live deployed function body is byte-identical to the file (`pg_get_functiondef` matches, run via MCP `execute_sql` against project `dedsavbjuwgarrhphgnl`), so this is the exact expression that will run in production.
- **suggested-fix:** `'request_id=' || coalesce(v_request_id::text, 'null') || ' alert_id=' || NEW.id` (or `format('request_id=%s alert_id=%s', v_request_id, NEW.id)`, which substitutes `NULL` as the literal text `NULL` rather than nulling the whole string).
- **status:** accepted, parked — real but non-load-bearing (the reviewer's own words: "telemetry-quality gap, not a correctness bug"), and the edge case requires a SECOND unlikely event (`net.http_post` returning NULL, not expected while `pg_net` is healthy) to ever manifest. Migration 134 is already applied to prod — per `supabase/migrations/CLAUDE.md`'s immutable-migration rule, fixing this now means authoring a THIRD migration (135) for a cosmetic diagnostic-string gap on a doubly-unlikely path. Not worth another apply+verify+review cycle in this batch; left for whoever next touches this trigger family. Ruling recorded in the SDD ledger.

## No-findings, with method shown

- **function_exception_swallow (primary question — does the nesting genuinely contain a telemetry-insert failure at all three call sites?)** — Traced PL/pgSQL exception scoping precisely, then confirmed against the LIVE deployed function (`pg_get_functiondef` via MCP `execute_sql`, byte-identical to the staged file): (1) the null-secret-guard `INSERT` is inside its own `BEGIN...EXCEPTION WHEN OTHERS THEN NULL; END;`, scoped before the outer `RETURN NEW;` — any exception there is caught locally and does not propagate. (2) the success-path `INSERT` (after `net.http_post`) is identically nested. (3) the critical one: the OUTER function-level `EXCEPTION WHEN OTHERS` handler's OWN telemetry `INSERT` is *also* wrapped in a nested `BEGIN...EXCEPTION WHEN OTHERS THEN NULL; END;`. This is the exact defect class documented in `078_fix_dispatch_proactive_coach_promotion_columns.sql`'s own header (migration 073's WHEN OTHERS handler re-raised on its own bad telemetry insert, which — because a PL/pgSQL EXCEPTION block cannot catch an exception raised within itself — escaped the trigger entirely and aborted every `rank_promotions` row). 134 closes that exact gap for this trigger family's third member. All three sites verified nested identically in both the staged file and the live `pg_get_functiondef` output.
- **guard_without_its_mirror (column usage across the 3 client_errors insert call sites)** — All three inserts use the identical 6-column list `(user_id, op_type, error_code, error_message, client_version, platform)` in identical order, with `client_version='server-trigger'`/`platform='server'` literal in all three.
