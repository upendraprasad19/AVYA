## Finding 1 — P1 — writer_reader_drift — ACCEPTED, FIXED

- **file:line:** `lib/features/auth/providers/auth_provider.dart:450-489`
- **claim:** The diagnose-doc said a stranded `signOutInProgress` is "mitigated
  by the `finally`". That holds only for a *thrown* exception. A `finally` runs
  when control LEAVES the `try`, and a never-resolving `await` never does. None
  of the four teardown steps carried a timeout, and
  `_supabase.client.auth.signOut()` is a network call — precisely the wedge
  class the sibling fix in this same commit (`applyRestoreCeiling`) exists for.
  A wedge there strands the flag ON forever, and since it is a process-global
  static it pins EVERY session on the device at `/sign-in` until restart.
  Second half: neither sign-out entry point debounces and `signOut()` had no
  re-entrancy guard, so two overlapping calls let the first-to-finish clear the
  flag while the other was still mid-teardown — reopening the exact window the
  fix closes.
- **verification:** `grep -n "\.timeout(" lib/features/auth/providers/auth_provider.dart lib/shared/repositories/user_repository.dart lib/core/services/hive_user_session.dart` → no matches in any of the three. `grep -rn "signOutInProgress" lib/` → 4 lines, no early-return guard.
- **fix applied:** `signOut()` now returns an in-flight `Future` so a second
  caller JOINS rather than races (`_inFlightSignOut`); teardown extracted to
  `_teardown()` and wrapped in `.timeout(signOutTimeout)` (20s) so control
  always leaves the `try` and the `finally` always runs. A timeout is reported
  as `auth_signout_teardown_incomplete`.
- **status:** fixed

## Finding 2 — P1 — writer_reader_drift — ACCEPTED IN PART, candidate REFUTED

- **file:line:** `docs/diagnoses/…-c9e4b7.md` `writers:` block
- **claim:** §4.1 requires naming the writer. The doc named only the reader-side
  bucketing methods and never named what set `current_phase=2` while
  `plan_start` stayed at the original date. Reviewer proposed
  `PhaseProgressReconciler._reconcileLocked` (writes only `{'current_phase':
  target}`, header says it advances "WITHOUT touching the in-progress plan"),
  arguing the true population would then be "every account the reconciler
  advances" — a materially larger blast radius.
- **verification:** `grep -rn "'current_phase':" lib/ --include="*.dart" | grep -v test` → 7 writers; read `phase_progress_reconciler.dart:130-145`.
- **triage:** The PROCESS half is accepted — the doc did fail §4.1 and now
  enumerates all 7 writers. The specific CANDIDATE is **refuted by the
  reconciler's own gate**, verified by reading it rather than taking the
  reviewer's word: it advances only when `reconciledPhase(currentPhase,
  completedBlocks)` is non-null, and `completedBlocks` comes from the STRICT
  `pastPhaseBlocks()`. An empty strict set — the founder's symptom — forces
  `completedBlocks == 0`, target null, write skipped. It is structurally
  incapable of producing "current_phase > 1 AND strict set empty", so the
  larger-blast-radius conclusion does not follow.
- **fix applied:** diagnose-doc now enumerates all 7 `current_phase` writers,
  records the reconciler refutation with its reasoning, and names the RESTORE
  path (`sync_service.dart:1102`) as the leading candidate — it writes
  `current_phase` from the cloud row while `plan_start_date` restores on a
  different path, which fits a fresh WEB session exactly. Recorded as *leading

- **status:** fixed (documentation); candidate false_alarm
