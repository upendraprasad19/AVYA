## Finding 3 — P2 — function_exception_swallow / guard_without_its_mirror
- **file:line:** `supabase/migrations/133_alert_critical_notify_trigger.sql:60-64` (the `EXCEPTION WHEN OTHERS THEN RETURN NEW;` block), contrasted with `supabase/migrations/073_proactive_coach_promotion_trigger.sql:31-42,88-105` (the precedent this migration's own comment cites as "same shape as 073").
- **claim:** 133's migration header and its `applied_migrations.json` note both explicitly claim "same shape as 073_proactive_coach_promotion_trigger.sql (... exception-swallowing, fire-and-forget pg_net dispatch)". That claim is only half true: 073's `EXCEPTION WHEN OTHERS` handler **also inserts an audit-trail row into `public.client_errors`** on failure (`op_type: 'proactive_coach_promotion_dispatch_failed'`, with `LEFT(SQLERRM, 500)`), and inserts a **success** telemetry row too (`op_type: 'proactive_coach_promotion_dispatched'`, carrying the `pg_net` `request_id`). 133's handler does neither — it is a bare `RETURN NEW;` with zero observability, on both the success path and the failure path. If `private.cron_get_secret()` starts throwing (permissions change, function drop) or `net.http_post()` itself raises (e.g. `pg_net` misconfigured), the failure is now **completely invisible** — no row anywhere, no log, nothing the founder's SessionStart alert-triage flow or any dashboard could ever surface. This is exactly the class CLAUDE.md's own `feedback_observability_silent_drop.md` names ("a rate-limited/best-effort sink must return a distinguishable response"), and it is a regression relative to the precedent this file claims to follow, not an improvement — note `078_fix_dispatch_proactive_coach_promotion_columns.sql` exists specifically because 073's telemetry columns needed a follow-up fix, which is evidence this repo has needed and relied on that telemetry, not that it's disposable boilerplate.
- **verification:** `grep -n "client_errors\|EXCEPTION WHEN OTHERS" supabase/migrations/073_proactive_coach_promotion_trigger.sql` vs. `grep -n "client_errors\|EXCEPTION WHEN OTHERS" supabase/migrations/133_alert_critical_notify_trigger.sql` (073 has both a success- and failure-path `INSERT INTO public.client_errors`; 133 has neither).
- **suggested-fix:** Add a failure-path (at minimum) `INSERT INTO public.client_errors(user_id, op_type, message, severity) VALUES (NULL, 'critical_alert_dispatch_failed', LEFT(SQLERRM, 500), 'warn')` inside the `EXCEPTION` block, mirroring 073. (Do not log to `public.alerts` itself for this — that would risk feeding the same trigger a new critical row; `client_errors` is the correct, already-established sink.)
- **status:** accepted, fixed in `supabase/migrations/134_alert_critical_notify_telemetry.sql` (separate commit, same batch, already applied live). ⚠ **The suggested-fix above was NOT used as written — it names the wrong `client_errors` columns.** Independently re-verified live via `information_schema.columns` before writing 134: the table has no `message`/`severity` columns at all (real: `error_code`, `error_message`, `client_version` NOT NULL, `platform` NOT NULL). Those exact wrong column names are what caused migration 073's original body to fail live and abort every `rank_promotions` INSERT — documented in `078_fix_dispatch_proactive_coach_promotion_columns.sql`, which 134 uses as its template instead (correct columns, plus the failure-path telemetry insert nested in its own `BEGIN/EXCEPTION WHEN OTHERS THEN NULL` block, matching 078's fix, so a telemetry-insert failure can never itself abort the parent alerts INSERT — 133 lacked this nesting entirely, which 073's original also lacked before 078). Live-verified post-apply: a rolled-back-transaction critical insert produced a correct `critical_alert_dispatched` / `error_code='info'` telemetry row.

## Finding 4 — P3 — guard_without_its_mirror
- **file:line:** `supabase/migrations/133_alert_critical_notify_trigger.sql:74-78` (`AFTER INSERT ... WHEN (NEW.severity = 'critical')`).
- **claim:** The trigger is `AFTER INSERT` only. Its mirror case — a row inserted as `info`/`warn` and later `UPDATE`d to `severity = 'critical'` — would never fire the Telegram push. I verified this is **currently dormant, not live-exploitable**: `grep -rn "UPDATE.*alerts\|alerts.*SET" supabase/migrations/*.sql supabase/functions` and a scan of every writer that touches `public.alerts` (`admin-dashboard-data`, `alert-critical-notify` (read-only), `telegram-admin-bot`, `founder_digest_content.ts`, and the three `alert_*` pg_cron functions in migration 076) show **zero** `UPDATE ... SET severity` sites anywhere in the tree today — every writer only ever `INSERT`s. So this is the same shape as this repo's own documented "dormant NULL-channel guard" class (OI-183): correct today, silently wrong the moment any future code path starts escalating an existing alert's severity in place instead of inserting a new row.
- **verification:** `grep -rn "UPDATE.*alerts\b" supabase/migrations/*.sql supabase/functions/**/*.ts` → 0 hits (besides this migration's own trigger definition, which is DDL not a data write).
- **suggested-fix:** No code change required now; add a one-line comment on the trigger (or a `COMMENT ON TRIGGER`) noting the AFTER-INSERT-only scope is deliberate and that any future `UPDATE ... SET severity` writer to `public.alerts` must add a mirror `AFTER UPDATE OF severity WHEN (NEW.severity = 'critical' AND OLD.severity IS DISTINCT FROM 'critical')` trigger or dispatch.
- **status:** accepted, fixed via `COMMENT ON TRIGGER` in `supabase/migrations/134_alert_critical_notify_telemetry.sql` (separate commit, same batch, already applied live) — verified live the comment is attached (`pg_catalog.obj_description` on the trigger).
