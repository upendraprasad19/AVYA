## Beyond the 5 lenses — adversarial digging

**Could `cappedHistory` or `chatRequestId` be undefined/out-of-scope at either log call site?**
Traced both declarations directly in `index.ts`:
- `chatRequestId` — declared `const chatRequestId = crypto.randomUUID().split("-")[0];` at line
  626, inside the same `serve(async (req) => { ... })` handler body, ~190 lines before either new
  log call (820, 835). Already referenced at lines 633 (existing warn) and 809 (`toolCtx.requestId`)
  before reaching the new call sites — no TDZ issue, no shadowing found via
  `grep -n "chatRequestId"` (7 total references, all consistent with one `const` declaration).
- `cappedHistory` — declared `const cappedHistory = capCoachHistory(history);` at line 817,
  immediately before the first new log line (820) and used again at 829 (`history: cappedHistory`)
  and inside the catch at 835. Same enclosing scope throughout. No possibility of
  undefined/out-of-scope at either site.

**Could the added `console.log` throw for any input shape (empty history, malformed history, huge
history)?** Read `capCoachHistory`'s full signature at `_shared/tool-loop.ts:158-169`:
`export function capCoachHistory(raw: unknown, opts: {...} = {}): Array<{role: string; text:
string}>`. Line 169: `if (!Array.isArray(raw)) return [];` — guards `undefined`, `null`, a string,
an object, anything non-array, to an empty array. `history` itself is destructured straight from
`req.json()` at line 180 with no prior validation (`const { message, snapshot_json, type, text,
context, image_base64, history } = ...`), so it is fully attacker/client-controlled arbitrary JSON
— exactly the "unknown" the function signature expects. Since the return type is always a real
array, `.length` at line 821 can never throw (`TypeError: Cannot read properties of
undefined/null`). For "huge history": `capCoachHistory` truncates to `maxEntries=16` internally
before returning (confirmed at `tool-loop.ts:166`, `opts.maxEntries ?? 16`), so `.length` is
bounded ≤16 regardless of input size — no risk of an absurdly long log line either. Confirmed
non-throwing for every input shape.

**Does the modified `console.error` still satisfy the CLAUDE.md-documented convention
(`console.error("[fn-name] request_id=X", err)` with `err` as a distinct final positional
argument)?** Read the modified call at lines 834-837:
```
console.error(
  `[ai-proxy] runToolLoop threw request_id=${chatRequestId} had_history=${cappedHistory.length > 0}`,
  loopErr,
);
```
`loopErr` remains the second, distinct positional argument — not stringified or interpolated into
the template literal. This matches the pattern at the file's outer catch (line 931:
`console.error(\`[ai-proxy] request_id=${requestId}\`, err_);`) and satisfies
`supabase/functions/CLAUDE.md`'s "never `JSON.stringify(err)` into the response body" convention
(that rule is about the HTTP response body specifically, but the log-call shape here also
independently preserves the two-argument convention). Confirmed compliant.

**Log-injection concern — could a malicious `history` entry's content leak into these log lines
and break log parsing?** No. `history_len=${cappedHistory.length}` interpolates a `number`
(`.length` of an array is always a `number` primitive) and `had_history=${cappedHistory.length >
0}` interpolates a `boolean`. Neither can contain newlines, ANSI escapes, or arbitrary text — a
number or boolean's string coercion is fixed-format and injection-proof by construction. The raw
`history` *content* (the `text` fields inside each entry, which genuinely are attacker-controlled
strings) is never touched by either new log line — only the post-cap array's `.length` is logged,
never any entry's `.text`. No injection surface introduced.
