### Finding 4 — P2 — the new backfill exemption in `migrationCountsInteractions` is defeatable by a same-statement data-modifying CTE and a block comment, and separately false-positives on an equally valid backfill ordering

**Claim under test:** `scripts/usage_counter_source_lib.dart`'s new `migrationCountsInteractions`
exempts a `count(*) FROM ai_coach_interactions` match only when the text between the previous `;`
and the match contains `insert into (public.)?usage_counters`. Its own doc comment says the
exemption is deliberately narrow and per-statement so "a future migration cannot buy an exemption
by name-dropping [the table]."

**Verification** (ran the real function against constructed inputs via a temporary scratch script,
deleted before this review ended):
```
migrationCountsInteractions(<real migration 129 text>)              = false   (correct, no FP)

migrationCountsInteractions(
  "... BEGIN
     WITH ins AS (
       INSERT INTO public.usage_counters (...) VALUES (NEW.user_id,'dummy_decoy',now(),0)
       ON CONFLICT (...) DO NOTHING RETURNING 1
     )
     SELECT count(*) INTO STRICT cnt
     FROM public.ai_coach_interactions
     WHERE channel = 'app' AND user_id = NEW.user_id ...")             = false   (BYPASSED)

migrationCountsInteractions(
  "... BEGIN
     /* insert into usage_counters : historical note, no longer used here */
     SELECT count(*) INTO cnt FROM public.ai_coach_interactions
     WHERE channel = 'app' AND user_id = NEW.user_id; ...")             = false   (BYPASSED)

migrationCountsInteractions(
  "WITH counts AS (
     SELECT user_id, count(*) AS c FROM public.ai_coach_interactions
     WHERE channel = 'new_channel' GROUP BY user_id
   )
   INSERT INTO public.usage_counters (user_id, quota_key, window_start, used)
   SELECT user_id, 'new_quota', now(), c FROM counts
   ON CONFLICT (...) DO NOTHING;")                                      = true   (FALSE POSITIVE)
```
Postgres always executes a data-modifying CTE exactly once even when unreferenced (documented PG
behaviour), so the first case is realistic, not just a text trick: a REAL, non-backfill quota
derivation placed after an earlier no-op `INSERT INTO usage_counters` **in the same top-level
statement** evades the gate entirely, because the checker only tests substring presence in the
preceding text, not that the counted value is what gets inserted. The second case shows
`stripSqlCommentsPreservingLines` only strips `--` line comments — unlike its sibling
`stripDartLikeCommentsPreservingLines`, which explicitly handles `/* */` too — so a block comment
containing the magic phrase silences the gate; no migration in this repo currently uses block
comments, so this is latent, not live. The third case shows the exemption is order-dependent: it
only recognizes "INSERT-then-count" text order (what migration 129 happens to use), not the
equally valid "CTE-then-INSERT" order, so a legitimate future backfill written the second way
would be wrongly blocked.

None of these three are exercised by `test/scripts/usage_counter_source_lib_test.dart`'s new
tests — its one adversarial case (`'a quota derivation is STILL caught in a file that also
backfills'`) uses TWO separate `;`-terminated statements, not one combined statement — nor by
`docs/audit/gate_test_ledger.yaml`'s mutation-proof entry for this gate (which proves the
statement-vs-file SCOPE mutation reddens 1/15, a different property).

**Suggested fix:** for the false negative, additionally require that the backfill statement's
INSERT target list and the counted expression are in the SAME statement with no intervening CTE
boundary that itself performs a write — or, more simply, require the count(*) match to be
textually inside a `SELECT` list that is itself the source of an `INSERT ... SELECT` (i.e. no
`WITH` between the `;` and the match). For the block-comment gap, extend
`stripSqlCommentsPreservingLines` to also blank `/* ... */` (as its Dart sibling already does).
For the false positive, extend the statement-boundary scan to also recognize a `WITH ... INSERT
INTO usage_counters` shape (checking whether the statement, once fully parsed to its next `;`,
targets `usage_counters` — not just whether the exemption text precedes the match).

**status: accepted**

### Finding 5 — P2 — `functionBlock` silently returns a corrupted, overlong block if a function ever uses a non-bare dollar-quote tag while a later function in the same file uses bare `$$`

**Claim under test:** `test/helpers/migration_cap_reader.dart`'s `functionBlock` doc comment
states: *"Every body in this repo opens `AS $$` and closes `$$;` with one consistent tag and no
nested dollar-quoting (verified across 111/114/127/128/129)."* The function itself finds the
match's position, then does `rest.indexOf(r'$$')` for the open tag and
`rest.indexOf(r'$$', open + 2)` for the close tag — it does not check that the SAME tag used at
the function's own `AS` clause is the one it's closing on.

**Verification:**
```
$ grep -rn "FUNCTION\s\+(public\.)\?\(enforce_chat_app_daily_limit\|enforce_vision_analysis_daily_limit\|enforce_food_text_daily_limit\)" supabase/migrations/*.sql
   ... (026, 111, 113, 114, 127, 129 — the complete set)

$ for f in 026 111 113 114 127 129; do dollar tags found in each: {$$}   # ALL SIX, only bare $$
```
So today the docstring's claim holds for real (I independently re-verified all 6, not just the 5
it names — 026 also uses bare `$$`). Feeding `functionBlock` a constructed function using
`$function$ ... $function$` immediately followed by an unrelated function using bare `AS $$ ...
$$;`:
```
functionBlock(altTagText, 'enforce_food_text_daily_limit')
  -> NOT NULL, and its content is BOTH functions concatenated together (the $function$-tagged
     function's full text PLUS the unrelated function's body, up to that function's own closing
     $$) — not an error, not the requested function's actual body.
```
With no later bare `$$` anywhere in the file, the same input correctly returns `null` (the safe
case). The dangerous case is specifically: differently-tagged function, followed later in the
same file by an unrelated bare-`$$` function.

Not triggered today (verified: all 6 real definitions use bare `$$`), but this is precisely the
"right file, wrong function" bug class `b8f4c2` already named and this helper exists to close —
migration 129 itself defines all three functions in one file for the first time, which is exactly
the shape (multiple functions, one file) that makes a tag mismatch reachable the moment any future
migration in this family departs from the bare-`$$` convention.

**Suggested fix:** after locating `open`/`close`, verify the substring at `open` matches a dollar
tag captured from the function's own `AS` clause (e.g. `RegExp(r'AS\s+(\$[A-Za-z_]*\$)')` applied
to `rest` before searching for the close), and search for THAT specific tag rather than the
literal `$$`.

**status: accepted**

### Finding 6 — P2 — the "no lib/ code inserts a GATED channel" test cannot see a channel value expressed as anything other than an inline string literal

**Claim under test:** `test/contracts/cap_triggers_use_usage_counters_test.dart`'s landmine-guard
group asserts no `lib/` writer inserts one of the four gated channels, via
`RegExp('''channel['"]?\\s*:\\s*['"]$channel['"]''')` matched against the captured insert-call
text.

**Verification:**
```
$ sed -n '55,65p' lib/core/services/app_events_service.dart
  static const String _channel = 'app_event';          # line 28, not shown in this range
  ...
      await SupabaseService.instance.client
          .from('ai_coach_interactions')
          .insert({
        'user_id': userId,
        'channel': _channel,
        ...
```
`app_events_service.dart` — one of the two positive-control writers this very test suite relies
on to prove the multiline matcher works — writes `'channel': _channel`, a reference to a
`static const` declared 35 lines above, not an inline literal. The channel-value regex requires a
quote character immediately after the colon; a bare identifier never matches it, for ANY of the
four gated-channel checks, regardless of what `_channel`'s value actually is. Today `_channel` is
`'app_event'` (correctly non-gated), so nothing is wrong in production — but the test provides

since `consume_quota`/`usage_counters` refuse non-service-role writers) — the gap is specifically
that this static contract test, whose entire purpose is to catch the mistake before it reaches a
real user, cannot.

**Suggested fix:** in addition to (or instead of) matching a literal after `channel:`, resolve a
bare identifier back to its `static const`/top-level `const` declaration in the same file (a
second regex pass: `RegExp('(?:static\\s+)?const\\s+\\w+\\s+$identifier\\s*=\\s*[\'"]([^\'"]+)[\'"]')`)
and check the RESOLVED value against the gated set. At minimum, add a code comment on
`_channel`'s declaration warning that changing its value bypasses this specific contract test.
