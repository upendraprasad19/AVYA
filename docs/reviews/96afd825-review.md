## Finding 4 — P2 — state-machine correctness (double-tap CONTINUE race)
- **file:line:** lib/features/auth/screens/sign_in_screen.dart:667-681 (`_buildEmailStepEnterEmail` CONTINUE `onPressed`); lib/features/auth/providers/auth_provider.dart:113-116 (`checkEmailRegistered`)
- **claim:** The CONTINUE button's tap-guard is `_buildPrimaryButton(isLoading: isLoading, ...)` where `isLoading` is derived from `ref.watch(authNotifierProvider).status == AuthStatus.loading`, computed once per `build()`. `checkEmailRegistered` sets `state = state.copyWith(status: AuthStatus.loading, ...)` synchronously as its first statement, but the resulting widget rebuild that disables the `InkWell.onTap` is deferred to the next frame (Riverpod's `notifyListeners` → `markNeedsBuild` doesn't force a synchronous rebuild). Two taps landing in the same frame (a fast real double-tap, or two near-simultaneous gesture recognitions) can both begin `checkEmailRegistered(email)` before either sees `isLoading == true`, firing the `email_is_registered` RPC twice and running the `if (!mounted || registered == null) return; setState(() { _emailStep = ... });` branch twice. There is no synchronous, same-frame reentrancy guard (e.g. a local field checked and set before the first `await`).
- **verification:** Read `_buildPrimaryButton` (`sign_in_screen.dart:1209-1258`) — `isDisabled = !enabled || isLoading` gates `InkWell.onTap`, but `isLoading` is a `build()`-time snapshot, not a live/synchronous check inside `onPressed`. No test in this diff exercises a double-tap scenario (`grep -n "double" test/auth/sign_in_screen_email_gate_test.dart` — no match).
- **suggested-fix:** Low practical severity — both concurrent calls check the same `email` value (captured once per tap from the same unedited controller) and are individually idempotent (deterministic same-`registered` result → same `setState` target), so the worst outcome is one extra RPC round-trip, not a wrong-step transition or data corruption. Still, the standard fix (a local `bool _checkingEmail` set synchronously at the top of `onPressed` and cleared in a `finally`) would close the window cheaply and is worth doing given this screen otherwise takes multi-tap-safety seriously (e.g. `isDisabled` gating elsewhere). Not release-blocking.
- **status:** fixed — added a synchronous `_checkingEmail` reentrancy guard (`sign_in_screen.dart`, `_buildEmailStepEnterEmail`'s CONTINUE `onPressed`) set before the first `await` and cleared in a `finally`; new regression test `test/auth/sign_in_screen_email_gate_test.dart` ("a same-frame double-tap on CONTINUE only fires checkEmailRegistered once") fires two taps in the same frame against a call-counting fake and asserts exactly one call.
