## Finding 1 — P1 — payment_integrity — FIXED
- **file:line:** supabase/functions/verify-payment/index.ts (the `users.update` path)
- **claim:** Replacing the upsert with pre-SELECT + insert left `users.subscription_expires_at`
  re-anchored to verify-time (`endDate = now + 30/365d`) while the canonical
  `subscriptions.end_date` stays at the webhook's value — so on the 23505-race path
  (and on any replay where the row already exists) the two tables diverge by
  seconds-to-minutes, and a late re-verify pushes the user's expiry forward.
- **verification:** `grep -n "subscription_expires_at" supabase/functions/verify-payment/index.ts`
- **fix:** Added `canonicalEndDateIso` — set to our `endDate` only when WE insert the row,
  and to the existing/race row's `end_date` otherwise (the pre-SELECT now selects
  `end_date`; the 23505 branch re-reads it). The `users.update` and the success response
  both use it. Pinned by `audit_2026_06_07_batch6_server_test.dart` ("users expiry uses
  the canonical row, not re-anchored").
- **status:** accepted (fixed)

## Finding 3 — P2 — payment_integrity — FIXED
- **file:line:** supabase/functions/razorpay-webhook/index.ts (replay-age guard)
- **claim:** `Math.abs(now - eventCreatedAtSec)` let a future-stamped event (clock skew or
  a crafted replay) within 300s of the future pass the replay gate.
- **verification:** `grep -n "ageSec" supabase/functions/razorpay-webhook/index.ts`
- **fix:** Signed age (no `Math.abs`); reject `> 300` (stale) OR `< -120` (future beyond a
  2-minute skew tolerance). The idempotency pre-SELECT + 23505 remain the backstop.
- **status:** accepted (fixed)
