## Finding 2 — P1 — writer_reader_drift (display reader)
- **file:line:** `lib/core/services/workout_schedule_read_service.dart:1334` (`getCurrentWeekNumber() => rawWeekNumber().clamp(1, 4)`, **unchanged** by this diff) read by `lib/features/train/providers/train_provider.dart:906-928` (`phaseArcProvider`) and rendered by `lib/features/train/widgets/phase_arc_strip.dart:96` (`isCurrent: (i + 1) == arc.currentWeek`)
- **claim:** This diff's own SoT-registry note (`docs/sot_registry.yaml`, `phase_arc_display` concept) says the fix makes a regen "stamp[] the row's TRUE week and cycle[] content via `contentFlavorIndex` instead of freezing on the last week or mislabeling week 6+ as week 1-4" — but the *display* half of `phase_arc_display` (which week is highlighted as "now") is not part of that fix and remains a raw clamp to `[1,4]`. Once a regen lands past week 4 — reachable **today**, in production, via the already-live `redoWeek4` extension (not gated behind the still-OFF `enable_hold_weeks`; this diff's own tests simulate exactly this via `redoWeek4`-style `plan_end` pushes) — `getCurrentWeekNumber()` returns **4 forever**, so the strip permanently highlights `waves[3]` ("DELOAD", and triggers the week-4 deload-reason banner via `arc.currentWeek == 4`) regardless of which of baseline/overreach/peak/deload the schedule rows actually cycle to for the real current week. Concretely: at real week 5, the schedule row correctly gets `contentFlavorIndex(5) == 0` ("baseline") per this diff's own fix, while the strip simultaneously tells the user they are in their deload week.
  `lib/features/train/CLAUDE.md`'s own `hold_week_identity` and `phase_arc_display` SoT rows already document this clamp as a known gap and note that `phase_arc_display` "reads `getCurrentWeekNumber()` DIRECTLY, not `weekIdentityProvider`, so it is a `hold_week_identity` surface that must be made hold-aware before OI-60 flips `enable_hold_weeks`" — but that framing is scoped to the not-yet-live `holdWeek` mechanism. `redoWeek4` is a **different, already-live** mechanism that reaches the exact same clamp bug today, and this diff (which explicitly targets "past week 4" regens) does not mention it as a residual gap anywhere in its docs.
- **verification:** Read `phaseArcProvider` (`train_provider.dart:906-928`) and `PhaseArcStrip.build` (`phase_arc_strip.dart:53-108`) directly — `currentWeek` comes from `getCurrentWeekNumber()` (clamped), `waves[i]` is read in raw array order from `currentWaveCharacters()`, and `isCurrent` is `(i+1)==currentWeek`. Confirmed `getCurrentWeekNumber()`/`rawWeekNumber()` are **not** in this diff's changed line ranges (only `contentFlavorIndex` is newly added beside them). This is not a *new* regression in the strict sense — the pre-fix code also unconditionally rewrote `current_plan` to the same canonical `[baseline,overreach,peak,deload]` order on every regen, so the mismatch existed before too — but this diff's paperwork describes the concept as now correctly serving the past-week-4 case without disclosing that the display's "now" indicator still does not.
- **suggested-fix:** either route `phase_arc_display`'s highlight through a cycle-aware index (`contentFlavorIndex(rawWeekNumber())` rather than a plain clamp) or, at minimum, add this as an explicit tracked residual gap (an OI, or an addition to `phase_arc_display`'s CLAUDE.md row) rather than leaving it implied-fixed by the diagnose-doc's wording.
- **status:** accepted (disclosure only, not a code fix) — a real fix means redesigning `hold_week_identity`'s clamp, a separate SoT concept with its own tests and explicit "clamped 4 is honest for some consumers" invariant; out of scope for this already-9-round-converged unit. ## Finding 3 — P1 — guard_without_its_mirror
- **file:line:** `lib/features/ai_coach/services/tool_dispatcher.dart:890-914` (`_executeRegeneratePlanBlock`) and `:1072-1096`-equivalent (`_executeSwitchGoal`, same shape)
- **claim:** Writer B (`workout_schedule_read_service.dart`'s `generateAndScheduleFromDate`) gained a dedicated `writeRangeIsNotEmpty` guard specifically to prevent "a blob rewrite backed by zero rows" (the diagnose-doc's own round-5 P0 description). Writer C's two new `current_plan` splices — introduced in this **same** diff, doing the **same kind of write** — have no equivalent guard. Both commit sites' write loops (`for (final schedule in rawSchedules) { ... if (existing is Map && existing['status'] == 'completed') { continue; } ... }`) can skip **every** row (the code's own comment calls this "Concurrent-edit safety net"/"completed days stay sacred" — i.e. an acknowledged, real race). The splice immediately below is gated only on `splicePhase != null && spliceRegenStartWeek != null` — a check about whether this was a normal (non-explicit-startDate) regen, with **no** connection to whether the loop above it actually wrote anything. So it is possible for `current_plan` to be rewritten with fresh cycled content while zero schedule rows back it — the exact defect class this same diff explicitly closed for the sibling writer, reopened for this one.
- **verification:** Read both method bodies in full (`tool_dispatcher.dart:829-920` and `:993-1096`). Both share the identical `continue`-on-completed shape immediately above an unconditional splice. Compared against writer B's gate: `final writeRangeIsNotEmpty = !today.isAfter(effectivePlanEnd); if (writeRangeIsNotEmpty) { ...splice... }` — writer C has nothing that plays this role; `spliceRegenStartWeek != null` answers a different question entirely (was this an explicit-startDate call), not "did any row actually land".
- **secondary consequence (verified):** if the splice's own internal casts throw (see Finding 4), the exception is caught by `ToolDispatcher.execute`'s outer catch-all (`tool_dispatcher.dart:228-236`, "Defensive — shouldn't happen since each handler should catch") **after** `clearCache` would have run — so `clearCache` is skipped and the user sees `'Could not execute that action.'` even though the write loop above had already committed real schedule-row writes. A partially-successful regen reports as a hard failure.
- **suggested-fix:** gate both splices on whether the write loop actually wrote at least one row (e.g. track a `wroteAny` bool alongside `results`/`errors` and only splice when `wroteAny` is true), mirroring writer B's intent for writer C.
- **status:** fixed — gated both splices on `results.isNotEmpty` (the loop's own existing tally, no new variable needed). New regression test "all rows already-completed race" drives a real `plan()`→`cache()`→`ToolDispatcher.execute()` call where every date is pre-marked completed, asserts `current_plan` stays byte-identical. Mutated (guard reverted): reddened exactly that one test (`+10 -1`), `Expected` the stale marker / `Actual` a freshly-regenerated blob — reverted, reconfirmed green.

## Finding 4 — P2 — missing_input
- **file:line:** `lib/core/services/workout_schedule_read_service.dart` (new splice, ~line 410-420) and both `tool_dispatcher.dart` commit sites (~890-913, ~1072-1096) — all three identical: `existingBlob['week_plans'] as List<dynamic>?` then `Map<String, dynamic>.from(existingWeekPlans[i] as Map)`
- **claim:** Both casts assume that if `current_plan`'s existing blob has a `week_plans` key at all, it is a `List` of `Map`s. Neither cast degrades gracefully on a violation — `x as List<dynamic>?` throws (not just returns null) if `x` is present and is anything other than a `List` or `null`; `existingWeekPlans[i] as Map` throws if entry `i` isn't a Map. This is inconsistent with the **pre-existing, same-file** reader `currentWaveCharacters()`, whose own doc comment states it is "Crash-safe: a missing / malformed / short blob returns `const []`" — i.e. the codebase's established posture for this exact blob already anticipates malformed shapes defensively; the new write-side splices (introduced identically 3×) do not carry the same posture.
- **verification:** Read `currentWaveCharacters()` (`workout_schedule_read_service.dart:1372-1380`) — explicit `if (raw is! Map) return const []`, `if (weeks is! List) return const []`, and a null-coalescing per-entry map read. Compared directly against the three new splice sites, which have no equivalent fallback for a present-but-wrong-shaped `week_plans`.
- **impact:** Low probability in normal operation (the app has only ever written this blob via `Phase.toMap()`, which reliably produces a `List<Map>`), but not purely theoretical given the reader's own defensiveness suggests malformed shapes have been observed/anticipated (legacy schema, hand-edited debug state, etc.). Failure mode is contained (caught by the outer catch-all, see Finding 3) rather than a hard crash, but produces a misleading "could not execute" error on what may be a partially-successful action.
- **suggested-fix:** mirror `currentWaveCharacters()`'s defensive pattern in the 3 new splice sites — treat a non-List/non-Map `week_plans` the same as "absent" (`existingWeekPlans = null`) rather than letting the cast throw.
- **status:** fixed — all 3 sites now use `is`-checked safe reads (`rawWeekPlans is List ? rawWeekPlans : null`, plus an `existingWeekPlans[i] is Map` guard before the per-element cast) instead of throwing `as` casts. Two new regression tests (not-a-List; List-with-non-Map-element), each driven through the real dispatch path, asserting no throw + fresh-content fallback. Mutated twice (one guard removed at a time, against the `_executeRegeneratePlanBlock` copy — the other two sites are byte-identical per this review's own answer to prompt 1): each sub-mutation reddened exactly its corresponding test and left the other green (`Expected: true / Actual: <false>` on `res.success`, the swallowed TypeError this finding's own "secondary consequence" predicted) — reverted, reconfirmed 11/11 green.
