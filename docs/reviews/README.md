# Code review findings — `docs/reviews/`

Generated by the `/review` skill (B-pass code reviewer) during this batch's commit prep.

## What lives here

One markdown file per code review, named `<staging-hash>-review.md` where the staging-hash is the SHA256 of the staged diff truncated to 12 chars.

Frontmatter fields:
- `reviewed_at` — ISO 8601 IST timestamp
- `staged_against` — git SHA or stage-hash
- `blast_radius` — feature | account | platform | catastrophic (per `docs/blast_radius.yaml`)
- `reviewer` — model + skill version (e.g. `claude-sonnet-via-skill`)
- `lens_set` — list of lenses run
- `findings_count`
- `verdict` — `pending` | `accepted` | `rejected`

## Why checked in (vs gitignored)

Audit trail. Future-you in 6 months will want to know: was this commit reviewed? What did the reviewer catch? What did the reviewer miss? Did we learn anything new?

The `docs/reviews/` history also feeds the self-evolution loop — when a lens consistently produces false positives, we can audit history + tune the prompt.

## When the gate enforces

- **blast-radius `feature`**: no review required. (Skip path.)
- **blast-radius `account` / `platform`**: review file is recommended but **not blocking**. The skill announces the recommendation at pre-commit time; founder decides.
- **blast-radius `catastrophic`**: review file with `verdict: accepted` is **required**. Gate `scripts/check_code_review_pass_exists.dart` blocks the commit otherwise.

## Triage workflow

For each finding:
- `accepted` — fix in same batch per `feedback_no_deferrals.md`
- `false_alarm` — annotate with reason; tunes the skill via self-evolution
- `spawn_followup_task` — emit a new task via `TaskCreate`

When ALL findings have non-`pending` status, set frontmatter `verdict: accepted` and the commit can proceed.
