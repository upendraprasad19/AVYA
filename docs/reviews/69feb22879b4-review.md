## Finding 2 — P2 — writer_reader_drift (data-quality / consent-timestamp semantics)

- **file:line:** `lib/core/services/auth_session_bootstrapper.dart:266-296` vs the migration SQL (POST-REVIEW: this migration file was removed from the batch after this review — see Founder triage notes; the same SQL now lives verbatim in the diagnose-doc's "Prepared backfill SQL" section, lines 23-26 of that block)
- **claim:** The OAuth/phone-OTP fallback in `hydrateFromCloud`'s `else` branch is gated purely on "Hive empty AND cloud empty" (`auth_session_bootstrapper.dart:258-266`), not on auth method — so it fires identically for any of the 19 pre-existing NULL email-signup rows if that user logs in again before migration 118 is applied (their Hive value is still empty because the old buggy write never once succeeded, satisfying the same `termsAcceptedAt is! String`/empty condition the comment attributes only to OAuth/phone-OTP). In that case the fallback stamps `terms_accepted_at = DateTime.now().toUtc().toIso8601String()` (line 285, "time of this login"), while migration 118 uses `created_at` (signup time) as its founder-approved proxy for the *exact same* rows (`118_backfill_terms_accepted_historical_rows.sql:24`, comment at lines 17-19: "consent was arguably given at signup time — `created_at` is used as the best-effort timestamp"). Migration 118's `WHERE terms_accepted_at IS NULL` (line 26) is not idempotent against an already-fallback-stamped row, so whichever happens first — an affected user's next login, or the founder applying the migration — silently and permanently decides which proxy semantics that user's DPDP consent record ends up with. Neither the diagnose-doc's `proposed_fix` (frontmatter) nor its `## Follow-ups` section mentions this interaction, and it isn't a hypothetical: the diagnose-doc's own live SQL sample shows the affected population is recently active (rows spanning 2026-06-26 → 2026-08-02).
- **verification:** Read `auth_session_bootstrapper.dart:258-296` next to `supabase/migrations/118_backfill_terms_accepted_historical_rows.sql:17-26` — confirm both target `users.terms_accepted_at IS NULL` for the same row population but source the stamp from two different columns/expressions (`DateTime.now()` vs `created_at`). `grep -n "terms_version = 'v1'\|AppConstants.termsVersion" supabase/migrations/118_backfill_terms_accepted_historical_rows.sql lib/core/constants/app_constants.dart` confirms the version string itself is consistent (`'v1'` both places) — only the timestamp proxy diverges.
- **suggested-fix:** Either (a) have the `hydrateFromCloud` fallback SELECT `created_at` alongside `terms_accepted_at` and use `created_at` as the stamp instead of `DateTime.now()` when backfilling a pre-existing row with no other Hive history (bringing both remediation paths onto the same semantic), or (b) explicitly call out and accept the race in the diagnose-doc's Follow-ups (e.g. "apply migration 118 before this branch reaches prod, to avoid any of the 19 rows being stamped with a login-time value instead of the created_at proxy"), so it's a documented decision rather than a silently-discovered one.
- **status:** accepted — fixed same batch. Implemented option (a): `auth_session_bootstrapper.dart`'s fallback now selects `terms_accepted_at, created_at` and stamps `row?['created_at'] ?? DateTime.now()...` instead of unconditionally `DateTime.now()...` — converges to the identical value migration 118 would produce, order-independent. `flutter analyze` clean on the touched file.

## Finding 3 — P2 — function_exception_swallow

- **file:line:** `lib/core/services/auth_session_bootstrapper.dart:293-295`
- **claim:** The fallback's inner `catch (_) { // Non-fatal — same spirit as the Hive-side write above. }` (wrapping the SELECT + conditional UPDATE + two Hive `.put()` calls, lines 277-295) has strictly worse observability than every other catch block in the same method — `hydrateFromCloud`'s other catches (lines 297-322, 452-460, 488-497) all pair a `debugPrint(...)` with an `unawaited(ErrorTelemetry.recordNonFatal(...))` call; this one has neither. Because this inner try/catch sits *inside* the pre-existing outer try (opened at line 222) whose own catch (lines 297-322) already calls `ErrorTelemetry.recordNonFatal` with Postgres-error-code classification (23505/23503), adding the inner catch doesn't just fail to add telemetry — it actively *suppresses* telemetry that would fire automatically if the inner try/catch were removed and the exception were allowed to propagate to the existing outer handler. If the fallback's SELECT/UPDATE starts failing systematically (an RLS policy change, a column rename, a scoped network/partition issue), the failure becomes exactly as silent and undetectable in production as the original 100%-failure-rate bug this diagnose-doc is about — with no telemetry signal for anyone to notice it, in the same file whose new debugging-skill entry (`.claude/skills/debugging/SKILL.md` §2.47, added by this same diff) explicitly instructs: "ask whether the catch is defending against an OCCASIONAL failure... or silently absorbing a GUARANTEED one."
- **verification:** `grep -n "catch (_)\|catch (e" lib/core/services/auth_session_bootstrapper.dart` then inspect the lines following each match for a paired `debugPrint`/`ErrorTelemetry.recordNonFatal` call — the block at 293-295 is the only catch in the file with neither.
- **suggested-fix:** Add `debugPrint('[AuthSessionBootstrapper.hydrateFromCloud] fallback terms stamp failed: $e');` plus `unawaited(ErrorTelemetry.recordNonFatal(e, st, reason: 'terms_fallback_stamp_failed', extra: {'user_id': user.id}));` inside the catch, matching this file's own established pattern (requires catching `(e, st)` instead of `(_)`) — or, more simply, delete the inner try/catch entirely and let the pre-existing outer catch (222-322) classify and log the failure, which is already wired up one level out.
- **status:** accepted — fixed same batch, exactly as suggested (kept the inner catch rather than deleting it, so a fallback-stamp failure doesn't get misclassified under the outer catch's 23505/23503 upsert-specific telemetry reason). Now catches `(e, st)`, `debugPrint`s, and calls `unawaited(ErrorTelemetry.recordNonFatal(..., reason: 'terms_fallback_stamp_failed', ...))`. `flutter analyze` clean.
