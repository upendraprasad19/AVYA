## Finding 4 — P3 — guard_without_its_mirror (concurrent drain race, mis-attributed safety claim)
- **file:line:** `lib/shared/providers/sync_state_provider.dart:56-65` (connectivity listener comment) and `lib/core/services/sync_queue.dart:227-235` (`drain()`)
- **claim:** The new comment states: *"`drain()` is documented idempotent, so firing on every reported change (including a flap) is safe — each op's own `_isDue` backoff check makes a redundant call a cheap no-op."* This mischaracterizes the actual protection. `_isDue(op, now)` (`sync_queue.dart:127-132`) is a **time-based backoff** check — it does nothing to prevent two *concurrent* `drain()` calls from both `_loadAll()`-ing the same op, both evaluating `_isDue` as true (no attempt has been recorded yet by either), and both calling `_runOne(op)` — and therefore the op's `executor` — at the same time. With the periodic timer now firing every 5 minutes AND the connectivity listener firing on every reported change (mobile/WiFi flapping in an elevator, a tunnel, a handoff between towers can produce several events within seconds), overlapping `drain()` invocations are now routine rather than requiring a user to double-tap Retry (the only pre-existing overlap risk). `drain()` itself has no in-flight guard (`SyncQueue` has no `_draining` boolean or mutex anywhere in the class). In practice this is currently low-impact because both registered executors (`_executeUserProfileUpsert` via Postgres `upsert(...).onConflict(...)`, `_executeUserProgressSync` via re-read-then-push) are idempotent by construction — but that safety comes from the *executors'* design, not from `_isDue`, and the comment attributes it to the wrong mechanism.
- **verification:** Read `_isDue` (`sync_queue.dart:127-132`) and `drain()` (`:227-235`) — confirmed no per-op or global concurrency lock exists; `_isDue` only compares `DateTime.now()` against `op.lastAttemptAt + backoff`, both of which are unchanged until `_runOne` completes and calls `_persist`/`_remove`. Read both registered executors (`sync_service.dart:695-772`) — confirmed both wrap Supabase calls in `try/catch` returning `Result`, and both are semantically safe to double-fire (upsert / re-read-and-push), which is why this hasn't manifested as a visible bug yet.
- **suggested-fix:** Either add a simple in-flight boolean guard to `drain()` (`if (_draining) return; _draining = true; try { ... } finally { _draining = false; }`), or correct the comment to state the real invariant ("safe today because every registered executor is independently idempotent — not because `_isDue` prevents concurrent execution") so a future non-idempotent executor registration doesn't inherit a false sense of safety from this comment.
- **status:** accepted — did BOTH: added the in-flight `_draining` guard to `drain()` exactly as suggested (structural + mutation-proof test added), and corrected the misattributed comment in `sync_state_provider.dart` and the diagnose-doc's `impact_analysis`.
