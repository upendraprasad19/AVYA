## Finding 3 — Medium — guard_without_its_mirror
- **file:line:** `test/contracts/admin_metrics_functions_role_revoke_test.dart:109-120` (the `exemptAlreadyAppliedWithFollowOnRevoke` set and its `continue`)
- **claim under test:** Is the exemption scoped narrowly enough that it cannot silently cover a case it wasn't written for?
- **verification:** Read the loop body (lines 117-127): `if (exemptAlreadyAppliedWithFollowOnRevoke.contains(name)) continue;` fires BEFORE the file is scanned for which `founder_metrics_*` function(s) it touches (`touching.allMatches(sql)` on line 125). The exemption is therefore **file-level**, not **function-level**. Both exempted files (135, 136) currently touch only `founder_metrics_ops()` — confirmed by reading both files in full — so today the file-level and function-level scopes coincide and there is no live gap. The mirror case the review brief asked about: if migration 135 or 136 were ever edited in the future to ALSO touch a *different* `founder_metrics_*` function (e.g. `founder_metrics_engagement`), that touch would be silently exempted too, because the file-level `continue` skips the whole file before any function is even extracted from it — the guard cannot distinguish "the one function this exemption is about" from "any function this file happens to touch." This is guarded today only by the process rule that an applied migration is immutable (`supabase/migrations/CLAUDE.md`, "An APPLIED migration is IMMUTABLE") — and that same file documents that this exact rule has already been violated once in this repo (migration 127's header comment was edited post-apply, caught only by a later review recomputing the sha256 by hand, per `supabase/migrations/CLAUDE.md`'s "b8f4c2" section). The mirror gap is real but requires a second, already-once-observed process violation to bite.
- **suggested-fix:** Either (a) tighten the exemption to be function-scoped — e.g. a `Set<(String file, String fn)>` checked after `fns` is computed, so an exemption for `135 → founder_metrics_ops` doesn't cover `135 → founder_metrics_engagement` if 135 is ever (improperly) edited to touch a second function — or (b) leave as-is but add a one-line comment acknowledging the file-level (not function-level) scope so a future reader doesn't assume it's already function-scoped. Not blocking: the immutability rule is the primary defense, and it's a documented, self-attested trust boundary consistent with this repo's established pattern (rule 21's `presence_only:`, rule 24's ledger).
- **status:** fixed — took option (a). `exemptAlreadyAppliedWithFollowOnRevoke` is now a `Set<(String, String)>` of `(filename, function)` pairs, checked after `fns` is computed inside the `for (final fn in fns)` loop, not as an early file-level `continue`. Re-mutation-proven: (1) commenting out migration 137's revoke line still reddens exactly the pinning test; (2) replacing the pair-check with `if (false)` still reddens exactly the original replay-guard test, naming migration 135 — both restored clean, 3/3 green.
