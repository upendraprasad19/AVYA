# Code Review — Round 2 — 1cf9f51d2565

## Finding 1 — P0 — oncontinueanyway_reachability
- **file:line:** `lib/features/auth/screens/restoring_screen.dart` `initState` (timer wiring) vs. `_kickoffRestore()`'s `await destinationFuture`, and the round-1 stamp guard in `_onContinueAnyway`
- **claim:** Round 1's diagnose-doc and SoT registry note both asserted "`_onContinueAnyway` can only be tapped while `_goHome` is already in-flight... cannot mis-onboard a new/mid-onboarding user." This was false. `initState` starts `_timeoutTimer` (30s) independently and concurrently with `_kickoffRestore()` — the timer is wall-clock, not conditioned on which switch branch `_kickoffRestore` eventually enters. `_kickoffRestore` first `await`s `destinationFuture` (`AuthSessionBootstrapper.instance.resolveDestination(user.id)`), a real network round trip to Supabase with no client-side timeout of its own. If that single query takes longer than 30 seconds (plausible on this app's own stated target demographic — India mobile users — and the file's own Theme-D comments cite a founder-measured 35.9s *total* restore), the CONTINUE CTA becomes visible and tappable **before `_kickoffRestore` has entered any switch branch at all** — before it's known whether the user is brand-new, mid-onboarding, or returning. Tapping CONTINUE in that window ran `_onContinueAnyway`, which (post round-1 fix) unconditionally stamped `UserRepository.instance.setOnboarded()` and navigated to `/home`, permanently setting the LOCAL `onboarding_completed` flag to `true` for a genuinely new or mid-onboarding user with no in-app path back to onboarding on that device.
- **verification:** Read `initState` — confirms `_timeoutTimer` starts unconditionally before `_kickoffRestore()` is even called. Read `_kickoffRestore` in full — confirms the `switch` on `destination` only begins after `await destinationFuture` resolves. Read `AuthSessionBootstrapper.resolveDestination` — confirms a live Supabase network call with no client-side timeout. Confirmed independently by the implementing agent (not just accepted from this review) before applying the fix.
- **suggested-fix:** Track classification state explicitly instead of relying on timing coincidence — a `_committedToGoHome` field set `true` only inside the `GoHome` and `ResumeOnboarding`-self-heal branches immediately before calling `_goHome`, gating `_onContinueAnyway`'s stamp on that flag rather than on elapsed wall-clock time.
- **status:** fixed — added `bool _committedToGoHome = false` field, set `true` at both `_goHome` call sites (the `GoHome` case and the `ResumeOnboarding` self-heal branch), and changed `_onContinueAnyway`'s guard to `ownershipOpen && _committedToGoHome && !UserRepository.instance.isOnboarded`. Navigation itself (`context.go(...)`) stays unconditional, matching pre-diff behavior exactly for the pending-classification edge case — only the flag-stamp side effect is now gated correctly. Diagnose-doc and SoT registry corrected to remove the disproven reasoning rather than leave it standing. `flutter analyze` clean; source-grep regression test (tightened to require 3 guard occurrences) + all 3 behavioral tests + the full `test/auth/` suite (66 tests) green after the fix.
