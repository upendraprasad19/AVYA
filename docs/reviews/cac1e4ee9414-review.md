## Finding 1 — P1 — guard_without_its_mirror

- **file:line:** `lib/features/auth/providers/auth_provider.dart:721-728` (the OI-205 `confirmEmailAuthGuardState` check) interacting with the new guard at `:743`
- **claim:** The new `ensureSupabaseReady()` guard is placed AFTER the pre-existing OI-205 "already authenticated" guard, but the OI-205 guard's `alreadyAuthenticated: _supabase.isAuthenticated` read (line 723) happens *before* Supabase is guaranteed initialized, and `SupabaseService.isAuthenticated` (`lib/core/services/supabase_service.dart:97-100`) unconditionally returns `false` while `_initialized` is false — regardless of whether the device actually holds a valid, persisted Supabase session in local storage. On a cold `/confirm` load (which this very diagnose-doc establishes is the *normal* case, not an edge case) where the browser/device already has a persisted session from a previous sign-in, the OI-205 guard will therefore always read "not authenticated" and let execution proceed to `state = loading` → `ensureSupabaseReady()`. `ensureSupabaseReady()` → `SupabaseService.initialize()` → `Supabase.initialize()` → `SupabaseAuth.initialize()` **synchronously restores that persisted session** whenever local storage holds any access token — verified directly in the pub-cache source, not assumed: `supabase_flutter-2.17.1/lib/src/supabase_auth.dart:107-125` calls `await Supabase.instance.client.auth.setInitialSession(persistedSession)` as part of the same awaited chain `ensureSupabaseReady()` sits on. Execution then falls straight into `try { await boundSignIn(() => _performConfirmEmail(tokenHash)); }` (line 752) — `confirmEmailAuthGuardState` is **never re-checked** after Supabase becomes ready. `_performConfirmEmail` calls `verifyOTP` for whatever account the link belongs to and, on success, signs the app into that account (`_ensureLocalUser`, line 863) — silently switching the device away from the just-restored, previously-signed-in user, with none of OI-205's intended "You're already signed in. Sign out first to confirm a different account." refusal ever shown. This is exactly the silent-account-switch class OI-205 was shipped one week earlier (2026-09-16) to close, reopened specifically for the cold-load path this diff newly makes reachable — pre-fix, a cold `/confirm` load never got past the `LateInitializationError` (see the diagnose-doc's own root cause), so this ordering hazard was structurally unreachable in production before today. Per `_ensureLocalUser`'s own cross-account guard (`auth_provider.dart:1089-1150`, `HiveUserSession.openForUser` namespace-isolates the boxes), this is not a raw Hive data leak — but it is a silent, un-consented account switch, i.e. the exact "missing consent signal" character this codebase's own docs use for this bug class (`lib/features/auth/CLAUDE.md`'s OI-205 pitfall row).
- **verification:**
  `grep -n "isAuthenticated" lib/core/services/supabase_service.dart` → confirms the unconditional `if (!_initialized) return false;` short-circuit (lines 97-100). `grep -n "setInitialSession\|hasPersistedSession" "C:/Users/upend/AppData/Local/Pub/Cache/hosted/pub.dev/supabase_flutter-2.17.1/lib/src/supabase_auth.dart"` → confirms the synchronous session restore inside the awaited `initialize()` chain (lines 107-125). - **suggested-fix:** Re-evaluate `confirmEmailAuthGuardState` (or at minimum re-read `_supabase.isAuthenticated`) *after* `ensureSupabaseReady()` returns `true` and *before* calling `_performConfirmEmail` — not only before it. This changes the property the existing OI-205 doc comment asserts ("Checked BEFORE the loading state so a blocked attempt never touches Supabase at all") since Supabase now has to become ready before its own auth state can be trusted; that assumption needs to be revisited as part of this fix, not patched around it.

Both comment blocks rewritten to state the corrected reasoning (the old "checked before the loading state so Supabase is never touched" claim was retired — it was never a deliberate safety property, only an accident of the pre-fix crash). Added a source-order pin test (`confirm_email_readiness_behavioral_test.dart`'s new group) asserting `ensureSupabaseReady()`'s call precedes `confirmEmailAuthGuardState`'s in source; mutation-proven by swapping the two blocks and confirming the test reds, with a genuine second-order catch along the way — the test's first draft used a bare `body.indexOf('ensureSupabaseReady()')` match, which stayed GREEN under the swap because a surrounding comment also contains that literal substring; fixed by matching the exact statement `if (!await ensureSupabaseReady()) return;` instead. ## Finding 2 — P2 — guard_without_its_mirror

- **file:line:** `lib/features/auth/providers/auth_provider.dart:743` (new guard), vs. the `boundSignIn` ceiling at `:752` and the comment at `:745-751`
- **claim:** `ensureSupabaseReady()` sits *outside* `boundSignIn`'s `signInTimeout` (40s) ceiling — identical in shape to the pre-existing gap in `signInWithEmail` (`:268`, also outside its own `boundSignIn` call at `:270`). That mirrored placement is not itself new, but the new code's own comment immediately above the `try` block explicitly argues the unbounded-hang risk matters *more* for `confirmEmail` than for `signInWithEmail`, precisely because it "fires automatically on mount, with no prior user gesture, so an unbounded hang here is worse, not better, than the sign-in case it borrows the ceiling from" (`:749-751`). Despite that stated rationale, the guard most likely to hang under a bad connection — `ensureSupabaseReady()` → `SupabaseService.initialize()` → `SupabaseAuth.initialize()`, which awaits local storage plus `Supabase.instance.client.auth.setInitialSession`/`onAuthStateChange` wiring — is placed precisely outside the ceiling the comment invokes. If `initialize()` hangs (the same backend-brownout shape diagnose `a9c4e2` documents for sign-in), the screen stays on `AuthStatus.loading` ("Confirming your account...") with no timeout-driven error ever surfacing. The only escape is the always-visible manual "GO TO SIGN IN" link (`lib/features/auth/screens/confirm_email_screen.dart:161-167`), not the bounded ceiling the surrounding prose implies is protecting this path.
- **verification:** `grep -n "boundSignIn\|ensureSupabaseReady" lib/features/auth/providers/auth_provider.dart` — confirms `ensureSupabaseReady()` (line 743) precedes `try` (line 744)/`boundSignIn` (line 752) in `confirmEmail`, and that `signInWithEmail` (`:266-298`) has the identical ordering. Read `SupabaseService.initialize()`/`_doInitialize()` (`supabase_service.dart:33-55`) — no internal timeout on `Supabase.initialize()`.
- **suggested-fix:** Either wrap `ensureSupabaseReady()` itself in a short bound for this call site, or move it inside `boundSignIn`'s ceiling (accepting that a not-ready failure then also consumes part of the 40s budget). At minimum, soften the comment's claim so it doesn't imply full ceiling coverage that isn't actually there yet. This is a pre-existing pattern shared with `signInWithEmail`, not unique to this diff — but this diff is the one that newly argues, in its own words, why it matters more here.
- **status:** accepted, resolved via the review's OWN "at minimum" bar rather than a new timeout wrapper — investigated the real risk first rather than assuming: `SupabaseAuth.initialize()`'s session-restore path (`setInitialSession`) is synchronous, local-storage-only work with no network I/O, so the realistic hang surface is narrow, not the same shape as `verifyOTP`/`_ensureLocalUser`'s cloud round-trips that motivated `signInTimeout` originally. The comment above `boundSignIn` now states this precisely instead of implying full ceiling coverage. A real fix (bounding `ensureSupabaseReady()` itself) is a shared-helper change affecting `signInWithEmail`/`checkEmailRegistered` too — disproportionate to do unilaterally inside this fix, same reasoning the original email-confirm-ux-bpass Finding 4 used for a comparably-scoped gap. The existing always-visible "GO TO SIGN IN" escape link remains the mitigation if this is ever wrong in practice.
