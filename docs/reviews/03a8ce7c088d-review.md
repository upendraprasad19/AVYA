## Finding 2 — P2 — sign_in_cross_button_reentrancy
- **file:line:** `lib/features/auth/screens/sign_in_screen.dart:307-313` (Google button) vs `:362-385` (CONTINUE button's `_checkingEmail` guard)
- **claim:** The redesign merges the Google-OAuth entry point and the email-registration-check entry point onto the *same* `_buildMainView` (previously they lived on different `_SignInView` values — `main` vs `email` — so they could never be interacted with concurrently). The CONTINUE button is protected by the synchronous `_checkingEmail` field (set before any `await`, per the existing comment at `sign_in_screen.dart:71-76` citing a prior B-pass finding for the *same-button* double-tap case). The `ENLIST VIA GOOGLE` button, however, is gated *only* by `isLoading` (`onPressed: isLoading ? null : () => authNotifier.signInWithGoogle()`), which is derived from `authState.status == AuthStatus.loading`. I traced `AuthNotifier.checkEmailRegistered` (`lib/features/auth/providers/auth_provider.dart:156-157`): its first statement synchronously sets `state = state.copyWith(status: AuthStatus.loading, ...)`, but per the existing code comment, that state change only disables consuming widgets on the *next frame* — the frame in which CONTINUE was tapped still has the old, not-yet-rebuilt Google button with its original (non-null) `onPressed` active. A tap landing on the Google button within that same frame (a second, near-simultaneous touch point — i.e., genuine multi-touch, not a single-finger double-tap) would invoke `signInWithGoogle()` while `checkEmailRegistered`'s RPC is still in flight, racing two concurrent auth operations against the same `AuthNotifier`/`authState`. Both eventual outcomes are individually `mounted`-guarded (no crash), but if `checkEmailRegistered` resolves and transitions `_currentView` to `.email` while Google's OAuth later resolves to `AuthStatus.success`, `ref.listen`'s `AuthStatus.success` branch (`sign_in_screen.dart:152-184`) fires regardless of `_currentView` and force-navigates to `/restoring`, silently discarding whatever the user was doing on the email step.
- **verification:** `grep -n "signInWithGoogle\|checkEmailRegistered\|AuthStatus.loading" lib/features/auth/providers/auth_provider.dart` to confirm both methods independently set `status: AuthStatus.loading` as their first statement with no mutual-exclusion guard between them. Read `lib/features/auth/screens/sign_in_screen.dart:306-385` to confirm the Google button's `onPressed` has no `_checkingEmail` (or equivalent) check.
- **suggested-fix:** Gate the Google button's `onPressed` on `isLoading || _checkingEmail` too (mirroring the CONTINUE button), or introduce a single shared `_anyAuthActionInFlight` bool set synchronously at the top of *every* main-view action handler. Given this requires genuine simultaneous multi-touch to trigger (not a realistic single-finger double-tap), I'd call this low real-world likelihood but cheap to close — two-line fix.
- **status:** fixed — gated both the Google button and the (flagged-off) phone button's `onPressed` on `isLoading || _checkingEmail`, matching the CONTINUE button's existing guard (`sign_in_screen.dart`). `flutter analyze` clean; full relevant test subset re-run and green.
