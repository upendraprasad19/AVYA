### Finding 2 — P2 — silent-failure — Saved Photos delete gives no feedback on failure
- file:line: `lib/features/profile/screens/saved_coach_photos_screen.dart:71-73`
- claim: `_delete()` shows a "Delete photo?" confirmation dialog, then `final ok = await
  _repo.delete(path); if (ok) await _load();` — with no `else`. `CoachMediaRepository.delete`
  swallows every Storage error internally (`catch (e) { debugPrint(...); return false; }`, `lib/features/ai_coach/repositories/coach_media_repository.dart:186-195`),
  so on any failure (RLS denial, network drop, transient Storage error) the screen does precisely
  nothing after the user confirms deletion — no SnackBar, no error state, no retry. The user has
  no way to tell a failed delete from a successful one that just didn't refresh. This is the exact
  pattern this repo's own `lib/features/ai_coach/CLAUDE.md` common-pitfalls table names explicitly
  ("every save action that mutates data MUST give the user a confirmation signal, even if the
  success is just a card vanishing") — and the very same batch's `_onSaveCoachMedia` (in
  `chat_area.dart`) does follow that discipline (SnackBar on `!saved`), making the omission here an
  inconsistency within the diff itself, not just a general gap.
- verification: Read `lib/features/profile/screens/saved_coach_photos_screen.dart:52-73` directly
  — confirmed no `else`/failure branch after `_repo.delete(path)`. Read
  `coach_media_repository.dart:186-195` (`Future<bool> delete(String path)`) — every throw path
  inside is caught and converted to `return false;` with only a `debugPrint`. Compared against
  `chat_area.dart`'s `_onSaveCoachMedia`, which calls `ScaffoldMessenger.of(context).showSnackBar(...)`
  when `!saved`.
- suggested-fix: On `ok == false`, surface a SnackBar (e.g. "Couldn't delete that photo — please
  try again"), mirroring `_onSaveCoachMedia`'s existing failure-feedback pattern from the same
  batch.
- status: fixed — added the SnackBar (same copy/styling as `_onSaveCoachMedia`'s failure path);
  new regression test `test/widgets/saved_coach_photos_screen_test.dart` (source-grep, honestly
  labelled — no DI seam to mock a failed live Storage delete, same reason this repo's other
  Storage-touching tests in this batch are source-grep).

- **writer_reader_drift**: Traced every writer/reader of `mediaStoragePath`, `mediaAnalysisComplete`,

  `recordMediaSaveDecision` (`:139-147`) always writes a non-null `'saved'`/`'declined'` string,

## Additional checks performed (considered, no finding)

- **`_savingCoachMediaKeys` mutual exclusion** (`chat_area.dart`): both `_onSaveCoachMedia` and
  `_onDeclineCoachMedia` do a synchronous check-then-add (`if (_savingCoachMediaKeys.contains(coachKey))
  return; setState(() => _savingCoachMediaKeys.add(coachKey));`) with no `await` between the check
  and the add, so a same-tick double-tap can't race past it on Dart's single-threaded event loop;
  both release in `finally`; both guard the same field. Correct.
- **`CoachMediaRepository._destinationExists` idempotency check**: uses `SearchOptions(search:
  fileName, limit: 1)` then re-verifies `objects.any((o) => o.name == fileName)` — the exact-name
  check after the (possibly fuzzy) server-side search means a substring/prefix match on the search
  API can't produce a false positive. The "stale leftover object at the same path" scenario the
  task asked me to consider would require a storage-path collision (`<uid>/<epoch-ms>.jpg`) between
  two different photos for the same user — that collision risk is pre-existing in `media_picker.dart`'s
  upload path (`DateTime.now().millisecondsSinceEpoch`, unchanged by this diff), not introduced or
  worsened here.
- **`ChatMessage.copyWithMediaState`'s null handling**: `mediaSaveState: mediaSaveState ??
  this.mediaSaveState` means the method can never explicitly clear `mediaSaveState` back to null —
  a caller passing `null` gets "keep existing," not "clear." Initially flagged this as a landmine,
  then found `test/contracts/coach_media_repository_test.dart:98-112` pins this exact behavior as
  *intentional* ("null args mean 'keep existing value', not 'clear to null'") and confirmed no
  current call site ever needs to clear it (the one call that passes `mediaSaveState: null` —
  `_onSaveCoachMedia`'s failure path — is a no-op against an already-null field, matching its own
  "leaves mediaSaveState untouched" doc comment). Deliberate, tested design, not a bug.
- **`ChatBubble.isSavingMedia` wiring**: traced end-to-end from `_savingCoachMediaKeys.contains(message.coachKey)`
  in `chat_area.dart` through the `ChatBubble` constructor call to the spinner/label swap inside
  `_buildMediaConsentChip()`. Fully wired, not partial.
  `test/widgets/chat_bubble_media_consent_test.dart`'s `isSavingMedia in-flight state` group
  exercises both tap-targets disabled + spinner-vs-icon swap.
  - Migration 116 idempotency: `DROP POLICY IF EXISTS`-equivalent `DO $$ ... IF EXISTS ... DROP
  POLICY ... END $$;` pattern before `CREATE POLICY`, matching migration 070's own established
  idiom exactly. No live-apply risk beyond the standard pattern already used elsewhere in this
  repo.
