## Finding 3 — P2 — timer_async_correctness (two minor, non-blocking observations)
- **file:line:** `lib/core/services/day_rollover_service.dart:301-309` (`durationUntilNextIstMidnight`'s defensive `while` loop) and `:94-105`+`:272-287` (the three-trigger `_checkAndRollover` check-then-act shape)
- **claim (a):** The `while (!nextMidnightUtc.isAfter(now)) { nextMidnightUtc = nextMidnightUtc.add(const Duration(days: 1)); }` guard is, by construction, currently unreachable: `istMidnightUtc(nowWall())` is always the midnight of the calendar day containing `now`, so it is always `<= now`; adding one day therefore always yields a result `> now` on the very first pass (verified algebraically for all 4 arithmetic test cases, including the exact-midnight boundary case). This isn't a bug — the arithmetic is correct either way, and defensive coding against a future DST/offset change is reasonable — but test 3's own `reason:` string ("the defensive while-loop guard exists for exactly this shape of input") overstates what that specific input actually exercises: the loop body never executes for it.
- **claim (b):** `_checkAndRollover()` is a non-atomic check-then-act (`configBox.get(_hiveKey)` compared to today, and only later — inside `_doRolloverWithRef` — is the new date `put` back). Two of the app's three triggers (the new foreground `Timer`, and the pre-existing `didChangeAppLifecycleState` resume) both call it unguarded by any mutex. If both fire within the same short async window (e.g. the app resumes at almost exactly the synthetic/real midnight the Timer is also about to fire on), both could read the stale date before either writes the new one, running the full `_doRolloverWithRef` body (and its ~24 provider invalidations + `refillIfNewWeek` + `reckonStreakDecayAndPersist` + `DeloadEvaluator.maybeEvaluate`) twice. This is NOT introduced by this diff — the same shape already existed between two resume events, or resume vs. cold-launch's unconditional `runRolloverNow` — and every operation inside `_doRolloverWithRef` is independently idempotent by the codebase's own design (`refillIfNewWeek`'s own doc comment: "Idempotent — same Monday twice is a no-op"; `ref.invalidate` is inherently idempotent), so I'm not treating this as blocking. The new Timer trigger simply adds a third party to a pre-existing race window rather than creating a new class of harm.
- **The specific race the brief asked me to scrutinize (`dispose()` vs. an in-flight `_onMidnightTimerFired`) is CLEAN**, verified two ways: (1) by direct trace — `_onMidnightTimerFired`'s body has no `await` before the `if (_attached) { _scheduleMidnightTimer(); }` re-arm check (the `unawaited(_checkAndRollover())` call kicks off the async chain and returns control synchronously without yielding), so Dart's single-threaded, run-to-completion semantics mean `dispose()` cannot interleave between the timer firing and that check; `dispose()` and `_onMidnightTimerFired` are always strictly sequential, never concurrent, in a single isolate. (2) empirically — I mutated the `ref.invalidate(streakFreezeProvider)` line, confirmed reddening, then separately ran `test/contracts/day_rollover_midnight_timer_test.dart`'s real-Timer end-to-end test and confirmed via log output (`[DayRollover] Foreground midnight timer fired.` → `[DayRollover] Date changed: 2026-09-28 → 2026-09-29`) that the Timer genuinely escapes FakeAsync and fires correctly with no resume/cold-launch call in the picture.
- **verification:** Algebraic trace of `istMidnightUtc`/`istDateOf` (`lib/core/utils/ist_date.dart:82-109`) against all 4 arithmetic test cases in `test/contracts/day_rollover_midnight_timer_test.dart`. Ran `flutter test test/contracts/day_rollover_midnight_timer_test.dart` (6/6 pass, real-Timer log confirms genuine firing) and `flutter test test/contracts/day_rollover_provider_invalidation_behavioral_test.dart` (5/5 pass).
- **suggested-fix:** None required to merge. Optionally: soften test 3's `reason:` string to not claim the loop iterated when it didn't; optionally add a per-date-key lock (matching `WorkoutWriteService`'s own `_acquireLock` pattern) around `_checkAndRollover` if the founder wants to close the theoretical double-invalidation window, but given universal idempotency downstream this is a "nice to have," not a defect.
- **status:** no_change_needed — both sub-findings are non-blocking per the review's own framing (dead code under the current fixed-IST-offset assumption, kept as cheap defensive insurance rather than removed; a pre-existing race the new Timer trigger joins but does not introduce or worsen, already mitigated by downstream idempotency). No code change made.
