- **file:line:** `lib/features/ai_coach/screens/muster_screen.dart:78-91`

## Finding 5 — P4 — asserted_fixture_value
- **file:line:** `test/contracts/mobile_frame_mediaquery_test.dart:87-118`; `lib/app.dart` (`MobileFrame.build`, the `frameH`/`frameW`/`contentWidth`/`contentHeight` formula)
- **claim:** The wide-viewport test's `expectedContentWidth`/`expectedContentHeight` values are computed by literally re-typing the same constants and formula (`maxH`, `maxW`, `notchHeight`, `homeIndicatorHeight`, `frameBorderWidth`, and the same clamp/subtraction arithmetic) that `lib/app.dart`'s `MobileFrame.build` uses to produce the value under test. This means a genuine arithmetic error in the production formula (e.g., a wrong border-width factor, or subtracting `notchHeight`/`homeIndicatorHeight` on the wrong axis) could not be caught by the `width`/`height` assertions — both sides would compute the identical wrong number. Only the independent `expect(captured.size.height, greaterThan(captured.size.width))` orientation check and the `narrow-viewport passthrough` test are behaviorally independent of the formula itself.
- **verification:** Read the test's own comment acknowledging this design choice ("this test doesn't hardcode a value that silently drifts from the widget's own clamp/aspect-ratio logic") — confirming the mirroring is intentional, not accidental. Independently verified the underlying formula IS correct against real Flutter behavior (not just against itself): read `lib/app.dart`'s `Container(decoration: BoxDecoration(border: Border.all(width: frameBorderWidth)))` wrapping the `Column` that contains the notch/content/home-indicator children, and confirmed via Flutter's own `BoxDecoration.padding => border?.dimensions` (a `Border.all(width:)` implies decoration-padding equal to the border width on every edge, via `Container._paddingIncludingDecoration`) that subtracting `frameBorderWidth * 2` from both axes is the mathematically correct net content box — so the current numbers are right; this finding is about the test's ability to catch a *future* regression in that formula, not a live bug today.
- **suggested-fix:** Optional/low-priority: add one assertion computed via a genuinely independent method (e.g., pump the widget tree and read the actual `RenderBox` size of the `Expanded`/`ClipRect` child via `tester.getSize`, rather than only via a second `MediaQuery.of(context)` capture derived from the same formula) so a formula-level regression has at least one behaviorally-independent check, not just the orientation inequality.
- **status:** accepted as noted, not fixed — P4, and the reviewer's own suggested-fix is explicitly framed as optional/low-priority. The test's existing comment already discloses the tradeoff honestly ("this test doesn't hardcode a value that silently drifts from the widget's own clamp/aspect-ratio logic"), and the reviewer independently confirmed the underlying formula is correct via a separate derivation (`Border.all` → `Container._paddingIncludingDecoration`), so this is a residual test-robustness limitation against a *future* formula regression, not a live bug today. Not worth the scope creep of an independent `tester.getSize` assertion in this batch; left as a documented, accepted limitation.
