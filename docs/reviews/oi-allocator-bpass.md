## Finding 1 — P2 — guard_without_its_mirror (lens 6g)
- **file:line:** `scripts/mint_oi.sh:96-113` (the argument-parsing `while`/`case` loop)
- **claim:** A title beginning with `-` can never be minted through the documented CLI (`sh scripts/mint_oi.sh "<title>"`): the parser's `-*) echo unknown flag; usage ;;` arm matches before the catch-all `*) TITLE=$1`, and the script has no `--` end-of-options separator to escape it.
- **verification:** `sh scripts/mint_oi.sh '-fix the retry loop'` (run from any clone with the script)
- **evidence:** Ran it against a throwaway fixture: prints `[mint_oi] unknown flag: -fix the retry loop` and the usage block, exits 64. Nothing is written (fails safely — no ledger commit, no CAS write, no stub), but a perfectly plausible OI title (anything starting with a literal hyphen, e.g. a title pasted from a bullet list, or one describing a negative-offset bug) is simply unmintable via the script's own contract.
- **suggested-fix:** Add a `--` separator to the parsing loop (`--) shift; break ;;` before the `-*)` arm, and document `sh scripts/mint_oi.sh -- "<title>"` for titles starting with `-`), or treat a bare-unmatched-flag-shaped last positional argument as the title when no other flags are pending.
- **status:** accepted — fixed. `--` end-of-options arm added; the unknown-flag message now says where a `-` title goes; usage updated. Test `a title beginning with "-" mints after the "--" end-of-options marker` (mint e2e) pins BOTH paths (bare `-x` still exits 64 and writes nothing; `-- -x` mints). Mutation: deleting the `--)` arm reddens exactly that test (14/15).

## Finding 3 — P3 — guard_without_its_mirror (lens 6b)
- **file:line:** `scripts/check_oi_numbering_unique.dart:309-310` (`mergeHead = _run('git', ['rev-parse','--verify','--quiet','MERGE_HEAD'])?.trim();`) vs `:359` (the `else if (mergeHead != null && mergeHead.isNotEmpty)` mid-merge arm)
- **claim:** The code comment at `:373` says "the mid-merge arm keeps precedence," but that is only true when `git rev-parse --verify --quiet MERGE_HEAD` **succeeds**. If `.git/MERGE_HEAD` exists but is unparseable/corrupt, `_run` returns `null` (its documented "could not answer" contract), `mergeHead` is null, and dispatch silently falls through to the `_boardDirty()` working-tree arm — which the code's own comment says is wrong mid-merge because "the working tree holds BOTH sides' entries and would make every number look contested," i.e. this produces false-positive FAILs, not a silent miss.
- **verification:** Inspect `scripts/check_oi_numbering_unique.dart:83-91` (`_boardDirty`) and `:309-378` (the dispatch chain) — no test in `oi_numbering_gate_e2e_test.dart` constructs a present-but-unparseable `MERGE_HEAD`.
- **evidence:** Code-reading only; this requires an already-corrupted git repository to trigger (a `.git/MERGE_HEAD` file that exists but fails `rev-parse --verify`), so it's a narrow, low-likelihood residue rather than a live path. Not exercised by any fixture (all `MERGE_HEAD`-shaped tests use a real `git merge --no-commit`, which always produces a resolvable `MERGE_HEAD`).
- **suggested-fix:** Treat "the file `.git/MERGE_HEAD` exists" (rather than "rev-parse succeeds") as the mid-merge signal, or explicitly report UNDETERMINED when the file exists but doesn't resolve, rather than silently falling through.
- **status:** accepted — fixed, and the fix found a second, pre-existing defect on the same line. A present-but-unresolvable MERGE_HEAD is now its own arm → `UNDETERMINED`, no comparison, exit 0. Implementing "the file exists" exposed that the gate located the file as the literal `.git/MERGE_HEAD` — which does not exist in a LINKED WORKTREE (`.git` is a one-line file there; §4.13 makes that every session), so the octopus mid-merge count had always read 0 in worktrees. Now resolved via `git rev-parse --git-path MERGE_HEAD`. Two tests (plain clone; linked worktree). Mutations: neutering the new arm reddens 2 (both); restoring the literal path reddens exactly 1 (the worktree test) — `--git-path` is load-bearing there and only there.

## Finding 4 — P3 — guard_without_its_mirror (lens 6e)
- **file:line:** `scripts/mint_oi.sh:212-221` (`cas_write`, git-transport branch: `case "$err" in *"stale info"*|*"already exists"*|*"rejected"*|*"failed to lock"*) return 3 ;; *) ... return 2 ;; esac`)
- **claim:** `*"rejected"*` is a broad substring match. A `git push` refused for a reason unrelated to ref-already-exists — e.g. a server-side branch-protection rule or pre-receive hook applied to `refs/heads/**` — also prints `! [rejected]` and would be misclassified as "taken" (return 3, triggering a retry with N+1) rather than a genuine unreachable/failure (return 2, which stops and reports the real error). Over up to 10 attempts this could exhaust the retry budget and exit 3 ("gave up after 10 lost races") with a misleading message that never surfaces the actual rejection reason.
- **verification:** Built a throwaway repo and ran `git push --force-with-lease="refs/heads/oi/999:" origin HEAD:refs/heads/oi/999` against an unreachable HTTPS/SSH host to confirm genuine network failures do NOT collide with this class (see evidence) — no fixture in this diff exercises an actual server-side push rejection (all e2e fixtures are `file://` bare remotes, which have no hooks/protection to reject with).
- **evidence:** Real DNS-failure text captured directly: `fatal: unable to access '...': Could not resolve host: ...` (HTTPS) and `ssh: Could not resolve hostname ...` / `fatal: Could not read from remote repository...` (SSH) — neither matches any of the four substrings, so the common offline case is correctly classified as unreachable (return 2), not "taken." The gap is specifically a same-repo, reachable-but-policy-rejected push, which is untested and would misclassify.
- **suggested-fix:** Narrow the "taken" match to lease-mismatch-specific text (e.g. `*"stale info"*|*"! [rejected]"*"(fetch first"*|*"non-fast-forward"*`) or check the ref actually exists on the remote (`git ls-remote`) before concluding "taken," rather than pattern-matching push stderr generally. Low priority since it requires branch protection on `refs/heads/oi/*`, which the design explicitly does not expect.
- **status:** accepted — fixed with the second suggestion, because it is the DEFINITION of a lost race rather than a wider grep: on any rejection-shaped stderr, `git ls-remote --exit-code <remote> refs/heads/oi/N` decides — ref present ⇒ taken (return 3, retry); absent or unanswerable ⇒ return 2 with the push's stderr printed, no retry. `cannot lock` added to the rejection shapes (git's server-side lease text). Test: a `pre-receive` hook on the fixture's bare remote refuses every push → exit 2, the hook's message appears exactly ONCE (one attempt, not ten), no ref, no stub. Mutation: restoring the unconditional `return 3` reddens exactly that test (14/15); the two race tests stay green (a real lost lease still finds the ref present).
