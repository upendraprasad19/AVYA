# Payment Flow — Reference

> Razorpay checkout + verification + DPDP §17 erasure (delete-account Edge Function).
> Fetch via Read when working on payment, webhooks, or account deletion.

```
User taps "Upgrade to PRO"
  → Opens Razorpay WebView checkout (amount adjusted for promo if applied)
    (WEB — since 2026-09-17 / ADR-0019: Razorpay Standard Checkout.js via
    dart:js_interop instead of the WebView; same order_id + server amount,
    same verification pipeline below, `payment.failed` wired to the same
    failure snackbar; kill-switch `disable_web_checkout` preserves the
    old mobile-only paywall per-browser)
  → User pays
  → Razorpay webhook → Edge Function (razorpay-webhook)
  → Verify HMAC-SHA256 signature (MANDATORY)
  → Derive plan from payment amount (promo-aware)
  → Write to Supabase subscriptions table
  → Redeem promo code (increment used_count + audit trail)
  → App polls Supabase for confirmation (exact payment_id match)
  → Falls back to verify-payment Edge Function if webhook slow
  → Updates Hive configBox {isPro: true, expiresAt, plan}
  → PRO features unlock immediately
```

## Payment Security Rules (NON-NEGOTIABLE)
1. **Plan derived from amount, NEVER from client:** Both `razorpay-webhook` and `verify-payment` derive the plan (monthly/yearly) from `payment.amount` in paise via `derivePlanFromAmount(amountPaise, promoCode)` (mirrored helper, identical logic in both functions; razorpay-webhook hardened to match verify-payment in Test #11 / Theme I1, 2026-05-04). Client-supplied `body.plan` / `notes.plan` is ignored for entitlement. `computeExpectedAmount` runs as a belt-and-suspenders cross-check after derivation. Prevents a ₹349 monthly payment from getting yearly (365-day) entitlement.
2. **Promo-aware amount validation: tolerant in the WRITERS, strict at the ORDER (payment-hardening U3, OI-366, 2026-10-24).** If `notes.promo_code` exists, the two payment writers (`razorpay-webhook`, `verify-payment`) look up the promo in `promo_codes` and compute the discounted expected amount from `discount_pct`. **Tolerant:** they accept the discounted amount even if the promo has since expired or run out — a payment already made at that price must stay recordable, and Razorpay capture can take minutes. They reject only if the code doesn't exist at all or the discount math doesn't match (which pages, c3e7a1). **Strict where a code is ACCEPTED for a new purchase:** `validate-promo` and `create-razorpay-order` both use `_shared/promo_rules.ts` `promoUsableAt` (inactive, then expired by the IST calendar day — a non-date `valid_until` counts as expired — then exhausted); an unknown or unusable code gives NO order (400 `promo_invalid`), and a failed promo read is an outage (500 `promo_check_unavailable`), never "a dead code". Strict-at-order cannot strand money because the writers stay tolerant. SoT concept `promo_usable_rule`.
3. **Promo redemption on success:** After subscription insert, `increment_promo_used_count` RPC atomically increments `used_count`. Audit row written to `promo_code_uses`. This is non-fatal — subscription is already created.
4. **Two-tier polling with plan filter:** Client polls by exact `razorpay_payment_id` (attempts 0-11), then falls back to any active subscription for the SAME PLAN (monthly/yearly) created in last 5 minutes (attempts 12-14). The plan filter is the safety rail against a monthly→yearly upgrade matching the stale monthly row (audit H5, 2026-04-18). See `razorpay_service.dart` `_pollWithPlanFilter()` (function-name anchor; audit 2026-05-20 / Doc14 swept hard-coded line ranges).
5. **Webhook idempotency:** `razorpay-webhook` handles replay attempts safely:
   - **Replay window (audit C4a, 2026-04-18; per event since OI-341 Piece B2a):** After HMAC verification, the webhook rejects any event whose own top-level `payload.created_at` (the webhook EVENT time, epoch seconds; NOT the payment entity's `created_at`, which for a UPI-collect payment precedes the capture by minutes, F32 audit-2026-06-07) is too old (more than 300 s for `payment.authorized`; more than 24 h + 10 min for `payment.captured` since Piece B2a, rule 10 (e), because Razorpay retries for 24 hours after event creation and nothing shows a retry re-stamps `created_at`) or more than 120 s in the future, with a 400; a missing timestamp skips the check. A stale signed captured event reaches only idempotent code. See `razorpay-webhook/index.ts` HMAC + replay-window block (function-name anchor).
   - **Pre-SELECT** `subscriptions` table by `razorpay_payment_id` BEFORE the INSERT. If a row exists, return 200 immediately with `alreadyProcessed: true` and skip promo redemption.
   - **23505 race fallback:** If two webhook replays race past the pre-SELECT, the second INSERT hits the unique constraint on `razorpay_payment_id` → Postgres throws `23505`. The function catches this code specifically and returns 200 (treats as success).
   - **Promo redemption guard:** `increment_promo_used_count` RPC is ONLY called when `alreadyProcessed === false`. Prevents a replayed webhook from double-incrementing `used_count` and burning the promo for nobody.
   - Razorpay retries webhooks aggressively (up to 24h on non-200). Without idempotency, every retry would write a duplicate subscription row AND re-redeem the promo. Never remove the pre-SELECT or the 23505 catch.
6. **verify-payment rate limit (audit C4b, 2026-04-18; moved onto `usage_counters` OI-162 slice 4, f2c8d5):** 20 calls per user per 10 minutes, enforced atomically via `consume_quota()` against `usage_counters` (quota_key `verify_payment`, fixed 10-minute bucket). Over-limit returns 429 with `Retry-After` set to the bucket's exact remaining seconds (not a fixed 600 — that was the old constant-window value). Fails CLOSED on a counter error, unlike delete-account below — see `verify-payment/index.ts` rate-limit block for why the two differ. Protects Razorpay API quota from a runaway client polling on every tick. ⚠ The PRIOR mechanism (`ai_coach_interactions` rows, `channel='verify_payment_attempt'`) is retired; that channel no longer exists.
7. **Promo codes use year-suffix for annual reuse:** `promo_code_uses` has `UNIQUE(code, user_id)` (migration 023, 2026-04-18). A user who redeems `INDEPENDENCEDAY2026` cannot re-redeem the same code the next year — marketing must generate new codes per campaign (`INDEPENDENCEDAY2027`, etc.). Keeps accounting clean and enables per-year attribution.
8. **The referral reward READS the paid rows these two functions write (migration 159, ADR-0021): treat their shape as a contract.** An hourly pg_cron job (`private.process_referral_conversions`) rewards a referrer when the friend's payment is a `subscriptions` row with `plan` `monthly` or `yearly`, `razorpay_payment_id` set, `status 'active'`, `cancelled_at` NULL, made at or after the moment the code was applied (a timestamp comparison, not a calendar day) and no later than 90 days after it, and 7 days old: 7 days of PRO for monthly, 30 for yearly (the FIRST qualifying payment decides). So a change to what `razorpay-webhook` / `verify-payment` write (the plan derivation, the payment id, the status, a different table, an UPDATE instead of an INSERT) changes who is rewarded, and a row cancelled before the 7 days (status set to `cancelled` by hand: the trigger then stamps `cancelled_at`) voids the reward. Neither function handles refund or dispute events, so a refund that never touches the row is invisible and there is no clawback after the vest. Neither function is edited by the referral change and no trigger sits on `subscriptions`: a referral failure can never block or roll back a payment write. **Since OI-341 Piece B2a** `create-razorpay-order` is the purchase door (rule 10): while it is SHUT it answers 409 for ANY active row including the 7-day `referral_trial` (the reward then lands about 14 days after the friend joins); once it is OPEN the friend CAN buy during the trial, the paid days start at the trial end (rule 9 stacking), and because a purchase made during the trial has `start_date` = the payment instant it qualifies at once, so the referrer's credit lands at payment + 7 days. SoT concept `referral_reward_on_conversion`. **Migration 160 (OI-344) hardens it without touching either payment function:** the credit select skips a row whose friend deleted their account, the redeem RPC retries a brief lock wait instead of surfacing it, the client can no longer read `converted_at` / `referrer_reward_days` / `referrer_credited_at` / `referrer_rewarded` / `referee_rewarded` (the REFERRER could otherwise read WHEN each named friend paid and on which plan; the counts reach the referrer through `public.referrer_summary()`), and `promo_codes.discount_pct` is capped at 90. SoT concept `referrer_summary`.
9. **Subscription stacking (OI-341 Piece A, built 2026-10-17; Piece B1, built 2026-10-20; DARK, not yet reachable):** `verify-payment` and `razorpay-webhook` decide the paid row's `end_date` through `_shared/subscription_stacking.ts` (`isStackingEnabled`, read once per request). **Since Piece B1 the ON path is ONE call to the Postgres function `public.record_paid_subscription` (migration 161)**: it takes the per-user advisory lock shared with the referral redeem and job (so two payments, or a payment and a referral grant, for one user run one at a time and add up), checks idempotency by payment id (another user's id raises P0001), computes the stacked end, refuses a non-finite base (22008, which replaces Piece A's `bad_end_date`) and inserts, in one transaction; `start_date` is `clock_timestamp()` after the lock. On the ON path a failure answers the writer's existing 500, logs the reconcile line below AND writes a `payment_record_failed` alert (`_shared/payment_alert.ts`: critical for the first failure of a payment id, warn after). With the Edge Function secret `ENABLE_SUBSCRIPTION_STACKING` absent (the default; only the exact string `"true"` enables it) it is `now + 30/365 days` as always and NO extra query is issued before the insert (Piece B2a adds ONE alarm read after the OFF insert, rule 10 (c)). Enabled, it is `max(now, the user's latest active, unexpired end other than this payment's own row) + days`, so prepaid time lands AFTER a referral trial instead of alongside it. `start_date` stays the PAYMENT time (rule 8's reward job reads it as the payment time, and PRO is read from `status` and `end_date` only; a future `start_date` would switch PRO on at once). The switch is consulted ONLY in the insert branch, after the idempotency pre-SELECT found nothing (on the ON path the function absorbs the 23505 race and its `inserted` flag decides promo ownership), and the stored value is what the response reports (`verify-payment` `end_date`, the webhook's `expires_at`). A read error or a thrown read FAILS the call (500, no insert, Razorpay or the client retries) and logs `[<fn>] stacking read failed request_id= payment_id= user_id= plan= amount_paise= code=` (the error code only, so a paid-but-unrecorded row can be reconstructed by hand) so a paid-but-unrecorded row can be found and fixed by hand; it never falls back to `now + days`, which would under-deliver paid time. Both functions reject a payment id that is not `^pay_[A-Za-z0-9]{1,64}$` with 400 (`verify-payment`: `Invalid payment_id`, before any Razorpay call; `razorpay-webhook`: `Invalid payment id`, right after the HMAC and the event checks, before any Supabase or Razorpay request). This is validation, not switch-gated: the id is interpolated into the Razorpay API URLs and the stacking read, and the UNIQUE column only dedupes the exact string, so the switch OFF and ON paths treat a malformed id identically. Rule 8's "a friend cannot buy during the trial" holds only while the door (rule 10) is SHUT; while it is shut a payment normally comes from a user with no active row, so even an enabled switch computes today's value (exception: a referral redeemed mid-checkout, caught by rule 10's mismatch alarm). **Enable/flip runbook (Piece B owns the flip; these are the hazards found in review):** (1) the secret value must be exactly `true` with no trailing newline or space (a pasted `true\n` fails safe, i.e. stays OFF, and looks like a no-op); (2) an active row whose `end_date` is unparseable (an `infinity` or garbage value) makes every payment by that user fail with 500 while the switch is ON (`bad_end_date`), and Razorpay then retries money already captured; none is known to exist; (3) apply migration 161 and probe `rpc/record_paid_subscription` through PostgREST (an invalid-plan call must answer the function's own 22023, not PGRST202), then deploy BOTH functions and boot-verify both BEFORE setting the secret (an old webhook with a new verify-payment under an ON switch leaves a payment unstacked, never over-delivered); (4) the 500-and-retry safety net for the webhook assumes Razorpay stamps a retry with a fresh top-level `created_at` (the comment in `razorpay-webhook/index.ts` says so; nothing in the repo evidences it): until a real retry or the docs confirm it, a read failure is recoverable only by the client's in-memory retry timers (60 s, 5 m, 15 m, lost on app kill), so an alert row on the read-failure path is a hard precondition of the flip (**the ALERT half is DONE by Piece B1**, `payment_record_failed`; the retry-timestamp half is CLOSED by Piece B2a, which no longer depends on it: `payment.captured` is accepted up to 24 h + 10 min, rule 10); (5) the reconcile line is a plain `console.error` with the platform's short log retention. **Per-user serialisation: DONE by Piece B1** (the function's advisory lock; proven by `test/sql/record_paid_subscription_local.sh` C1-C4: two queued payments stack 30 then 60, a payment and a referral grant add up in either order, the referral job skips rather than waits). Piece B2a (the door, the alarm, the replay window, both flips; rule 10) is the server half; B2b (the client: per-order estimate, paywall and checkout notice, trial 409 copy, EST seal; concept `trial_stacking_client_estimate`, plan `docs/plans/oi341-piece-b2b-client.md`) is built and reviewed but merged ONLY after the door opens (live step 4a), so the paywall line is true from its first web deploy; the stacked trial purchase (step 4b) then runs through the new client. SoT concepts `subscription_end_date_stacking`, `payment_record_failed_alert`; tests `test/sql/record_paid_subscription_local.sh` (the function, on a disposable replica), `supabase/functions/_shared/payment_alert_test.ts`, `supabase/functions/_shared/subscription_stacking_test.ts` and `verify-payment/index_test.ts` / `razorpay-webhook/index_test.ts` (a fetch-level fake with a golden recording of the unmodified `origin/main` writers for the switch-OFF path).
10. **The purchase door, the switch-mismatch alarm and the replay window (OI-341 Piece B2a, built 2026-10-21; plan `docs/plans/oi341-piece-b2-door.md`).** (a) `create-razorpay-order` reads the caller's active unexpired rows ONCE (no limit). A read ERROR answers 500 `subscription_check_unavailable` and creates no order (before B2a it was ignored and the order was created: fail OPEN). The door is OPEN only when BOTH `ENABLE_TRIAL_PURCHASE` and `ENABLE_SUBSCRIPTION_STACKING` are exactly `"true"` in the door's own isolate (`isEnvExactlyTrue`, read once per request). SHUT: any active row answers today's 409 `already_pro` from the latest-ending row, and the response has no `stacks_after` key. OPEN: a paid (non-`referral_trial`) row answers 409 from the latest-ending PAID row; otherwise the order is created and the response carries `stacks_after` (the latest trial end, null when none), also written into the order notes when non-null; it is an estimate and reconciliation tag only, never read back for entitlement (rule 1: the writers compute their own base). (b) Both writers log `[<fn>] stacking_switch=on|off payment_id=` for every payment that reaches the insert branch, so after a flip each payment shows which state its isolate read. (c) In each writer's OFF branch, ONLY after that request's own insert succeeded (not the skip paths, not the 23505 race arm, not the ON path) and AFTER the promo redemption, one read looks for an active `referral_trial` row of the same user ending after the new row's start. A hit means a trial user was charged while this isolate read stacking OFF (a door-ON order on a stale isolate, a referral redeemed mid-checkout, or a referrer's own credit landing mid-checkout; the last two are possible even with the door shut): it logs `stacking_switch_mismatch` and writes a `stacking_switch_mismatch` alert (critical, deduped per payment on its OWN source, `_shared/payment_alert.ts` `reportStackingMismatch`). The row, the status and the body never change; a read error, throw or hang (bounded at 1 s) is logged and ignored, and each alert round trip is bounded at 1 s, so the alarm adds at most about 3 s to a success response (read, dedup, insert). (d) The webhook's `reportPaymentRecordFailure` round trips are bounded at 1 s (verify-payment keeps 3 s), so its failure 500 stays near Razorpay's 5 s clock. (e) The webhook's replay window depends on the event: `payment.captured` up to 24 h + 10 min (Razorpay retries "for 24 hours after event creation" and nothing shows a retry re-stamps `created_at`), `payment.authorized` 300 s (its path calls the capture API); every event keeps the -120 s future-skew rejection. A stale signed captured event reaches only idempotent code. Stated residual risks: within that day it can re-create a row an operator deleted by hand or after a refund; and a captured event first delivered late records the row from the delivery time, so the user gets up to that delay in extra days (bounded, in the user's favour); a captured event for an account deleted since then fails the insert and retries for up to the window (the ON path pages once). So a paid row that must go is CANCELLED (`status = 'cancelled'`), never deleted, within 24 h 10 min of its payment: a cancelled row still blocks the re-insert, a deleted one does not. (f) A captured payment whose amount matches no plan (a promo code deleted or its percentage edited mid-checkout, or a stray amount), or that fails the webhook's amount cross-check, still answers the same 400, and now also writes a `payment_record_failed` alert with code `amount_no_match` / `amount_cross_check`, because the money is taken and no row can be written (diagnose c3e7a1). **Flip order and rollback** are the plan's section 4 (each step its own founder go; stacking first, then the door; door rollback = unset `ENABLE_TRIAL_PURCHASE` and redeploy the door, stacking stays ON). SoT concept `trial_purchase_door`; tests `supabase/functions/create-razorpay-order/index_test.ts` (a golden recording of the unmodified `origin/main` door for the shut path), the alarm, log-line and replay tests in both writers' `index_test.ts`, and `_shared/payment_alert_test.ts`.
11. **Payment hardening (OI-350/359, OI-360, OI-351, OI-366, OI-406; plan `docs/plans/2026-10-24-payment-hardening.md`, 2026-10-24).** (a) **Ownership before any side effect:** `verify-payment` requires `notes.user_id` (400) and its equality with the JWT caller (403) directly after the Razorpay GET, before it captures an authorized payment or answers with a payment's status (concept `verify_payment_owner_before_capture`, diagnose b5e8d2). (b) **Log safety:** a payment-path log line carries a code, a type, the notes' shape or a bounded, quoted client value (`_shared/payment_log_safe.ts`), never a whole PostgREST error, Razorpay body, the notes or a raw client string; the non-23505 insert failure logs `[verify-payment] subscription insert failed (non-23505) request_id= payment_id= user_id= plan= amount_paise= code=` / `[razorpay-webhook] subscription insert failed (non-23505) payment_id= user_id= plan= amount_paise= code=` (money is captured and no row exists there, so the ids stay), and `redeemPromo` logs a labelled code-only line when `increment_promo_used_count` or the `promo_code_uses` insert returns an error (concept `payment_log_safety`, diagnose d1a4f6; the source contract's rules are in `supabase/functions/CLAUDE.md`, pitfall "A payment-path log carries a whole error"). (c) **Webhook recovery:** when Razorpay refuses (or the call throws on) the webhook's capture of an authorized payment, the webhook re-reads the payment once (1.5 s bound, the GET aborted on timeout) and, only if it is captured for the same id and amount, records the row from the signed event (log `capture refused, payment already captured; continuing`); otherwise today's 502. Kill switch `DISABLE_WEBHOOK_CAPTURE_RECOVERY` (exactly `true` = today's 502) (concept `webhook_already_captured_recovery`, diagnose a9e2f7). (d) **Order and promo-check limits:** `create-razorpay-order` allows 30 order attempts and `validate-promo` 7 checks per user per fixed 1-hour UTC bucket (`consume_quota`, keys `create_order` / `promo_validate`, in the founder digest); the order limit answers 429 and fails CLOSED; validate-promo answers HTTP 200 `{valid:false, reason}` for both its refusals (the paywall shows any non-2xx as "Network error"). Kill switch `DISABLE_ORDER_ABUSE_GUARDS` (exactly `true`, both functions together, also turns off the strict promo rule of rule 2; logged as `order_abuse_guards=<on|off>`). Removal of both switches after their live checks: OI-407 (concepts `create_order_rate_limit`, `promo_validate_rate_limit`, `promo_usable_rule`; diagnose f2c9a8). (e) **`promo_codes` is server-only** (migration 163, OI-406, diagnose a6c2e9): no client role holds a privilege and the table has no policy; the four payment functions read it through the service role. (f) **Hermes pass (diagnose c7e3b1):** the webhook checks `notes.user_id` (present, a UUID) BEFORE it captures an authorized payment, so a payment with no usable user id is refused while only authorized and Razorpay's auto-refund returns the money (an amount that matches no plan is still found after the capture and pages `amount_no_match`, as rule 10 says; OI-409); the outer catch-alls' `stackFrames` reads the stack only after the message and escapes each frame; the outer catch-alls log the error's name and stack frames, never the error; a refused Razorpay order answers 500 with the guards on (the client retries 502/503/504, each retry a unit; validate-promo and consume-day-swap set `spendsQuotaPerCall: true` and are sent once, OI-414, diagnose a6d2f9; create-razorpay-order stays unflagged on purpose: 30 per fixed hour, a duplicate order is unpaid and harmless, the re-send recovers a cold start at payment start; every other per-call-spending call is classified in `docs/audit/oi414-promo-no-gateway-retry.closure.yaml`); validate-promo's limit reason names the wait in minutes; a repeat-use 23505 on `promo_code_uses` is an info line; the founder digest marks both counters UNMETERED while `DISABLE_ORDER_ABUSE_GUARDS` is on and keeps the four abuse-limit counters out of Top users.
12. **`verified: true` means THIS request read the row as active (OI-410, diagnose 060837, 2026-10-26; plan `docs/plans/2026-10-26-oi410-verify-payment-non-active-row.md`).** For a stored `subscriptions` row that the request did not itself insert, `verify-payment` answers `verified: true` only after a read in the same request saw `status === "active"`. Three replay doors read that row: the idempotency pre-select's `else` arm, the OFF-branch 23505 re-read and the stacking-ON `record_paid_subscription` answer with `inserted = false` (migration 161 returns the stored row whatever its status); the early read already filters `status = active` in SQL. One pure function, `replayVerdict`, decides for all three (`ok` / `not_active` / `unconfirmed`), strict equality, and a non-active row answers HTTP 200 `{verified:false, error:"Subscription for this payment is not active"}` while an absent or unreadable row answers HTTP 200 `{verified:false, error:"Could not confirm this payment yet; please retry"}` (no 500 on a returned read error, a transport failure included: supabase-js returns it in `error`, and a test fetch that throws answers the same soft failure; no write, promo or alarm). The founder accepted this as design B2 (it replaces d6b736 F2's seeded `verified:true` when the winner row cannot be re-read; a compound three-failure case now costs one client retry interval). **Client effect:** `razorpay_service.dart` (Phase 2) and `payment_retry_attempt.dart` write PRO only on `verified == true`, so a refusal leaves the optimistic local PRO and the in-flight marker open for the grace window (`kPaymentGraceWindow`, about 21m45s) and `refreshFromSupabase` / `verifyFromServer` keep suppressing a downgrade meanwhile: the fix DELAYS an honest demotion by up to about 20 minutes for the rare class (an operator-cancelled, still-captured paid row inside the confirmation window); it is not a user-visible improvement. The compare is on `status` only, as the early read always was: there is deliberately no `end_date` term, because Phase 2 and the retries run within about 22 minutes of a payment, so a paid row already past its end cannot occur in this flow (the shared PRO predicate `status = active AND end_date > now()` is `_shared/subscription.ts`). How a row becomes non-active is an operator action (rule 8: neither payment writer handles refund events). Two log lines: `[verify-payment] replay refused, row not active payment_id= status=<code token>` and `[verify-payment] replay unconfirmed payment_id= code=`. No runtime switch (founder ruling, 2026-10-26: rollback is a forward-deploy of the previous bundle). SoT concept `verify_payment_verified_means_active_row`; tests `supabase/functions/verify-payment/index_test.ts` (T0-T4) and `test/contracts/verify_payment_verified_means_active_row_writer_to_reader_test.dart`.

## DPDP §17 erasure — hard delete account (Test #11 H1, 2026-05-04)

User-initiated hard delete via `/profile/delete-account` (2-step confirm UI: blast-radius page → type-name+`DELETE` confirm). Client invokes `delete-account` Edge Function with `confirmation_token: 'DELETE-MY-ACCOUNT-${userId.substring(0,8)}'`. Server flow (`supabase/functions/delete-account/index.ts`, `verify_jwt: true`):

1. JWT re-validated server-side via `userClient.auth.getUser()`.
2. **Rate limit — 5 attempts per user per hour** (Hermes-R2 #9, 7ad009), enforced atomically via `consume_quota()` against `usage_counters` (quota_key `delete_account`, fixed 1-hour bucket; OI-162 slice 4, f2c8d5). Fails OPEN on a counter error — a DPDP §17 erasure is a legal right and must not be blocked by a counter outage; contrast verify-payment above, which fails closed. ⚠ **This limit did not function before f2c8d5** — its prior mechanism (`ai_coach_interactions` insert) hit two schema violations (nonexistent columns, a NOT NULL column left unset) on every call, silently, so the count was always 0.
3. Confirmation token check — exact match required (token derivation defends against stolen-JWT replay where attacker doesn't know user ID prefix).
4. **Razorpay subscription cancel — best-effort, NON-FATAL (a2c8e6).** For every active sub on the user, POST to `https://api.razorpay.com/v1/subscriptions/{id}/cancel`. ⚠ This row previously said "MUST SUCCEED... any non-200/exception → return 502, abort" — that described the PRE-a2c8e6 behaviour and was stale by the time this correction was made (2026-09-11). The live code cancels FIRST (protects the user from post-deletion charges on success) but a FAILURE is now recorded durably in `account_deletion_log.razorpay_cancel_status` and the erasure PROCEEDS — a Razorpay outage must not indefinitely block a legally-required deletion. See `delete-account/index.ts` step 4 comment block (function-name anchor) for the full reasoning.
5. **OneSignal player_id unsub** (best-effort, logged on failure). Reads `user_progress.onesignal_player_id` (column added by migration 049). Note: Flutter app doesn't yet write this column — known gap. Delete still succeeds; push unsub silently no-ops until the write path is wired.
6. **Storage purge** across every bucket in `_shared/user_owned_buckets.ts` `USER_OWNED_BUCKETS` — `progress-photos`, `chat-media`, `coach-media`, `avatars`, `banners`, each under `<uid>/`, recursive (`_shared/purge_user_storage.ts`; best-effort, per-bucket errors accumulated into `purgeStats.errors[]`). ⚠ Until 2026-09-26 only the first three were purged, so a deleted user's avatar and banner stayed reachable in two PUBLIC buckets (single-owner audit P0 #6). `test/contracts/delete_account_purges_all_user_buckets_test.dart` fails if the client writes to a bucket this list does not name.
7. **`auth.users` delete** via service role — CASCADE through `public.users` (FK with `ON DELETE CASCADE` from migration 039) and every user-scoped table. **5 community surfaces are exempt from cascade** (migration 049, `ON DELETE SET NULL`): `user_custom_exercises`, `user_custom_foods`, `community_reviews` (FK on `reviewer_id`, not `user_id`), `food_corrections`, `promo_code_uses`. Their rows survive with `user_id = NULL` ("deleted user" pseudonymization). Read consumers MUST tolerate NULL. **A sixth surface since migration 158 (OI-320, 2026-10-11): `referral_redemptions`** — both `referrer_id` and `referee_id` are nullable `ON DELETE SET NULL`, so the audit row of a referral outlives either party's account (the deleted party's id becomes NULL). That is deliberate: the audit row is the referrer's reward record and `UNIQUE(referee_id)` keeps a referee from redeeming a second code; with CASCADE an account deletion would delete that record or hand a deleted referee a second code.
8. **Audit row** to `account_deletion_log` (no FK, survives cascade). Captures `deleted_user_id`, `deleted_at`, `request_id`, `razorpay_cancel_status`, `storage_purge_status` JSONB.
9. Client wipes Hive (`HiveService.instance.clearAllData`) + `signOut(global)` + routes to `/sign-in`.

Step 1 copy explicitly states: subscription cancelled with no refund, Razorpay payment receipts retained per Indian tax law, backups purge within 30 days. No refund automation, no 24-hour grace period, no soft-delete fallback.

`UserRepository.softDeleteAccount` is `@Deprecated` — kept for back-compat only, no active callers remain.
