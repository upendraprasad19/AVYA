## Findings

### Finding 1 — P2 — OI-205's "consistently extended, not a new regression" framing understates a real asymmetry between `/confirm` and `/reset`

- **file:line:** `docs/audit/open_issues.md:4383-4392` (OI-205 "Scope note"); `lib/features/auth/CLAUDE.md`'s pitfall-table row "An already-authenticated user opening a valid `/reset` or `/confirm` link…"; `android/app/src/main/AndroidManifest.xml:57-74` (new `autoVerify="true"` intent-filter, added by THIS branch, for `/confirm` only); `lib/core/router/app_router.dart:638,641,672,675` (`isOnReset`/`isOnConfirm` passthroughs); `lib/features/auth/widgets/forgot_password_sheet.dart:77-79` (`resetPasswordForEmail(redirectTo: 'https://app.icanbefitter.com/reset')`, unchanged by this branch).
- **claim being checked:** OI-205 and the new CLAUDE.md pitfall row both assert `/confirm`'s "already-authenticated user gets silently switched to a different account" risk is the SAME shape `/reset` has always had — "not a brand-new pattern… this diff extends it to a second entry point" — implying the two are symmetric and the deferral-to-OI is equally low-stakes for both.
- **verification performed:** Read `_authRedirect` in full (`app_router.dart:630-745`). Confirmed `isOnReset` (`:638`, passthrough at `:672`) and `isOnConfirm` (`:641`, passthrough at `:675`) really are structurally identical — both return `null` unconditionally, above `isAuthenticated` at `:692`. That part of the claim is accurate.
  But then grepped the ENTIRE `AndroidManifest.xml` for every `intent-filter`/`android:host`/`android:path`/`autoVerify` (`grep -n "intent-filter\|android:host\|android:path\|android:scheme\|autoVerify\|launchMode"`): there is **no Android App Link registered for `/reset` anywhere** — the only `https://app.icanbefitter.com/...` App Link in the whole manifest is the brand-new one this branch adds, scoped to `path="/confirm"` exactly. `forgot_password_sheet.dart:79`'s `redirectTo` still points at a bare web URL with no native-app claim, and per `docs/diagnoses/2026-08-06-reset-link-device-bound-pkce-c9e2b7.md`, the live password-reset flow was redesigned in 2026-08 to a 6-digit code typed directly into `ForgotPasswordSheet` — the common case involves no tappable link at all any more (`password_recovery_detector.dart`'s `?code=`/`#type=recovery` detection is legacy-email backward-compat, not the primary path).
  So on Android, a `/reset` link — if one is ever tapped at all — opens a **browser**, a separate Flutter-web instance with its own session storage, structurally incapable of touching the native app's live session. `/confirm`, by contrast, is now an OS-level `autoVerify` App Link: tapping `app.icanbefitter.com/confirm?...` from ANY app (Gmail, WhatsApp, SMS, a browser) on a phone with the native app installed hands control DIRECTLY to the already-running Activity via `onNewIntent`/`singleTop`, regardless of what screen an already-signed-in user is currently on — no "happens to be in the same browser tab" precondition required. This is a materially NEW, more automatic, more silent account-switch surface that `/reset` never had and still doesn't have. The router-guard-shape symmetry is real; the real-world-reachability symmetry the OI's "Scope note" implies from it is not.
- **suggested fix:** Correct OI-205's "Scope note" and the CLAUDE.md pitfall row to state this asymmetry plainly — `/confirm`'s exposure is broader and more automatic than `/reset`'s because of the new native App Link, not merely "the same shape extended to a second entry point" — so whoever eventually prioritizes OI-205 is working from an accurate risk picture. This is a cheap, non-blocking doc correction. Separately (a product call, not something I'm prescribing): given `/confirm` is the one being armed with a brand-new automatic OS-level trigger in this very commit, consider whether it alone warrants the minimal interim guard the B-pass's Finding 4 already proposed (an `isAuthenticated` check + a lightweight "you're signed in as X — confirm to switch accounts" step) ahead of `/reset`, rather than waiting for a single UX decision that covers both symmetrically.

### Finding 2 — informational only — the `vercel.json` `.well-known` fix conflicts with Vercel's own current docs, but is empirically necessary and correctly implemented

- **file:line:** `vercel.json:11-13`; `web/.well-known/assetlinks.json` (new).
- **claim being checked:** the branch's stated rationale (`lib/features/auth/CLAUDE.md`, code comments) — that the old unconditional `"source": "/(.*)"` rewrite would swallow `/.well-known/assetlinks.json` and serve `index.html` instead, silently breaking Android App Link `autoVerify` — is load-bearing enough to verify independently rather than take on faith.
- **verification performed:** Fetched Vercel's current "Rewrites on Vercel" doc directly (`https://vercel.com/docs/routing/rewrites`), which states: *"The /.well-known path is reserved and cannot be redirected or rewritten"* — read literally, this would make the branch's fix unnecessary. To resolve the conflict I tested the LIVE, currently-deployed (pre-merge) production URL: `https://app.icanbefitter.com/.well-known/assetlinks.json` right now returns the Flutter-web SPA's `index.html` shell (title "Avya FIT"), not a 404 and not JSON — empirically proving the OLD catch-all rewrite DOES currently swallow this path in production, contradicting Vercel's own documentation for this project's actual configuration. This confirms the underlying bug is real, not a false premise. I then independently confirmed the new regex `"/((?!\\.well-known/).*)"` matches Vercel's own officially-documented negative-lookahead idiom for excluding a prefix from a same-application rewrite (their docs show the identical shape: `"source": "/:path((?!uk/).*)"`), so the fix should resolve it once deployed.
- **suggested fix:** None to the code — it's correct as written. Recommend a one-time post-deploy smoke check once this branch merges (`curl -I https://app.icanbefitter.com/.well-known/assetlinks.json`, expecting a real JSON body, not the SPA shell) before relying on `autoVerify` succeeding, since this specific mechanism can't be verified from `flutter test` (already honestly stated in the nested CLAUDE.md). Also worth knowing for future work: don't trust Vercel's "`.well-known` is reserved" documentation at face value for this project — it does not match observed behavior here.
